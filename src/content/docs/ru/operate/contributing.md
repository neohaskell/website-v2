Чтобы сделать фреймворк лучше, не нужно понимать его целиком. Непонятный шаг установки, пропущенный пограничный случай или пример, который больше не компилируется, — полезная отправная точка. Ваш опыт изучения NeoHaskell или создания приложения показывает, где может столкнуться со сложностью следующий читатель.

Вклад — отдельная ветка пути приложения. Для уверенной эксплуатации приложения не нужно становиться сопровождающим фреймворка.

## Начните с ограниченного улучшения

Хорошее первое сообщение содержит цель, самую маленькую воспроизводимую ситуацию, ожидаемое поведение, фактический результат и соответствующую версию. Перед публикацией удалите учётные данные и личные данные.

В изменении документации сохраняйте постепенный путь обучения: сначала объясните ситуацию, приведите точный пример и скажите, как читатель может проверить результат. Для ошибки добавьте регрессионный случай, который падает по заявленной причине, до изменения реализации.

## Найдите ответственную часть

| Область | Часть репозитория |
| --- | --- |
| Терминология языка и фреймворк сервисов | `core/` |
| Исполняемые примеры корзины/запаса и HTTP-приёмочные тесты | `testbed/` |
| Интеграции провайдеров | `integrations/` |
| Rust CLI и встроенная визуальная IDE | `neo/` |
| Документация для людей | `website/` |
| Архитектурные решения | `docs/decisions/` |

Прочитайте [README для участников](https://github.com/neohaskell/NeoHaskell/blob/main/README.md) и [карту возможностей](https://github.com/neohaskell/NeoHaskell/blob/main/codemap/README.md). Карта связывает концепцию с реализацией и тестами, поэтому небольшое исправление не обязано превращаться в неограниченное исследование репозитория.

## Работайте с цепочкой инструментов репозитория

Из клона репозитория NeoHaskell команды `./dev` при необходимости входят в зафиксированную среду:

```sh
./dev watch
```

Оставьте этот наблюдатель запущенным во время редактирования. В другом терминале:

```sh
./dev check
./dev test "EventStore" nhcore-test-service
./dev lint
```

`./dev test "EventStore" nhcore-test-service` — пример сфокусированного выбора тестов. Выбирайте тесты, устанавливающие именно ваше изменение; несвязанный набор не даёт свидетельств. Для сервисных тестов может потребоваться PostgreSQL, а HTTP-приёмочным тестам — настоящие фикстуры. Подробности описаны в README участника.

Эти команды репозитория отличаются от `neo build` и `neo test`, которые работают со сгенерированными приложениями. Для изменений Rust CLI и IDE действуют отдельные scoped-инструкции и уровни тестов под `neo/`.

## Сначала предложите публичное поведение, потом широкую реализацию

Репозиторий использует спецификации изменений и черновые pull request для управляемых изменений. Спецификация объясняет обещанную разницу API и называет тесты, доказывающие каждый критерий. Проверка сопровождающего предложения предшествует большой реализации; итоговая проверка рассматривает реализованный результат и свидетельства.

Прочитайте текущий [контракт участия в репозитории](https://github.com/neohaskell/NeoHaskell/blob/main/AGENTS.md), чтобы узнать точные границы, процесс веток/стеков, этапы проверки и исключения. Не меняйте существующие ожидаемые результаты тестов только для того, чтобы ошибка стала зелёной. Объясните изменение поведения, видимого пользователю, и получите требуемую проверку сопровождающего.

## Углубляйтесь, когда этого требует изменение

Архитектура основного сервиса разделяет решения команд, сохранение событий, восстановление сущностей, запросы, транспорты и интеграции. Изменение одного публичного события может повлиять на несколько таких частей. Следуйте ответственным тестам и архитектурным решениям, затем проверьте и публичное справочное приложение, и локальный модуль.

Изменение CLI также может повлиять на каждое вновь созданное приложение. Встроенный стартовый проект и проверки совместимости стартового проекта с фреймворком относятся к той же ответственности.

**Попробуйте внести первый вклад:** выберите непонятный момент учебного пути или собственного проекта. Напишите объяснение, которого вам не хватало, найдите публичный исходник, его подтверждающий, и попросите другого читателя пройти этот путь. Это конкретное улучшение даже до прикосновения к внутреннему устройству фреймворка.
