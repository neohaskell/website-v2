Пользователь сообщает, что принятое изменение не видно. Нужно отличить отклонённый запрос, задержанное представление, неверный аккаунт и внешнюю ошибку. «Сервер работает» отвечает лишь на небольшую часть этого вопроса. В учебном интернет-магазине сообщение может звучать так: «Я добавил товар, но корзина не изменилась».

Наблюдайте приложение по уровням: процесс, сохранённые факты, представления и внешние результаты. Каждое оповещение должно отвечать на вопрос, с которым человек может что-то сделать.

## Начните с двух встроенных сигналов

Для приложения со стандартной веб-проводкой на порту 8080:

```sh
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/ready
```

Ответ готовности — агрегированное состояние:

```json
{"status":"ready"}
```

Во время догоняния он равен `{"status":"rebuilding"}` с HTTP `503`. При ошибке также возвращается `503`, `status` получает значение `failed`, а ответ содержит `reason`. Текущий HTTP-ответ не является панелью значений отставания для каждого запроса.

Здоровый процесс может перестраивать запросы. Готовый процесс всё ещё может столкнуться с недоступным внешним провайдером. Бизнес-операцию отслеживайте отдельно.

## Читайте журналы приложения

Модуль `Log` записывает JSON-записи в стандартный вывод с полями `time`, `level` и `message`, а также, когда доступны, с информацией места вызова и полями области фреймворка. Хост должен собирать, хранить и делать эти записи доступными для поиска.

Для локального диагностического запуска:

```sh
LOG_LEVEL=debug neo run
```

Уровень по умолчанию — `Info`; реализация распознаёт написания debug, info, warn, error и critical в нижнем, обычном или верхнем регистре. Для изменения окружения нужен новый процесс. `neo --verbose` управляет подробностью CLI, а `LOG_LEVEL` — журналированием приложения.

Журналы фреймворка указывают прогресс и ошибки воспроизведения запросов. Сообщения о прогрессе содержат `events_replayed`, `lag_from_head` и `duration_seconds` внутри текста сообщения. Не считайте, что эти значения отдельно экспортируются как метрики. Тест холодного запуска проверяет сообщения о прогрессе и убеждается, что журналы ошибок содержат идентичность и позицию запроса, но не полезную нагрузку события.

[Изучите реализацию журналирования](https://github.com/neohaskell/NeoHaskell/blob/main/core/core/Log.hs) и [проверку холодного запуска](https://github.com/neohaskell/NeoHaskell/blob/main/testbed/scripts/cold-start-readiness.sh).

## Проследите одну операцию по системе

Запишите версию, примерное время и безопасный идентификатор операции или сущности. Сохраните идентификатор корзины, возвращённый запросом `mug-shop`. Затем спросите:

1. Команда завершилась успехом или сообщила об отказе?
2. Содержит ли долговременная история ожидаемый факт?
3. Догнал ли нужный запрос историю и разрешено ли читателю его видеть?
4. Если ожидалась интеграция, какой результат она сообщила?
5. Стал ли результат следующим бизнес-фактом или последующая работа ещё ожидает?

Используйте [граф IDE](/ru/getting-started/visual-ide/), чтобы найти ответственную команду, событие, запрос и интеграцию. Он объясняет связи в исходном коде, но не показывает живую историю базы данных и не заменяет production-мониторинг.

Выбирайте безопасные диагностические идентификаторы. Личные адреса, токены доступа, загруженные документы и полные ответы провайдера обычно не должны попадать в обычные журналы. Скрытие типизированного поля конфигурации не скрывает произвольный текст, который вы позднее записываете в журнал.

## Упражнение: зелёный процесс с ожидающим результатом

После добавления внешней интеграции в `mug-shop` спроектируйте staging-сценарий, в котором запускающее изменение принято, но внешнее подтверждение задерживается. До запуска опишите состояние, видимое покупателю, и сигнал, видимый оператору.

<details>
<summary>Подсказка для рассуждения</summary>

Состояние может оставаться зелёным, пока подтверждение ожидает. Соответствующее представление должно честно сообщать промежуточное состояние. Оператору нужны длительность ожидания и безопасный идентификатор корреляции. Многократный перезапуск здорового процесса вряд ли устранит отказ провайдера и может усложнить диагностику.

</details>

Используйте [восстановление](/ru/operate/recovery/), когда диагностика выявит прерванную работу или потерянную инфраструктуру.
