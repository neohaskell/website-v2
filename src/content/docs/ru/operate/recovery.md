Восстановление базы данных возвращает только одну часть приложения. Внешние системы могут по-прежнему помнить работу, которой нет в восстановленной копии. Восстановление должно учитывать обе истории, не повторяя завершённые операции и не забывая молча незавершённые. В примере интернет-магазина это может означать согласование платежа без повторного списания с покупателя.

История событий помогает восстановить состояние приложения. Она не создаст заново потерянное вложение по метаданным и сама не отменит внешний платёж. Восстановление включает ресурсы и организации вокруг приложения.

## Сначала определите, что сломалось

| Наблюдение | Что исследовать до изменения данных |
| --- | --- |
| Нет ответа `/health` | Запуск процесса, конфигурация, соединение с базой, привязка порта |
| `/health` работает, `/ready` остаётся `503` | Прогресс или ошибка перестройки запроса |
| Готово, но одно представление неверно | Логика проекции, сохранённые события, авторизация, запущенная версия |
| Метаданные файла есть, скачивание не работает | Том байтов и состояние жизненного цикла файла |
| Провайдер сработал, результат приложения неопределён | Идентичность транзакции провайдера и локальная история продолжения |

Сохраните полезные журналы и идентичность неисправной версии. Слепой сброс базы может уничтожить свидетельства, нужные для различения этих случаев.

## Репетируйте восстановление в изолированной среде

Сначала завершите [настройку хранения](/ru/operate/persistence/); у начального хранилища в памяти нет сохранённой истории для восстановления. До того как люди начнут полагаться на сохранённые данные, проведите репетицию с характерными операциями:

1. Создайте небольшую известную историю: принятое изменение, отклонённое изменение и любое поддерживаемое вложение или результат интеграции. В `mug-shop` создайте корзину, добавьте положительное количество и подтвердите отказ для нуля.
2. Создайте резервную копию по процедурам базы данных и файлового хранилища вашего хостинга.
3. Восстановите данные в изолированной среде с выключенными внешними эффектами или с их заменой контролируемыми тестовыми конечными точками.
4. Запустите `neo run` из проекта восстановленного приложения с изолированной конфигурацией хранения и дождитесь `/ready`.
5. Сравните восстановленные сущности и представления с известной историей.
6. Проверьте байты вложений, границы авторизации и обработку незавершённой внешней работы.
7. Запишите длительность восстановления и последнюю принятую операцию, вошедшую в резервную копию.

Включите в репетицию заброшенные загрузки. В модуле загрузки файлов есть рабочий очистки, но обычный запуск приложения сейчас его не запускает. Не считайте, что заданный срок или интервал очистки доказывает удаление просроченных байтов.

Последние два измерения отвечают на бизнес-вопросы: как долго приложение может быть недоступно и сколько недавней работы может потребовать согласования? NeoHaskell не выбирает эти допуски за вас.

## Репетируйте с локальной базой Postgres

Для базы Docker Compose из раздела [хранение](/ru/operate/persistence/) можно потренировать восстановление только базы, не заменяя исходную. После создания известной корзины и записи её итога остановите `neo run`. Из `mug-shop` экспортируйте локальную базу в защищённый файл резервной копии:

```sh
docker compose exec -T postgres pg_dump -U neohaskell -d neohaskell --format=custom > mug-shop.backup
```

Создайте новую базу в том же локальном сервисе Postgres и восстановите в неё данные:

```sh
docker compose exec -T postgres createdb -U neohaskell mug_shop_restore
docker compose exec -T postgres pg_restore -U neohaskell --dbname=mug_shop_restore < mug-shop.backup
```

`createdb` должен завершиться ошибкой, если база восстановления уже существует. Для следующей репетиции выберите новое имя, а не заменяйте данные, которые ещё не проверили. До запуска приложения убедитесь, что обе команды завершились успешно.

Если вы добавили настоящие исходящие интеграции, сначала используйте контролируемые конечные точки провайдера или удалите их регистрации в изолированной версии приложения. Затем выберите восстановленную базу конфигурацией:

```sh
DB_NAME=mug_shop_restore DB_PASSWORD=neohaskell neo run
```

Сохраните собственный `DB_PORT`, если использовали его для локальной базы. В другом терминале проверьте `/ready` и получите исходный итог Cart с тем же идентификатором, используя запросы из раздела [HTTP и фронтенд](/ru/build/http-and-frontend/). Сравните его до запуска тестов или создания новых данных. Резервная копия содержит данные базы, включая потенциально чувствительную историю событий; храните её с подходящей защитой доступа.

Эта процедура восстанавливает базу событий. Байты загрузок и отдельные хранилища учётных данных провайдеров требуют собственных копий. Успешный `pg_restore` — начало проверок приложения, а не их замена.

## Поймите границу перестройки

Подписчик запросов может перестраивать представления из событий и предоставляет состояния готовности. Существуют низкоуровневые API `rebuildAllAsync`, `rebuildFrom` и контрольных точек; это API приложения или фреймворка, а не команда `neo rebuild`.

Обычная проводка `Application` сейчас создаёт `Subscriber.new`, не подключая хранилище контрольных точек автоматически. Одни только постоянные строки запросов не доказывают продолжение по контрольной точке. Проверьте именно используемые хранилище, путь запуска и логику проекции; см. [хранение данных](/ru/operate/persistence/).

Хранилище запросов Postgres создаёт таблицу, если её нет. Это не универсальный сервис миграции схемы. Для существующих установок с несовместимой схемой таблицы нужен явный план миграции.

## Восстанавливайте внешнюю работу по идентичности

Храните достаточно информации, чтобы связать операцию приложения с её внешним соответствием. В будущем рабочем процессе платежа учебного интернет-магазина это означает связь заказа с операцией провайдера. Определите, что происходит, когда провайдер принимает запрос, но соединение обрывается до ответа.

Это требование дизайна вашего адаптера платежей, а не утверждение, что NeoHaskell поставляет полную систему платежей и согласования. Идемпотентность и получение статуса, которые поддерживает провайдер, могут помочь в проектировании; их точные гарантии нужно проверить у выбранного провайдера.

## Упражнение: прервите передачу

Для описанного выше дизайна платежа организуйте контролируемый тест, в котором внешняя операция завершается успехом, но локальное подтверждение прерывается. Перезапустите приложение и изучите результат. Примените тот же метод к внешнему побочному эффекту собственного приложения.
