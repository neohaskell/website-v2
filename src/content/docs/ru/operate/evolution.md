Требования меняются, а существующие данные сохраняют свой смысл. Новый код должен поддерживать обе реальности. Например, добавление необязательного текста в новые записи не должно притворяться, будто прежние пользователи его указали. В учебном проекте интернет-магазина попробуйте добавить необязательную заметку в новые Cart, сохранив для старых явное отсутствие такой информации.

Система с событийным хранением делает историю явной. Это ценно для объяснения решений, но создаёт ответственность: будущий код должен по-прежнему понимать уже принятые факты.

## Классифицируйте изменение до написания кода

| Изменение | Главный вопрос |
| --- | --- |
| Новое правило для будущих операций | Можно ли по-прежнему восстановить существующее состояние до запуска нового решения? |
| Новый вид события | Смогут ли старые и новые версии приложения прочитать все истории, с которыми могут столкнуться? |
| Изменение формы сохранённого события | Как исторический JSON останется декодируемым и осмысленным? |
| Новый или изменённый запрос | Сможет ли он правильно восстановиться по всем поддерживаемым историям? |
| Новый внешний рабочий процесс | Может ли выпуск или воспроизведение повторить внешнее действие? |

Используйте [моделирование событий](/ru/start/event-modeling/) и [визуальную IDE](/ru/getting-started/visual-ide/), чтобы определить затронутых потребителей. Изменение одного события может по-разному повлиять на команды, запросы и интеграции.

## Сохраните историческую фикстуру

До принятия изменения храните в тестах небольшую характерную историю. Включите поведение до и после изменения, а также отклонённую операцию. Для примера интернет-магазина используйте старую Cart и новую Cart с заметкой. Проверьте, что новый код:

- декодирует сохранённые события старого и нового формата;
- восстанавливает задуманное состояние каждого;
- применяет новое правило только там, где этого хочет бизнес;
- строит ожидаемые результаты запросов после воспроизведения;
- не повторяет внешний эффект во время упражнения.

Успешная компиляция типа JSON не доказывает, что исторический JSON успешно декодируется. Храните исторические случаи рядом с тестами `Shop.Cart` и запускайте `neo test` из `mug-shop` против одноразовой базы данных. За исполняемыми свидетельствами обратитесь к разделу [тестирование](/ru/build/testing/).

## Используйте блокировку предметной области как напоминание

Из корня сгенерированного проекта CLI может заблокировать найденные файлы предметной области:

```sh
neo lock --all
neo lock install
neo lock check
```

До блокировки проверьте `git status` и очистите постороннюю подготовленную работу. Блокировка добавляет выбранные файлы и `.locked-files` в staging и создаёт коммит Git; уже подготовленное содержимое может попасть в него тоже. `neo lock install` записывает путь к pre-commit hook, поэтому существующий hook нужно осознанно сохранить и объединить.

Манифест — `.locked-files`; установленный Git hook и `neo build` проверяют изменения заблокированных путей. `neo lock check` включает подготовленные, неподготовленные и неотслеживаемые изменения. Блокировка помогает сделать существенное редактирование осознанным. Она не устанавливает совместимость схемы и не предоставляет реализацию миграции.

`neo build --skip-lock-check` существует для намеренного обхода на этапе сборки. Отдельно решайте лежащий в основе вопрос совместимости истории; обход проверки на него не отвечает.

## Не считайте, что изменения запросов мигрируют сами

Хранилище запросов Postgres и подписчик предоставляют операции хеширования и контрольных точек. Само их наличие не означает, что каждое изменение функции запроса обнаруживается или мигрирует автоматически, и не означает, что обычный запуск приложения включает продолжение по контрольной точке. Спланируйте и проверьте перестройку в соответствии с настоящей проводкой приложения.

Для несовместимой сохранённой схемы запроса сделайте переход явным. Сохраните авторитетную историю событий и отрепетируйте переход на восстановленной копии. Укажите, может ли прежняя версия работать с полученными данными; «откатить бинарник» после изменения данных бывает недостаточно.

## Упражнение: добавьте заметки Cart

В учебном проекте интернет-магазина попросите агента предложить, как новые Cart получают необязательную заметку и что показывают старые. До принятия кода самостоятельно объясните поведение старой истории.

<details>
<summary>Полезная граница принятия</summary>

Старая Cart должна сохранить исходный смысл с явным отсутствием заметки. Новая Cart с заметкой должна сохранять её после перезапуска и воспроизведения. Заметка, нарушающая выбранную политику размера или содержимого, должна быть отклонена до превращения в принятый факт. До проверки реализации выберите точную политику этого упражнения.
