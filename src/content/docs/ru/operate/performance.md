Приложение, которое кажется быстрым на маленьком наборе данных, может вести себя иначе по мере роста истории и числа одновременных действий. Работа с производительностью начинается с выбора опыта, который должен оставаться приемлемым: отправка изменения, чтение результата или перезапуск после выпуска. Напряжённая распродажа в учебном интернет-магазине даёт конкретную нагрузку для исследования.

Архитектура NeoHaskell задаёт этим операциям разную работу. Измеряйте их отдельно до изменения размеров пулов или добавления параллельности.

## Выберите наблюдаемый бюджет

Записывайте цель вместе с нагрузкой. Для интернет-магазина проверяемо утверждение «доступность Stock появляется в согласованное время, пока несколько покупателей резервируют последние кружки». «Фреймворк быстрый» — не проверяемое утверждение.

Измеряйте как минимум:

- время ответа команды, включая отказы;
- время до отражения принятого события соответствующим запросом;
- время запуска до `/health` и отдельно до `/ready`;
- длительность внешнего провайдера и возраст ожидающей работы;
- соединения с базой, расход ресурсов и частоту ошибок во время теста.

Сохраняйте вместе с результатом версию приложения, размер набора данных, размер машины и нагрузку. Измерение только Cart не предсказывает задержку будущей интеграции платежей.

## Поймите конкуренцию за одну сущность

Одновременные команды могут конкурировать за изменение одной сущности. В примере интернет-магазина два покупателя могут попытаться зарезервировать последнюю кружку у одной сущности Stock. Оптимистическая конкуренция обнаруживает конфликтующие записи, а исполнитель команды может заново получить состояние и повторить решение.

Текущий исполнитель допускает максимум 10 повторов при конфликте, используя экспоненциальную задержку с дрожанием и ограниченной верхней границей. Это ограниченный механизм конфликтов, а не гарантия успеха всех запросов при неограниченной конкуренции. Сохраняйте бизнес-решения детерминированными и не помещайте внешние эффекты в решение, которое может выполняться снова.

Спросите, не содержит ли одна сущность несвязанную друг с другом активность. Разделение независимой активности — например, запаса для разных товаров — может уменьшить конкуренцию, но разделение одного неделимого бизнес-инварианта может усложнить корректность. Сохраняйте правило, которое пытаетесь обеспечить.

## Рассчитайте соединения с базой по всему развёртыванию

Хранилища событий Postgres, хранилища запросов, хранилища состояния файлов и слушатели создают спрос на соединения. Размеры пулов по умолчанию равны 6 для `PostgresEventStore` и 4 для `PostgresQueryObjectStoreConfig`; это не универсальная рекомендация по ёмкости.

Инвентаризируйте реальные пулы, созданные вашей проводкой, их ограничения, соединения слушателей и число процессов. Учитывайте старые и новые процессы, живущие во время выпуска, а также запас для операторов и обслуживания. Подписки на отдельные потоки могут добавить спрос сверх простой суммы фиксированных пулов.

Увеличение пула может перенести узкое место в Postgres. До и после изменения измеряйте очередь, длительность запросов и ошибки.

## Тестируйте воспроизведение по мере роста истории

Используйте одноразовую базу Postgres, настроенную через [хранение данных](/ru/operate/persistence/). Создайте характерные Cart и принятые добавления через HTTP-маршруты приложения, запишите ожидаемые результаты Cart и Stock, затем остановите приложение. Из того же каталога `mug-shop` и против той же базы запустите его снова:

```sh
LOG_LEVEL=info neo --ci run
```

В другом терминале проверьте два сигнала отдельно:

```sh
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/ready
```

Запишите момент, когда каждый становится успешным, и сравните результаты запросов с ожидаемыми значениями. Повторите с большей известной историей. Для любых внешних эффектов используйте контролируемые замены, чтобы эксперимент воспроизведения не отправлял настоящие уведомления и не повторял действия провайдера. Начальное хранилище в памяти не позволяет измерить восстановление истории после перезапуска.

Храните повторно используемые сценарии запросов в `tests/` и запускайте `neo test` для проверок корректности. Измеряйте время запросов и готовности приложения отдельно от времени компиляции CLI. Быстрые неверные результаты — провал теста.
