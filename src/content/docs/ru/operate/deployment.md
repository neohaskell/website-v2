Выпуск успешен, когда задуманная версия обслуживает корректное поведение, а не просто когда завершается команда развёртывания. Для сервиса с событийным хранением не направляйте трафик к свежему процессу, пока его модели чтения догоняют историю. То же правило относится к представлению бронирования, очереди документов или итогу корзины учебного проекта.

NeoHaskell предоставляет исполняемое приложение и HTTP-конечные точки проверок. Среда размещения предоставляет менеджер процессов, маршрутизацию трафика, секреты, долговременное хранилище и политику перезапуска. В текущем CLI нет команды `neo deploy`.

## Подготовьте то же приложение для хоста

Продолжайте с проектом `mug-shop`, включая `neo.json`, `src/Shop/Cart/`, `src/Shop/Stock/` и тесты. До обещания, что принятые изменения переживут перезапуск, завершите [настройку хранения](/ru/operate/persistence/). Начальная конфигурация `SimpleEventStore` намеренно работает в памяти.

Один конкретный путь — хост Linux с установленными Neo CLI, Nix и Git для аккаунта, запускающего приложение. Поместите туда проверенную версию **своего приложения**, сохраните фиксацию фреймворка и lock-файлы и собирайте на этом хосте или совместимом хосте сборки. Перед проверками в изолированной staging-базе данных передайте staging-значения окружения `DB_*` из раздела [хранение](/ru/operate/persistence/):

```sh
neo --ci build
neo --ci test
```

Команда тестирования создаёт настоящее состояние приложения и запускает собственный сервер. Не выполняйте её против production-базы и пока другой процесс занимает порт 8080. Настраивайте production-базу только после успешных staging-проверок.

Из каталога приложения эта команда запускает сервер без интерактивного вывода:

```sh
neo --ci run
```

Для небольшого размещения на хосте настройте менеджер процессов этой командой запуска и каталогом проекта как рабочим каталогом. Ниже приведён **шаблон юнита systemd** для приложения, установленного в `/opt/mug-shop`. Замените путь к Neo результатом `command -v neo` для сервисного аккаунта и убедитесь, что его `PATH` содержит исполняемые файлы Nix и Git этого аккаунта:

```ini
[Unit]
Description=Mug shop application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=mug-shop
WorkingDirectory=/opt/mug-shop
EnvironmentFile=/etc/mug-shop.env
Environment=PATH=/home/mug-shop/.nix-profile/bin:/nix/var/nix/profiles/default/bin:/usr/local/bin:/usr/bin:/bin
ExecStart=/usr/local/bin/neo --ci run
Restart=on-failure
RestartSec=5
KillMode=control-group

[Install]
WantedBy=multi-user.target
```

Аккаунту нужен доступ к проекту и сгенерированным каталогам сборки. Создайте `/etc/mug-shop.env` через защищённый механизм конфигурации хоста, используя поля ниже. Сохраните адаптированный юнит как `/etc/systemd/system/mug-shop.service`, затем воспользуйтесь административным аккаунтом хоста:

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now mug-shop
sudo journalctl -u mug-shop -f
```

Этот путь запуска по-прежнему выполняет согласование и сборку через CLI при перезапуске; ему нужна цепочка инструментов и может понадобиться сеть. Это не заранее собранный минимальный образ среды выполнения. Зафиксируйте версию и зависимости, соберите до допуска трафика и протестируйте остановку/перезапуск. Более специализированная упаковка — выбор развёртывания; CLI не создаёт готовый контейнер приложения или облачную среду.

## Предоставьте ресурсы среды выполнения

До запуска версии установите:

- Поля `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_POOL_SIZE`, `DB_SSL_MODE` и `DB_SSL_ROOT_CERT`, подключённые в разделе [хранение](/ru/operate/persistence/), а также доступную базу данных.
- Том для долговременных загрузок, если используется локальное хранилище байтов.
- Учётные данные провайдеров и конфигурацию аутентификации через механизм секретов развёртывания.
- Фактический HTTP-порт, переданный транспорту.
- Идентификатор версии, записанный системой выпусков рядом с журналами и результатами smoke-тестов.

Проверяйте не только объявление конфигурации, но и проводку. Объявленное поле порта не влияет на приложение, если оно не использовано для настройки сервера.

## Разделяйте запуск, живость и готовность

При стандартной проводке приложения и веба:

| Запрос | Значение | Типичный ответ |
| --- | --- | --- |
| `GET /health` | HTTP-процесс отвечает | `200` |
| `GET /ready` | Зарегистрированные проекции запросов догнали историю | `200` при готовности, `503` во время восстановления или после ошибки |

Состояние не доказывает работоспособность платёжного провайдера. Готовность не сертифицирует каждый бизнес-процесс. Пользовательская проводка может изменить или исключить эти маршруты; проверяйте настоящую версию.

Для Kubernetes это **иллюстративный фрагмент проверок**, а не полный манифест развёртывания:

```yaml
startupProbe:
  httpGet:
    path: /health
    port: 8080
  periodSeconds: 5
  failureThreshold: 12
  timeoutSeconds: 2
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
  timeoutSeconds: 2
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 5
  failureThreshold: 3
  timeoutSeconds: 2
```

Примерный бюджет запуска — `5 × 12 = 60` секунд. Рассчитайте его на ограниченную инициализацию процесса и базы данных. Воспроизведение исторических запросов запускается после регистрации живой подписки и не должно задерживать привязку HTTP; готовность остаётся `503`, пока не завершатся воспроизведение и обработка перекрывающихся живых событий. Проверка запуска не даёт политике живости в штатном режиме неоднократно убивать инициализацию.

## Осознанно допускайте трафик

1. Запустите версию, не направляя на неё пользовательский трафик.
2. Наблюдайте `/health`, затем ждите, пока `/ready` вернёт `200`.
3. Запустите характерные smoke-тесты против **идентичности новой версии**.
4. Допустите трафик и наблюдайте за ошибками, задержками и бизнес-результатами.

Общий входной слой всё ещё может обращаться к старой версии. Одного его успешного ответа недостаточно, чтобы доказать работоспособность новой версии.

Для `mug-shop` создайте корзину, добавьте допустимое количество, изучите результаты запросов Cart и Stock, затем убедитесь, что ноль отклоняется. Используйте формы запросов из раздела [HTTP и фронтенд](/ru/build/http-and-frontend/) для новой версии. Проверяйте внешний результат, только если реализовали такую интеграцию, используя контролируемую среду провайдера. Встроенные проверки устанавливают более узкие факты. Это руководство не предоставляет и не сертифицирует сквозное облачное, платёжное или AI-развёртывание.

Для локального экземпляра на порту 8080:

```sh
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/ready
```

## Учитывайте текущие эксплуатационные ограничения

Клиенты Postgres используют ограниченные пулы. Соединения слушателя для `LISTEN/NOTIFY` требуют прямого соединения с сохранением сессии; не направляйте их через PgBouncer в режиме транзакций. Поддержка разделённых пуловой/прямой конечных точек и Neon scale-to-zero отслеживается в [issue #857](https://github.com/neohaskell/NeoHaskell/issues/857).

Отмена SIGTERM и сброс контрольных точек при активной перестройке по-прежнему отслеживаются в [issue #662](https://github.com/neohaskell/NeoHaskell/issues/662). Не увеличивайте бесконечно время ожидания завершения в надежде дождаться воспроизведения. Репетируйте прерывание и перезапуск в staging и используйте контракт готовности для управления трафиком.

Далее изучите, [что наблюдать](/ru/operate/observability/), и отрепетируйте [восстановление](/ru/operate/recovery/).
