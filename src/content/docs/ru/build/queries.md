Экрану или отчёту нужна информация, сформированная вокруг вопроса читателя. Если показать всю внутреннюю историю приложения, ответить на этот вопрос станет сложнее. Запрос готовит полезное представление — например, ожидающую проверки работу или ход запроса.

Модели чтения NeoHaskell отделяют показ информации от решения о том, разрешено ли изменение. Это даёт свободу формировать представление, но имеет последствие: недавно принятое изменение может появиться в нём с небольшой задержкой.

Эта страница продолжает [добавления в Cart](/ru/build/commands-and-events/). На той странице сущность Cart была изменена так, чтобы содержать `items`; запрос ниже читает это состояние. Пройдите [первый рабочий срез](/ru/build/first-cart/) и страницу о добавлениях в одном проекте `mug-shop`. Если вы пришли сюда напрямую, сначала используйте их полные контрольные точки, затем создайте или замените `src/Shop/Cart/Queries/CartSummary.hs` полным файлом с этой страницы.

## Начните с вопроса на экране

Существующий `CartSummary` отвечает: «Что это за Cart, кто её владелец, сколько в ней позиций и пуста ли она?» Он не сообщает общее количество единиц или цены. До просьбы агенту добавить поле определите смысл каждого: сейчас `itemCount` означает количество позиций, поэтому одно добавление пяти кружек даёт счётчик один.

Бизнес-логика запроса находится в `src/Shop/Cart/Queries/CartSummary.hs`. Из корня проекта `mug-shop` после просмотра сфокусированной проекции замените этот файл:

```haskell
instance QueryOf CartEntity CartSummary where
  queryId cart = cart.cartId
  combine cart _previous = do
    let count = cart.items |> Array.length
    Update CartSummary
      { cartSummaryId = cart.cartId
      , ownerId = cart.ownerId
      , itemCount = count
      , isEmpty = count == 0
      }
```

`queryId` определяет, какой строке представления соответствует эта сущность. `combine` получает текущее состояние сущности и существующее представление, если оно есть. Здесь текущее состояние содержит всё необходимое, поэтому старое представление не используется и заменяется через `Update`.

Другие результаты — `Delete`, удаляющий строку представления, и `NoOp`, оставляющий её без изменений. В один запрос могут вносить вклад несколько типов сущностей. Начните с одного, пока экран не даст причины для объединённого представления.

## Выведите и зарегистрируйте представление

Для этого запроса файл определяет запись данных, `canAccess` и `canView`, а затем вызывает канонический помощник:

```haskell
deriveQuery ''CartSummary [''CartEntity]
```

Поместите соответствующий бизнес-экземпляр `QueryOf` **после** этого маркера: он зависит от экземпляра `Query`, который маркер генерирует. Маркер приходит из ориентированного на фреймворк импорта `Core` и создаёт стандартную поддержку запросов. Полный файл ниже сохраняет необходимые импорты и порядок объявлений.

Регистрация приложения уже присутствует в `src/App.hs` после первого среза. Если в существующем приложении есть сервис Cart, но нет регистрации запроса, добавьте эту строку рядом с регистрацией сервиса:

```haskell
  |> Application.withQuery @CartSummary
```

Внутреннее имя маркера — `CartSummary`; URL HTTP — `/queries/cart-summary`. Учебный запрос намеренно разрешает публичный доступ. Прежде чем открывать частные данные приложения, определите и протестируйте [политики управления доступом](/ru/build/access-control/).

## Полный текущий файл запроса

При необходимости создайте каталог `src/Shop/Cart/Queries`, затем замените `src/Shop/Cart/Queries/CartSummary.hs` этим собранным файлом из корня проекта:

<!-- complete-file -->
```haskell title="src/Shop/Cart/Queries/CartSummary.hs"
module Shop.Cart.Queries.CartSummary (CartSummary (..), canAccess, canView) where

import Array qualified
import Core
import Service.AccessControl (AccessError, UserClaims)
import Service.AccessControl qualified as AccessControl
import Shop.Cart.Core (CartEntity (..))

data CartSummary = CartSummary
  { cartSummaryId :: Uuid
  , ownerId :: Text
  , itemCount :: Int
  , isEmpty :: Bool
  }

canAccess :: Maybe UserClaims -> Maybe AccessError
canAccess = AccessControl.publicAccess

canView :: Maybe UserClaims -> CartSummary -> Maybe AccessError
canView = AccessControl.publicView

deriveQuery ''CartSummary [''CartEntity]

instance QueryOf CartEntity CartSummary where
  queryId cart = cart.cartId
  combine cart _previous = do
    let count = cart.items |> Array.length
    Update CartSummary
      { cartSummaryId = cart.cartId
      , ownerId = cart.ownerId
      , itemCount = count
      , isEmpty = count == 0
      }
```

`Array qualified` — настоящий импорт, используемый проекцией; сохраняйте его при сборке файла. `canAccess` и `canView` — явные функции политики приложения. Здесь они открыты, чтобы упражнение могло исследовать Cart без аутентификации; это удобство не является рекомендацией для частных данных.

## Найдите свою Cart

Запустите приложение из корня проекта `mug-shop`:

```sh
neo build
neo run
```

Создайте Cart, добавьте позицию, как описано в разделе [добавления в Cart](/ru/build/commands-and-events/), и замените `YOUR-CART-UUID` идентификатором, возвращённым при создании:

```sh
curl --get http://localhost:8080/queries/cart-summary \
  --data-urlencode 'q=.cartSummaryId == "YOUR-CART-UUID"' \
  --data-urlencode 'limit=10' \
  --data-urlencode 'offset=0'
```

Ожидайте объект страницы. Его массив `items` содержит подходящий итог после того, как проекция догонит историю. `total` отражает доступное количество отфильтрованных результатов; `hasMore` сообщает, остались ли ещё подходящие результаты; `effectiveLimit` показывает применённое ограничение страницы.

По умолчанию размер страницы равен 100, смещение — нулю, а абсолютный максимум — 1000. Запрос может задать меньший предел, определив `maxResults :: Int` до своего маркера. Клиентам следует использовать возвращённый `effectiveLimit` при переходе между страницами.

Текущий NeoQL поддерживает доступ к полям и сравнение на равенство со строковыми или числовыми литералами. Это не универсальный язык SQL: не придумывайте соединения, сортировку, составные условия или сравнение с логическими литералами. Неверный синтаксис даёт ошибку разбора; выражения ограничены 500 символами.

## Не вводите в заблуждение экраном загрузки

После принятой команды показывайте понятное состояние ожидания, пока представление догоняет историю. Читайте снова с ограниченным числом повторных попыток и полезным состоянием ошибки. Пустой первый ответ не доказывает, что команда завершилась неудачей. Повторная отправка добавления только потому, что итог ещё не появился, может добавить товар дважды.

## Упражнение: значок Cart

Интерфейс говорит «5 товаров», но покупатель сделал одно добавление пяти кружек. Должен ли значок показывать один или пять? Сформулируйте смысл, затем попросите агента определить, что нужно изменить.

<details>
<summary>Подсказка для рассуждения и проверки</summary>

Существующий итог сообщает об одной позиции. Если значок означает единицы, спроектируйте итог количества, а не переименовывайте `itemCount`. Проверьте одно добавление пяти кружек, два добавления одного товара, пустую Cart и отклонённое добавление. Также запросите неизвестный ID Cart: фильтр должен вернуть ноль подходящих строк, а не Cart другого покупателя. Тесты должны ждать ограниченного обновления проекции, а не предполагать мгновенную видимость.

</details>
