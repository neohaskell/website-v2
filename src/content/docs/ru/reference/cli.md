Neo CLI помогает создавать, собирать, тестировать и исследовать проект NeoHaskell. Используйте команду, соответствующую ближайшей цели; визуальная IDE предлагает другой способ понять тот же проект.

Запускайте команды проекта из каталога, содержащего `neo.json`. Используйте `neo --help` или `--help` конкретной команды для встроенной справки установленного бинарного файла. Эта страница описывает Neo 0.10.0 — релиз, использованный в [настройке](/ru/getting-started/); более старый установленный релиз может отличаться.

## Общие флаги

| Флаг | Эффект |
| --- | --- |
| `-v`, `--verbose` | Включить отладочный вывод CLI |
| `--ci` | Отключить интерактивные подсказки, анимации и цвета |
| `--help` | Показать справку |
| `--version` | Показать версию |

`--ci` полезен в повторяемых скриптах. Он не превращает локальный тест в production-развёртывание.

## Создание, сборка, запуск и тестирование

Эта последовательность использует `mug-shop` — имя постоянного учебного проекта. Подставьте имя своего проекта; команды работают так же.

```sh
neo --ci new mug-shop
cd mug-shop
neo build
neo run
```

`neo run` продолжает обслуживать запросы, пока вы не остановите его через Ctrl-C. Остановите его до запуска тестов, потому что `neo test` запускает собственный процесс приложения:

```sh
neo test
```

| Команда | Параметры | Поведение |
| --- | --- | --- |
| `neo new [project_name]` | `--library` | Создать каркас из встроенного стартового проекта; в режиме CI имя обязательно. Для библиотеки не создаются запускающий файл и секция исполняемого файла. |
| `neo build` | `--watch`, `--skip-lock-check` | Согласовать конфигурацию и собрать проект; watch использует обратную связь GHCi; skip только обходит проверку блокировок сборки. |
| `neo run` | `--watch` | Согласовать, собрать и запустить; watch пересобирает и перезапускает при изменениях. |
| `neo test` | `--watch` | Запустить модульные тесты проекта, затем найденные HTTP-тесты Hurl. |

Build, run и test заново создают управляемые файлы сборки из `neo.json` и находят модули под `src/` и `tests/`. Модули `Shop.Cart` и `Shop.Stock` остаются в приложении; CLI включает их в сборку.

Если существуют тесты Hurl, команда тестирования запускает приложение и ждёт HTTP-ответа на `127.0.0.1:8080`. Это ожидание принимает любой HTTP-ответ и не ждёт контракт готовности `/ready` для проекций. Оставляйте тестовый порт проекта свободным и добавляйте в сценарии проверки готовности, если они зависят от перестроенных запросов. Пользовательский порт приложения требует внимания и к целям тестов, и к текущей фиксированной проверке запуска.

## Управляйте зависимостями проекта

`neo.json` — источник решений о зависимостях проекта. Сохраняйте существующие поля `name`, `version` и `neo-version`, а объект `dependencies` изменяйте, когда приложению нужен дополнительный пакет. `neo-version` выбирает ревизию фреймворка и отличается от установленной версии CLI, которую показывает `neo --version`.

Следующая таблица показывает поддерживаемый синтаксис. Имена пакетов и репозитории — примеры формы объявления, а не зависимости, необходимые уроку корзины.

| Запись зависимости | Значение |
| --- | --- |
| `"package-name": "^1.2.3"` | Разрешить пакет из реестра NeoPackages с версией, соответствующей диапазону |
| `"hackage:package-name": "^1.2.3"` | Явно разрешить пакет из Hackage |
| `"package-name": "github:owner/repository#revision"` | Использовать указанный источник GitHub и ревизию |
| `"package-name": "git:https://host/repository.git#revision"` | Использовать другой источник Git |
| `"package-name": "file:../package-directory"` | Использовать локальный пакет, который вы поддерживаете рядом с приложением |

Диапазоны версий используют формы вроде `^1.2.3`, `~1.2.3` и `>=1.2.3 <2.0.0`. Простое имя пакета направляется в реестр NeoPackages и не переключается молча на Hackage. Источники Git без ревизии по умолчанию используют `main`, поэтому при важной воспроизводимости называйте проверенную ревизию.

После изменения `neo.json` запустите из `mug-shop`:

```sh
neo build
neo test
```

Проверьте сгенерированные изменения и зафиксируйте выбор зависимости вместе с использующими её кодом приложения и тестами. Не поддерживайте отдельные изменения в заново созданных файлах `.cabal`, `cabal.project` или `flake.nix`. В описанной здесь версии нет команды `neo add`.

## Исследуйте приложение

Запустите IDE из каталога проекта:

```sh
neo ide
```

Для другого порта IDE используйте `neo ide --port 2324`. Оставьте этот процесс работающим и исследуйте тот же проект из второго терминала:

```sh
neo inspect
neo inspect commands
neo inspect wiring
```

`neo ide` по умолчанию использует `127.0.0.1:2323`. `--host` принимает буквальный IP-адрес, а не имя хоста. Например, `--host 0.0.0.0` открывает IDE на других интерфейсах IPv4; выбирайте это намеренно. Остановите сервер через Ctrl-C.

`neo inspect` печатает JSON. Его представления: `domains`, `commands`, `events`, `queries`, `integrations` и `wiring`. Без представления он печатает весь исследованный проект.

`neo inspect sync` — **мутация**: он обновляет `event-model.json` по исходному коду. Изменения существующих полей могут сохранять раскладку; новые узлы запускают работу по раскладке. Используйте его, когда намерены обновить модель, а не для отчёта только на чтение.

О том, как читать эту модель, см. [путь визуальной IDE](/ru/getting-started/visual-ide/).

## Проверьте сохранённую модель

```sh
neo validate
neo validate ./event-model.json --json
```

Проверка выполняется только на чтение. Необязательный путь по умолчанию — `event-model.json` в текущем каталоге. Проверяются целостность схемы и ссылок, но не корректность бизнес-правил.

| Код выхода | Значение |
| --- | --- |
| `0` | Корректная модель |
| `1` | Ошибка ввода-вывода или инструмента |
| `2` | Модель не прошла проверку |
| `3` | Некорректный JSON |
| `4` | Файл отсутствует |

`--json` выдаёт структурированный результат проверки без префиксов человеческого журнала; коды выхода сохраняют тот же смысл.

## Защитите файлы предметной области

```sh
neo lock --all
neo lock Cart
neo lock install
neo lock check
```

`neo lock [search]` использует нечёткий поиск файлов предметной области. `--all` или отсутствие поиска выбирает все найденные файлы предметной области. Манифест находится в `.locked-files`. `install` записывает Git pre-commit hook, перезаписывая существующий hook по этому пути; `check` обнаруживает изменённые заблокированные файлы, включая изменения рабочего дерева. Историческая проблема совместимости, стоящая за этой возможностью, описана в разделе [развитие](/ru/operate/evolution/).

Блокировка добавляет выбранные пути и `.locked-files` в staging и создаёт коммит Git. Сначала проверьте `git status`: постороннее уже подготовленное содержимое может попасть в этот коммит. Сохраните существующий pre-commit hook до установки hook блокировки.

## Установите отдельные навыки агента

```sh
neo skills setup --tool codex --dry-run
neo skills setup --tool codex
```

Эта команда получает общую библиотеку навыков и устанавливает её для выбранных инструментов. Документация для людей остаётся отдельной от этих инструкций.

Параметры настройки: повторяемый `--tool` (`claude`, `codex`, `kiro`, `cursor`), `--all-tools`, повторяемый `--skill`, `--force`, `--dry-run`, `--refresh` и `--no-primer`. `--dry-run` печатает план без установки в проект, но получение библиотеки может заполнить локальный кэш; `--force` разрешает перезаписывать назначения; `--refresh` повторно клонирует библиотеку; `--no-primer` исключает постоянно включённый primer и его подключение к файлу инструкций. Запуск `neo skills` без подкоманды выполняет настройку.

Источник истины — [определение CLI](https://github.com/neohaskell/NeoHaskell/blob/main/neo/src/cli.rs). При ошибке используйте [устранение неполадок](/ru/reference/troubleshooting/).
