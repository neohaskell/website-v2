Когда приложению нужен внешний API или локальный инструмент, который NeoHaskell не оборачивает, такую работу можно упаковать в повторно используемую интеграцию. Вызывающие описывают запрос в небольшой записи; детали протокола, учётные данные и разбор ответа остаются в одной реализации.

Это более глубокая ветка пути. Вы берёте на себя ответственность за сетевое поведение или работу подпроцесса, а также за правила приложения. Если провайдер уже подходит под этот случай, начните с [общего HTTP](/ru/connect/http-and-payments/).

## Дайте адаптеру место в mug-shop

Продолжайте работать из проекта `mug-shop`. Начните с модуля вроде `src/Shop/Integrations/Parcel.hs`; разделите его на модули запроса, ответа и внутренней реализации, когда этим ответственностям понадобятся отдельные места. Импорты получившихся модулей должны оставаться `Shop.Integrations.Parcel` и его дочерними модулями. Храните зависимости, специфичные для провайдера, в `neo.json` проекта, следуя [настройке интеграций](/ru/connect/#prepare-your-project).

Полезная структура разделяет:

- фасадный модуль для API, который импортируют вызывающие;
- тип запроса со входными данными, конфигурацией и обратными вызовами результата;
- тип ответа с полезным результатом провайдера;
- внутренний модуль, реализующий или составляющий выполнение.

Для воображаемого провайдера этикеток посылок запрос приложения может содержать ссылку на отправление и сведения о посылке. Это пример дизайна, а не предоставленный API доставки. Решите, какой конкретный статус провайдера устанавливает создание этикетки и что делать при потере ответа.

Оба обратных вызова должны возвращать один тип команды, объявленный с `InternalTransport`. Пусть вызывающий сам захватывает идентификатор собственного рабочего процесса в этих обратных вызовах. Не связывайте повторно используемую интеграцию с конкретной сущностью приложения.

## Поймите контракт выполнения

`Integration.ToAction` превращает запрос в `Action`. Его основной метод:

```haskell
class ToAction config where
  toAction :: config -> Action
```

Действие получает `ActionContext` и возвращает `Task IntegrationError (Maybe CommandPayload)`. Успешная работа может использовать `Integration.emitCommand`; работа без последующей команды — `Integration.noCommand`.

Вы уже использовали `Integration.Command.Emit` в разделе [координация Cart и Stock](/ru/connect/workflows/). Он не выполняет внешнюю операцию, а выдаёт настроенную команду. Адаптер посылок добавляет работу с протоколом до выбора команды результата.

Для HTTP-провайдеров составляйте запрос через `Integration.Http.Request`, а не дублируйте механику. Конкретный пример `toHttpRequest` OpenRouter создаёт конечную точку, тело, заголовки, аутентификацию, обратные вызовы и тайм-аут, а затем передаёт выполнение дальше. Сохраняйте [текущее поведение повторов](/ru/connect/http-and-payments/#understand-the-current-retry-boundary) в тестах совместимости провайдера.

## Выбирайте ошибки, помогающие восстановлению

Словарь ошибок среды выполнения включает `NetworkError`, `AuthenticationError`, `ValidationError`, `RateLimited`, `PermanentFailure` и `UnexpectedError`.

Решите, какие ошибки превращаются в команду результата, а какие останавливают подготовку до запуска запроса. Объясните эту границу в документации интеграции. Вызывающему, ожидающему обратный вызов, нужен эксплуатационный способ обнаружить ошибки, обходящие этот обратный вызов.

Не возвращайте произвольные тела провайдера как строки ошибок. Они могут содержать данные покупателей или учётные данные. Сохраняйте безопасное объяснение и идентификатор корреляции, если провайдер его поддерживает.

## Отделяйте долгоживущие ресурсы от надёжного состояния

Если интеграции нужен дорогой ресурс для одной сущности, `Integration.Lifecycle.OutboundConfig state` предлагает:

```haskell
initialize :: StreamId -> Task Text state
processEvent :: state -> Event Json.Value -> Task Text (Array Integration.CommandPayload)
cleanup :: state -> Task Text Unit
```

Это **сигнатуры полей**, взятые из типа жизненного цикла. Рабочие инициализируют ресурсы, обрабатывают события и очищают ресурсы при остановке или удалении. Более позднее событие может создать нового рабочего, поэтому это состояние не является долговременной историей рабочего процесса.

Рабочий может хранить `ConcurrentVar`, дескриптор соединения или другой временный ресурс. Его значения могут сбрасываться при пересоздании рабочего. Незавершённую работу нужно хранить в долговременном состоянии приложения, а не только в этой переменной. В `mug-shop` таким состоянием является, например, «покупка этикетки всё ещё ожидается».

После реализации `shipmentLifecycle` сделайте его и `CartEntity` доступными в `src/App.hs`. Этот **фрагмент регистрации** связывает его с событиями Cart:

```haskell
    |> Application.withOutboundLifecycle @() @CartEntity (\_ -> shipmentLifecycle)
```

`shipmentLifecycle` должен быть вашим значением `OutboundConfig state` со всеми тремя функциями выше; готовой реализации посылок здесь нет. Используйте этот уровень только когда жизненный цикл ресурса полезен. Большинство запросов провайдера могут оставаться без состояния.

## Принимайте внешнюю работу

`Integration.inbound` оборачивает `InboundConfig`, чья функция `run` получает обратный вызов выдачи. Рабочий переводит входную информацию в команды. При запуске приложения запускаются зарегистрированные входящие рабочие.

Интеграции вебхуков по-прежнему нужны настоящий слушатель, аутентификация или проверка подписи провайдера, ограничения входных данных и стратегия подтверждения. Абстракция не является автоматически сгенерированным сервером вебхуков. Аналогично, потребителю очереди нужна осознанная политика подтверждения, повторной доставки и долговременного прогресса.

## Докажите адаптер до выпуска

Используйте `Integration.getActions`, чтобы исследовать действия, выбранные обработчиком, и `Integration.runAction` с контролируемым `ActionContext`, чтобы проверить выполнение. Особенно полезны чистые функции построения запросов: они позволяют тестировать отображение протокола без отправки трафика.

Поместите тесты адаптера рядом с остальными тестами в каталоге `tests/`. После добавления модуля запустите `neo build`, затем `neo test` для отображения запросов и случаев ошибок. Проверьте корректный ввод, отказ провайдера, искажённые успешные данные, отсутствующие учётные данные, тайм-аут, повторный вызов и потерянный ответ после успеха на стороне провайдера. Подсчитайте запросы через контролируемый сервер. Наконец, запустите `neo run` с учётными данными песочницы и проверьте контракт провайдера через команды приложения и запрос результата.

**Упражнение:** упакуйте для учебного проекта поиск статуса отправления через контролируемого тестового провайдера. Попросите другого читателя настроить его, используя только публичный API запроса. Если для обычных параметров ему приходится понимать внутренний разбор HTTP, пересмотрите API и документацию вместе.

Вернитесь к [эксплуатации приложения](/ru/operate/deployment/) за сведениями о зависимостях среды выполнения, конфигурации и планировании восстановления.
