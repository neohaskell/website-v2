Человек хочет, чтобы приложение использовало аккаунт, которым он владеет в другом месте: например, календарь, сервис документов или бухгалтерский инструмент. Он должен иметь возможность разрешить такое подключение, не передавая приложению пароль провайдера. OAuth2 предоставляет поток согласия и учётные данные для последующего доступа.

Это отличается от входа в приложение. JWT-аутентификация определяет его пользователя; OAuth2-токены провайдера разрешают доступ к внешнему аккаунту. Для учебного проекта можно рассмотреть подключение тестового бухгалтерского аккаунта. Согласие — лишь часть возможности; создание счета или экспорт заказа потребуют отдельного адаптера.

Начните с [управления доступом приложения](/ru/build/access-control/) и [результатов интеграций](/ru/connect/). Выберите минимальный набор разрешений провайдера, необходимый настоящей возможности.

## Дайте подключению место в mug-shop

Продолжайте в проекте, созданном командой `neo new`. Поместите конфигурацию провайдера и помощники кодирования обратного вызова в `src/Shop/Integrations/Accounts.hs`, а подключение выполните из `src/App.hs`. Модули OAuth2 и хранилища секретов идут из основного пакета; чтобы смонтировать маршруты согласия, пакет интеграций провайдера не нужен.

Сначала добавьте в зарегистрированный приложением сервис команды `InternalTransport` для результатов подключения, ошибки и отключения. Запрос должен показывать состояние подключения, не раскрывая токены. Это новые возможности подключения аккаунта; Cart и Stock остаются начальными срезами приложения.

## Установите совместимость провайдера

Основной пакет предоставляет настраиваемый поток кода авторизации с PKCE, но не заготовку для бухгалтерского провайдера. `Provider` содержит `name`, `authorizeEndpoint` и `tokenEndpoint`. Подтвердите, что выбранный провайдер поддерживает фактический формат обмена клиента: параметры формы включают `client_id`, `client_secret` и проверяющий код PKCE. Специфичные провайдеру области, дополнительные параметры авторизации и операции API требуют собственной проверки совместимости.

При запуске проверяются HTTPS конечных точек и ограничения сетевых адресов, а одинаковые имена отклоняются. Постройте URI обратного вызова через `OAuth2.mkRedirectUri`, обработайте его `Result` и зарегистрируйте этот же URI у провайдера. HTTPS обязателен, кроме поддерживаемых адресов localhost для разработки.

## Подключите аккаунт

Это **частичный конструктор приложения**. Окружающее приложение уже должно зарегистрировать транспорт и сервисы. `identityServerUrl`, `accountProviderConfig` и `existingSecretStore` — значения, которые предоставляете вы:

```haskell
    |> Application.withAuth @() (\_ -> identityServerUrl)
    |> Application.withSecretStore @() (\_ -> existingSecretStore)
    |> Application.withOAuth2StateKey "SHOP_OAUTH_STATE_KEY"
    |> Application.withOAuth2Provider @() (\_ -> accountProviderConfig)
```

Настройка ключа состояния называет переменную окружения, содержащую секрет длиной не менее 32 байт. Установите её до запуска. `withOAuth2StateKey` должен идти до регистрации провайдера. Для значений, зависящих от конфигурации, замените фабрики `@()` функциями от типа конфигурации, зарегистрированного через `Application.withConfig`.

И `withSecretStore`, и `withOAuth2Provider` принимают **функции-фабрики**, а не запись хранилища или провайдера напрямую. Хранилище, требующее работы при запуске, нужно создать в дизайне запуска до возврата его дескриптора из фабрики; этот API не принимает `Task` как результат фабрики.

Конфигурация провайдера содержит этот **фрагмент создания записи**:

```haskell
OAuth2ProviderConfig
  { provider = selectedProvider
  , clientId = registeredClientId
  , clientSecret = registeredClientSecret
  , redirectUri = validatedCallbackUri
  , scopes = requestedScopes
  , onSuccess = encodeConnected
  , onFailure = encodeConnectionFailure
  , onDisconnect = encodeDisconnected
  , successRedirectUrl = connectedPage
  , failureRedirectUrl = failedPage
  }
```

`OAuth2ProviderConfig` определён в `Auth.OAuth2.Provider`. Для ID клиентов, секретов, URI обратного вызова и областей используются типы из `Auth.OAuth2.Types`; применяйте его умные конструкторы для секретов и проверенных URI перенаправления. Храните учётные данные в [секретной конфигурации](/ru/build/configuration/).

## Проследите три маршрута

| Предполагаемый запрос | Что происходит |
| --- | --- |
| `GET /connect/{provider}` | Аутентифицирует пользователя и перенаправляет к согласию провайдера |
| `GET /callback/{provider}?code=…&state=…` | Проверяет подписанное состояние, использует сохранённую транзакцию и обменивает код |
| `POST /disconnect/{provider}` | Аутентифицирует пользователя и пытается удалить локальный токен |

Маршрут подключения принимает заголовок bearer и резервный токен в запросе для перенаправлений браузера. По возможности предпочитайте заголовок; не допускайте попадания URL с токеном в журналы приложения или прокси. Обратный вызов использует подписанное состояние и сохранённую транзакцию, а не требует JWT из перенаправления провайдера.

Состояние истекает через пять минут. Его транзакция хранит идентичность пользователя и проверяющий код PKCE на сервере и используется один раз. Поэтому после неудачного обмена нужно начать новое подключение, а не воспроизводить тот же обратный вызов.

## Превратите согласие в результат приложения

После успешного обмена токены сохраняются до того, как `onSuccess` получает ID аутентифицированного пользователя и `TokenKey`. Каждый обратный вызов возвращает текст JSON в формате `Integration.CommandPayload`; создайте его через `Integration.encodeCommand` вокруг зарегистрированной команды приложения.

`encodeConnected` обрабатывает `Text -> TokenKey -> Text`; `encodeConnectionFailure` — `Text -> OAuth2Error -> Text`; `encodeDisconnected` — `Text -> Text`. Получившиеся команды могут иметь разные типы, потому что граница обратного вызова кодируется текстом. Не помещайте необработанные токены в полезные нагрузки команд и события. Пусть команда подключения запишет связь приложения и подходящую ссылку, а запрос покажет результат.

Не считайте переход на URL успеха доказательством работоспособности подключённой возможности. Отдельно проверяйте диспетчеризацию команды обратного вызова и настоящую операцию API провайдера. Ошибки до обмена и перенаправления отказа от согласия без `code` не обязательно вызывают `onFailure`; текущий веб-обратный вызов ожидает и `code`, и `state`.

## Спланируйте срок жизни учётных данных

Хранилище секретов по умолчанию находится в памяти. До обещания, что подключения переживут перезапуск, реализуйте и предоставьте долговременное хранилище секретов. Текущее приложение также создаёт хранилище транзакций в памяти: перезапуск во время согласия теряет транзакцию, а нескольким экземплярам нужны осознанная маршрутизация обратных вызовов или другая интеграция хранилища транзакций.

`TokenRefresh.withValidToken` — явный помощник для авторов адаптеров. Он читает сохранённые токены, выполняет переданное действие и обновляет токен при ошибке, которую вызывающий определяет предикатом неавторизованного ответа. Он сохраняет обновлённые токены и один раз повторяет действие. Он не планирует обновление заранее по `expiresInSeconds`; блокировки обновления на ключ действуют только внутри процесса.

Отсутствующий токен, отсутствующий токен обновления или неудачное обновление требуют результата «подключиться снова». Отключение аккаунта сейчас пытается удалить локальные данные, но игнорирует ошибки удаления и не вызывает конечную точку отзыва провайдера. Проверьте удаление и реализуйте отзыв у провайдера там, где этого требует продукт; «отключено» не является свидетельством удалённого отзыва.

## Запустите подключение локально

После регистрации команд результатов и конфигурации аккаунта запустите `neo build` и `neo test` из `mug-shop`. Запустите `neo run` с учётными данными клиента разработки и ключом состояния, используя зарегистрированный у провайдера callback localhost. Пройдите согласие и изучите запрос подключения. Отдельно проверьте вызов API провайдера: попадание на страницу перенаправления не устанавливает доступ к API.

## Упражнение: согласие прервано

Попросите агента продемонстрировать подключение, изменённое или повторно использованное состояние, отказ в согласии, перезапуск во время согласия, ошибку обновления и отключение при неисправном хранилище секретов. Затем объясните, что видит человек, подключающий свой аккаунт, в каждом случае.

Сохраняйте контролируемые проверки маршрутов и обновления в наборе тестов проекта. Они не сертифицируют конкретного бухгалтерского провайдера. Проверку песочницы этого провайдера запишите отдельно, затем создайте настоящий [адаптер провайдера](/ru/connect/custom-integrations/).
