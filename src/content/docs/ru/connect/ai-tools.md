Модель может перевести запрос на обычном языке в структурированное предложение: добавить товар, запланировать задачу или обновить черновик. Приложение по-прежнему решает, какой объект можно менять, допустимы ли предложенные значения и должен ли человек подтвердить действие.

Интеграция агента NeoHaskell описывает инструменты через схемы команд и декодирует возвращённые аргументы в команду. Это придаёт передаче структуру. Но это не делает аргументы модели заслуживающими доверия и не выдаёт модели идентичность пользователя. Мы потренируемся на фразе «Я хочу две синие кружки» в примере интернет-магазина.

Предварительно изучите [запросы ИИ](/ru/connect/ai/), [команды](/ru/build/commands-and-events/) и [разрешения](/ru/build/access-control/).

## Расширьте тот же проект mug-shop

Завершите [настройку интеграций](/ru/connect/#prepare-your-project). Поместите помощник запроса модели в `src/Shop/Integrations/CartAssistant.hs`, а команду предложения определите в `src/Shop/Cart/Commands/`. Зарегистрируйте эту команду с `InternalTransport` в сервисе Cart до добавления обработчика в `src/App.hs`.

Команда — новое поведение приложения. Не открывайте существующую `AddItem` как инструмент модели, считая её проверку положительного количества политикой владения. Начните с предложения, которое покупатель может проверить до того, как отдельное авторизованное действие изменит корзину.

## Начните с команды предложения

Начните с команды, которая записывает предложение для проверки. В учебной корзине оставьте за её пределами оформление заказа, платежи и необратимые действия. Сервер должен сам связать доверенный контекст корзины и пользователя, а не принимать утверждения о владении, сгенерированные моделью.

`Agent.commandTool @YourCommand` получает сетевое имя из `NameOf`, описание из `Documented`, а JSON Schema — из `ToSchema`. Используйте маркер команды и установленные [соглашения команд](/ru/build/commands-and-events/); предоставьте экземпляры схемы и документации, которые требуются реальным путём вывода вашей команды.

Следующее — **частичное выражение запроса**, а не полная реализация команды:

```haskell
Agent.agent
  customerMessage
  [proposalTool]
  modelName
  recordProposalFailure
  |> Integration.outbound
```

`proposalTool` — это `CommandTool`, обычно привязанный один раз через `Agent.commandTool`. Тип `command` запроса должен поддерживать кодирование/декодирование JSON и имя команды. Его обратный вызов ошибки возвращает тот же тип, поэтому типу нужен осознанный способ представить и ошибку, и успешное предложение.

Текущий экземпляр выполнения находится в `Integration.Agent.Internal`. Хотя описание API не зависит от провайдера, эта реализация отправляет запросы через OpenRouter, используя `OPENROUTER_API_KEY`.

## Точно поймите, что выполняется

Текущая реализация:

1. Отклоняет пустой список инструментов через обратный вызов ошибки.
2. Отправляет запрос без потоковой передачи с обязательным выбором инструмента.
3. Читает первый вызов инструмента первого варианта ответа.
4. Проверяет, входит ли имя инструмента в разрешённый список.
5. Декодирует его аргументы как единственный тип `Request command`.
6. Передаёт эту команду диспетчеру приложения.

Она не запускает многошаговый цикл планирования и не выполняет каждый вызов инструмента из ответа.

**Несколько описаний инструментов не приводят автоматически к диспетчеризации разных типов команд Haskell.** Все формы возвращённых аргументов должны декодироваться в один целевой тип запроса. Для суммы или конверта нужна явная проверенная схема декодирования; начните с одной совместимой формы инструмента.

## Оставьте полномочия за приложением

Диспетчер интеграций использует доверенный системный контекст для выдаваемых команд. Это обходит внешний шлюз доступа и не является исходным контекстом аутентифицированного запроса пользователя. Бизнес-правила команды по-прежнему важны, но границу идентичности и полномочий нужно спроектировать явно.

Для помощника, действующего по запросам пользователя, безопасный первый дизайн — записать предложение, связанное с доверенной информацией запроса, показать его пользователю и потребовать обычную авторизованную команду подтверждения. Любой сгенерированный моделью ID сущности или признак разрешения считайте недоверенным вводом.

Список разрешённых имён инструментов не даёт принять неизвестное имя. Но он не доказывает, что аргументы разрешённого имени безопасны. Аналогично, системная подсказка — инструкция модели, а не механизм авторизации.

## Проверьте границу предложения

Запустите `neo build`, чтобы проверить новую команду предложения и типы запроса модели. Добавьте фиксированные ответы вызова инструмента в набор `tests/` и запустите `neo test`, особенно ответ, называющий другую корзину. С `neo run` и учётными данными разработки выполните один живой запрос и изучите предложение до подтверждения. Обычный итог корзины должен изменяться только через авторизованное последующее действие.

## Репетируйте непонимание

> **Джесс:** «Покупатель попросил две кружки. Почему в предложении упоминается другая корзина?»
>
> **Агент:** «Модель включила этот идентификатор корзины».
>
> **Джесс:** «Свяжи предложение с корзиной аутентифицированного запроса и отклоняй противоречащие идентификаторы. Покажи тест».

Проверьте пустой список инструментов, неизвестные имена, искажённые аргументы, отсутствие вызова инструмента, несколько возвращённых вызовов, неверные количества, идентификатор другого покупателя и безобидную на вид подсказку, которая просит модель игнорировать ограничения. Исследуйте отдельно предложение и окончательный подтверждённый результат.

**Упражнение:** решите, должно ли неоднозначное название товара создавать предложение или просить покупателя уточнить запрос. Запишите ожидаемый результат до обращения к модели. Правило принятия должно оставаться стабильным при смене моделей.

Если нужно другое поведение провайдера или более богатый цикл выполнения, продолжите с [пользовательскими интеграциями](/ru/connect/custom-integrations/).
