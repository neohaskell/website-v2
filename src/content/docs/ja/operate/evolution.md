要件が変わっても、既存データはその意味を保ちます。新しいコードは両方の現実を支えなければなりません。たとえば新しいレコードに任意のテキストを追加しても、以前のユーザーがそれを提供したことにはなりません。EC の練習用プロジェクトでは、新しく作る Cart に任意のメモを追加し、古い Cart にはその情報が明示的にない状態を保つことを試します。

イベントソーシングされたシステムは履歴を明示します。これは決定の説明に役立ちますが、同時に責任も生みます。将来のコードは、すでに受け入れた事実を理解し続けなければなりません。

## コードを書く前に変更を分類する

| 変更 | 主な問い |
| --- | --- |
| 将来の操作への新しいルール | 新しい決定を実行する前に、既存の状態を再構築できるか？ |
| 新しいイベント種別 | 遭遇する可能性のある履歴を、古い版と新しい版のアプリケーションが読めるか？ |
| 保存済みイベントの形の変更 | 過去の JSON をどうすればデコード可能で意味のある状態に保てるか？ |
| 新規または変更したクエリ | サポートするすべての履歴から正しく再構築できるか？ |
| 新しい外部ワークフロー | ロールアウトやリプレイで外部アクションが重複する可能性はあるか？ |

[イベントモデリング](/ja/start/event-modeling/)と[視覚的な IDE](/ja/getting-started/visual-ide/)を使って、影響を受ける利用者を特定します。1 つのイベントを変えると、コマンド、クエリ、インテグレーションに異なる形で影響することがあります。

## 過去のフィクスチャを保つ

変更を受け入れる前に、代表的な小さな履歴をテストに残します。変更前と変更後の振る舞いに加え、拒否された操作も含めます。EC の例では、古い Cart とメモ付きの新しい Cart を使います。新しいコードが次を満たすことを確認します。

- 古い保存イベントと新しい保存イベントをデコードできる。
- それぞれについて意図した状態を再構築できる。
- ビジネスが意図した場所にだけ新しいルールを適用する。
- リプレイ後に期待するクエリ結果を構築できる。
- 演習中に外部の効果を繰り返さない。

JSON 型のコンパイルが成功しても、過去の JSON が正常にデコードできる証明にはなりません。履歴のケースを `Shop.Cart` のテストの隣に置き、使い捨てデータベースに対して `mug-shop` から `neo test` を実行します。実行可能な証拠は[テスト](/ja/build/testing/)を参照してください。

## ドメインロックをリマインダーとして使う

生成されたプロジェクトのルートから、CLI で見つかったドメインファイルをロックできます。

```sh
neo lock --all
neo lock install
neo lock check
```

ロックする前に `git status` を調べ、無関係なステージ済み作業を片付けます。ロックは選択されたファイルと `.locked-files` をステージし、Git コミットを作成します。すでにステージされた内容が含まれることがあります。`neo lock install` は pre-commit フックのパスを書き込むため、既存のフックを意図的に残し統合します。

マニフェストは `.locked-files` です。インストールされた Git フックと `neo build` がロックされたパスの変更を確認します。`neo lock check` はステージ済み、未ステージ、未追跡の変更を含みます。ロックにより、影響の大きい編集を意図的に行いやすくなります。スキーマ互換性を確立したり、移行実装を提供したりはしません。

意図的なビルド時迂回のために `neo build --skip-lock-check` があります。根底にある過去の互換性の問いは別に扱います。チェックを迂回しても、その問いには答えられません。

## クエリの変更が自動移行されると思わない

Postgres のクエリストアとサブスクライバーは、ハッシュ・チェックポイント操作を公開します。存在するからといって、クエリ関数のすべての変更が自動的に検出・移行されるわけではありません。また、標準のアプリケーション起動でチェックポイント再開が有効になるわけでもありません。実際のアプリケーション配線を使った再構築を計画し、テストします。

保存されたクエリスキーマに互換性のない変更があるなら、移行を明示します。権威あるイベント履歴はそのまま保ち、リストアしたコピーで移行をリハーサルします。結果のデータに以前のリビジョンを実行できるかも含めます。データ変更後は「バイナリをロールバック」だけで十分とは限りません。

## 演習：Cart にメモを追加する

EC の練習用プロジェクトで、新しい Cart が任意のメモを得る方法と、古い Cart に何を表示するかをエージェントに提案させます。コードを受け入れる前に、古い履歴の振る舞いを自分で説明します。

<details>
<summary>役に立つ受け入れ境界</summary>

古い Cart は元の意味を保ち、メモがないことを明示するべきです。メモ付きの新しい Cart は、再起動とリプレイをまたいでメモを保つべきです。サイズまたは内容のポリシーに反するメモは、受け入れられた事実になる前に拒否するべきです。実装を確認する前に、この演習の正確なポリシーを選びます。

</details>
