ユーザーから、受け入れられた変更が見えないと報告されました。拒否されたリクエスト、遅れているビュー、間違ったアカウント、外部の失敗を区別する必要があります。「サーバーは起動している」は、その問いの一部分にしか答えません。EC の練習用プロジェクトなら、「商品を追加したのに、カートが変わらない」という報告かもしれません。

アプリケーションをレイヤーごとに観測します。プロセス、保存された事実、ビュー、外部の結果です。各アラートに、人が行動できる問いを与えます。

## 組み込みの 2 つのシグナルから始める

ポート 8080 のデフォルト Web 配線を使うアプリケーションでは、次を実行します。

```sh
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/ready
```

レディネス応答は集約された状態です。

```json
{"status":"ready"}
```

追いついている途中では、HTTP `503` と `{"status":"rebuilding"}` になります。失敗でも `503` を返し、`status` は `failed`、`reason` が設定されます。現在の HTTP 応答は、クエリごとの遅延値を表示するダッシュボードではありません。

健全なプロセスでもクエリを再構築していることがあります。レディなプロセスでも、外部プロバイダーの停止に遭遇することがあります。ビジネス操作は別に監視します。

## アプリケーションログを読む

`Log` モジュールは、`time`、`level`、`message` を持つ JSON レコードを標準出力へ書きます。利用できる場合は呼び出し元情報とフレームワークのスコープフィールドも含みます。ホスト側でレコードを収集し、保持し、検索可能にする必要があります。

ローカルで診断するには、次を実行します。

```sh
LOG_LEVEL=debug neo run
```

デフォルトレベルは `Info` です。実装は debug、info、warn、error、critical の綴りを、小文字、タイトルケース、大文字で認識します。環境を変更したら新しいプロセスが必要です。`neo --verbose` は CLI の詳細度を制御し、`LOG_LEVEL` はアプリケーションのロギングを制御します。

フレームワークログは、クエリのリプレイの進行と失敗を識別します。進捗メッセージには、メッセージ本文内に `events_replayed`、`lag_from_head`、`duration_seconds` が含まれます。これらが独立したメトリクスとして出力されるとは仮定しないでください。コールドスタートテストでは、進捗メッセージを検証し、イベントペイロードを漏らさずにクエリ識別子と位置が失敗ログにあることを確認します。

[ロギング実装を調べる](https://github.com/neohaskell/NeoHaskell/blob/main/core/core/Log.hs)と[コールドスタート検証](https://github.com/neohaskell/NeoHaskell/blob/main/testbed/scripts/cold-start-readiness.sh)を参照してください。

## 1 つの操作をシステムで追う

リビジョン、概算時刻、操作またはエンティティの安全な識別子を記録します。`mug-shop` のリクエストが返した Cart 識別子を保ちます。その後、次を尋ねます。

1. コマンドは成功したか、拒否を報告したか？
2. 永続化された履歴に期待する事実があるか？
3. 関係するクエリは追いついたか、読み手には見る権限があるか？
4. インテグレーションを期待していたなら、どんな結果を報告したか？
5. 結果は次のビジネス上の事実になったか、それとも後続作業が保留中か？

[IDE グラフ](/ja/getting-started/visual-ide/)で、担当するコマンド、イベント、クエリ、インテグレーションを見つけます。グラフはソース内の関係を説明しますが、実際のデータベース履歴を表示したり、本番監視の代わりになったりはしません。

安全な診断識別子を選びます。個人の住所、アクセストークン、アップロードされた書類、プロバイダーの完全な応答は、通常のログには入れません。型付き設定フィールドの秘匿は、後でログに出す任意のテキストを秘匿しません。
