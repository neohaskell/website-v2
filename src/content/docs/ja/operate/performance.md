小さなデータセットでは速く感じるアプリケーションでも、履歴と同時アクティビティが増えると振る舞いが変わることがあります。パフォーマンス作業は、どの体験を許容できる状態に保つ必要があるかを選ぶことから始まります。変更を送信すること、結果を読むこと、デプロイ後に再起動することのどれでしょうか。EC の練習用プロジェクトで忙しいセールを再現すると、調べる具体的な負荷になります。

NeoHaskell のアーキテクチャでは、これらの操作に異なる作業があります。プールサイズを変えたり並列化を追加したりする前に、別々に測定します。

## 観測可能な予算を選ぶ

目標と負荷を一緒に書きます。EC の例なら、「複数の顧客が最後のマグカップを予約している間、合意した時間内に在庫の可用性が表示される」はテストできます。「フレームワークが速い」はテストできません。

少なくとも次を測定します。

- 拒否を含むコマンド応答時間。
- 受け入れられたイベントが関係するクエリに反映されるまでの時間。
- `/health` までの起動時間と、`/ready` までの起動時間。
- 外部プロバイダーの所要時間と保留作業の経過時間。
- テスト中のデータベース接続数、リソース使用量、失敗率。

結果と一緒に、アプリケーションのリビジョン、データセットの大きさ、マシンの大きさ、負荷を残します。Cart だけの測定から、後で追加する決済インテグレーションのレイテンシーを予測することはできません。

## 1 つのエンティティの競合を理解する

同時に実行されるコマンドが、同じエンティティの変更を競合することがあります。EC の例では、2 人の顧客が同じ Stock エンティティから最後のマグカップを予約しようとするかもしれません。楽観的同時実行制御が競合する書き込みを検出し、コマンド実行器が状態を再取得して決定を再試行できます。

現在の実行器には最大 10 回の競合再試行があり、ジッター付き指数バックオフと上限付き遅延を使います。これは上限のある競合メカニズムであり、無制限の競合下ですべてのリクエストが成功する保証ではありません。ビジネス上の決定は決定的に保ち、再実行される可能性のある決定の中に外部効果を置かないでください。

1 つのエンティティに、関係のないアクティビティを不必要に含めていないか尋ねます。独立したアクティビティ（たとえば商品ごとの Stock）を分けると競合を減らせますが、分割できない 1 つのビジネス不変条件を分けると正しさが難しくなることがあります。実現しようとしているルールを保ちます。

## デプロイ全体でデータベース接続の予算を取る

Postgres のイベントストア、クエリストア、ファイル状態ストア、リスナーが接続需要に加わります。デフォルトのプールサイズは `PostgresEventStore` が 6、`PostgresQueryObjectStoreConfig` が 4 ですが、これは普遍的な容量の推奨値ではありません。

実際の配線が作るプール、その上限、リスナー接続、プロセス数を一覧にします。ロールアウト中に動く古いプロセスと新しいプロセス、運用と保守の余裕も含めます。ストリームごとの購読で、単純な固定プール合計を超える需要が加わることがあります。

プールを増やすと、ボトルネックが Postgres に移る可能性があります。変更の前後でキュー待ち、クエリ時間、失敗を測定します。

## 履歴が増えたときのリプレイをテストする

[永続化](/ja/operate/persistence/)で設定した使い捨ての Postgres データベースを使います。アプリケーションの HTTP ルートから代表的な Cart と受け入れられた追加を作り、期待する Cart と Stock の結果を記録し、アプリケーションを停止します。同じ `mug-shop` ディレクトリから、同じデータベースに対して再び起動します。

```sh
LOG_LEVEL=info neo --ci run
```

別のターミナルで、2 つのシグナルを別々に確認します。

```sh
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/ready
```

それぞれが成功する時刻を記録し、クエリ結果を期待値と比較します。既知の大きな履歴でも繰り返します。外部効果には制御した代替を使い、リプレイ実験で本物の通知を送ったりプロバイダーアクションを繰り返したりしないようにします。最初のインメモリストアでは、再起動をまたぐ履歴の復旧を測定できません。

再利用可能なリクエストシナリオを `tests/` に置き、正しさの確認には `neo test` を実行します。アプリケーションのリクエスト時間とレディネス時間を、CLI のコンパイル時間とは別に測定します。速くても間違った結果なら、テストは失敗です。
