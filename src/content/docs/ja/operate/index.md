アプリケーションは、再起動をまたいで受け入れた作業を保ち、リリース後も意図した振る舞いを提供するべきです。運用とは、その期待を繰り返し実行できる確認に変えることです。適切な確認は、予約、書類、注文、その他の作業を扱う目的によって変わります。

NeoHaskell はイベントストレージ、リードモデル、ヘルスエンドポイント、ロギング、テストを提供します。ホスティング環境を選び、データを保護し、許容できるサービスの状態を決めるのはあなたです。ビルドが成功したことから得られる自信と、リストアのリハーサルが成功したことから得られる自信は異なります。

## 5 つの約束を作る

イベントソーシングされたサービスでは、インフラを選ぶ前に次の約束から始め、アプリケーションに合わせます。

| 約束 | 必要な証拠 |
| --- | --- |
| 受け入れた変更が再起動後も残る | 永続的なイベントストアと再起動テスト |
| ユーザーが正確な情報を見る | レディネス確認と代表的なクエリ結果 |
| リリースが意図したリビジョンを提供する | ビルド識別情報と、そのリビジョンへのスモークテスト |
| 失敗を診断できる | 役に立つログ、識別子、復旧手順 |
| 変更が既存のビジネス履歴を保つ | 古いイベントのフィクスチャと互換性テスト |

`neo new` で作成した `mug-shop` プロジェクトで続けます。`src/Shop/Cart/` と `src/Shop/Stock/` のモジュールに、運用できる具体的な振る舞いがあります。同じ確認はほかのドメインにも適用できます。現時点では、インメモリイベントストアは再起動時に履歴を失います。次の章で意図的に変更します。

## 運用の道のりを追う

1. [再起動後に何を残すか選ぶ](/ja/operate/persistence/)。イベント、リードモデル、アップロードファイル、プロバイダー認証情報には異なるストレージ要件があります。
2. [リビジョンをデプロイする](/ja/operate/deployment/)。実行ファイルをビルドし、設定を提供し、準備ができたときだけトラフィックを受け入れます。
3. [実行中のアプリケーションを観測する](/ja/operate/observability/)。応答するプロセスと、完了したビジネス作業を区別します。
4. [復旧を練習する](/ja/operate/recovery/)。分離環境にリストアし、外部の効果を照合します。
5. [安全に進化させる](/ja/operate/evolution/)。要件が変わっても、過去のイベントの意味を保ちます。
6. 露出やトラフィックを増やす前に、[セキュリティ](/ja/operate/security/)と[パフォーマンス](/ja/operate/performance/)を確認します。

これらは、合格を判定するチェックリストではなく、つながったテーマです。単一ホストのパイロットと広く使われる公開サービスでは必要な可用性が異なります。どちらにも前提を正直に説明する必要があります。

## エージェントに結果を実演させる

EC の練習用プロジェクトでは、次のように依頼します。

> 「Cart と、受け入れた商品の数量がプロセスの再起動後も残ることを示してください。イベントがどこにあるかを特定し、再構築された Cart サマリーを見せ、拒否された数量がそれを変えていないことを実演してください。」

[視覚的な IDE](/ja/getting-started/visual-ide/)で、関係するエンティティと利用者を見つけます。この例では Cart とそのサマリーです。グラフはアプリケーションの説明を助け、デプロイログとテストは実行中のリビジョンが実際に行ったことを確立します。

自分のアプリケーションを運用・変更できるようになったら、NeoHaskell の改善への別の道として[貢献](/ja/operate/contributing/)へ進みます。
