データベースをリストアすると、アプリケーションの一部分が復旧します。外部システムには、リストアしたコピーにない作業がまだ記憶されている可能性があります。復旧では、完了した操作を繰り返さず、未完了の操作を静かに忘れずに、両方の履歴を扱う必要があります。EC の例では、顧客にもう一度請求せずに決済を照合することがこれに当たります。

イベント履歴は、アプリケーション状態の再構築に役立ちます。メタデータから失われた添付ファイルを再作成したり、それだけで外部決済を取り消したりはできません。復旧にはアプリケーションの周囲にあるリソースと組織も含まれます。

## まず何が失敗したかを特定する

| 観測 | データを変更する前に調べること |
| --- | --- |
| `/health` の応答がない | プロセスの起動、設定、データベース接続、ポートバインド |
| `/health` は動くが `/ready` が `503` のまま | クエリの再構築の進行または失敗 |
| レディ状態だが、1 つのビューが間違っている | プロジェクションロジック、保存イベント、認可、実行中のリビジョン |
| ファイルメタデータはあるが、ダウンロードに失敗する | Blob ボリュームとファイルのライフサイクル状態 |
| プロバイダーは成功したが、アプリケーションの結果が不明 | プロバイダーのトランザクション識別子とローカルの後続履歴 |

役に立つログと、失敗したリビジョンの識別情報を保ちます。無計画にデータベースをリセットすると、これらのケースを区別するために必要な証拠を壊す可能性があります。

## 分離環境へのリストアをリハーサルする

まず[永続化](/ja/operate/persistence/)を完了します。最初のインメモリストアには、リストアする保持履歴がありません。保持データを人が利用する前に、代表的な操作で練習します。

1. 既知の小さな履歴を作ります。受け入れられた変更、拒否された変更、対応している添付やインテグレーションの結果を含めます。`mug-shop` では Cart を作り、正の数量を追加し、数量 0 が拒否されることを確認します。
2. ホスティング環境のデータベースとファイルストレージの手順でバックアップを取得します。
3. 本番のアウトバウンド効果を無効にするか、制御したテストエンドポイントへ置き換えた分離環境へリストアします。
4. リストアしたアプリケーションプロジェクトから、分離ストレージの設定で `neo run` を実行し、`/ready` を待ちます。
5. 再構築されたエンティティとビューを既知の履歴と比較します。
6. 添付ファイルのバイト列、認証境界、未完了の外部作業の処理を確認します。
7. 復旧にかかった時間と、バックアップに含まれる最後の受け入れ操作を記録します。

放置されたアップロードもそのリハーサルに含めます。ファイルアップロードモジュールにはクリーンアップワーカーがありますが、通常のアプリケーション起動では現在起動されません。設定した期限やクリーンアップ間隔だけで、期限切れバイト列が削除されたと仮定しないでください。

最後の 2 つの測定は、ビジネス上の問いに答えます。アプリケーションが利用できなくなる可能性のある時間はどれくらいか、照合が必要になる可能性のある最近の作業量はどれくらいか。NeoHaskell がこれらの許容値を選ぶことはありません。

## ローカル Postgres データベースで練習する

[永続化](/ja/operate/persistence/)の Docker Compose データベースでは、元のデータを置き換えずにデータベースだけのリストアを練習できます。既知の Cart を作成しサマリーを記録した後で `neo run` を停止します。`mug-shop` から、保護されたバックアップファイルへローカルデータベースをエクスポートします。

```sh
docker compose exec -T postgres pg_dump -U neohaskell -d neohaskell --format=custom > mug-shop.backup
```

同じローカル Postgres サービスの中に新しいデータベースを作成し、そこへリストアします。

```sh
docker compose exec -T postgres createdb -U neohaskell mug_shop_restore
docker compose exec -T postgres pg_restore -U neohaskell --dbname=mug_shop_restore < mug-shop.backup
```

リストア先のデータベースがすでに存在する場合、`createdb` は失敗するはずです。確認していないデータを置き換えるのではなく、後のリハーサルには新しいリストア名を選びます。アプリケーションを起動する前に、両方のコマンドが成功することを確認します。

実際のアウトバウンドインテグレーションを追加している場合は、分離したアプリケーションリビジョンで、まず制御したプロバイダーエンドポイントを使うか、その登録を削除します。その後、追加した設定でリストアしたデータベースを選びます。

```sh
DB_NAME=mug_shop_restore DB_PASSWORD=neohaskell neo run
```

ローカルデータベースで使ったカスタム `DB_PORT` があれば保ちます。別のターミナルで `/ready` を確認し、[HTTP とフロントエンド](/ja/build/http-and-frontend/)のリクエストを使って元の Cart サマリーを同じ識別子で取得します。テストを実行したり新しいデータを作ったりする前に、元の結果と比較します。バックアップには、機密性のあるイベント履歴が含まれる可能性があります。適切なアクセス保護を付けて保存します。

この手順で復元されるのはイベントデータベースです。アップロードのバイト列と、別のプロバイダー認証情報ストアには、それぞれのバックアップが必要です。`pg_restore` が成功したことは、アプリケーション確認の始まりであり、それらの代わりではありません。

## 再構築の境界を理解する

クエリサブスクライバーはイベントからビューを再構築でき、レディネス状態を公開します。低レベルには `rebuildAllAsync`、`rebuildFrom`、チェックポイント API があります。これらはアプリケーション・フレームワーク API であり、`neo rebuild` コマンドではありません。

通常の `Application` 配線は現在、チェックポイントストアへ自動接続せず `Subscriber.new` を作成します。永続クエリ行だけでは、チェックポイントからの再開を証明できません。使うストア、起動経路、プロジェクションロジックそのものをテストします。[永続化](/ja/operate/persistence/)も参照してください。

Postgres のクエリストアは、なければテーブルを作成します。これは汎用スキーマ移行サービスではありません。互換性のないテーブルスキーマを持つ既存インストールには、明示的な移行計画が必要です。

## 識別情報で外部作業を復旧する

アプリケーションの操作を外部の対応する操作に関連付けるのに十分な情報を保ちます。EC の将来の決済ワークフローなら、注文をプロバイダーの操作につなぎます。プロバイダーがリクエストを受け入れた後、応答が届く前に接続が失敗した場合にどうするかを定義します。

これは決済アダプターに必要な設計であり、NeoHaskell が完全な決済・照合システムを同梱するという主張ではありません。プロバイダーが対応する冪等性と状態検索は設計の参考になりますが、正確な保証は選んだプロバイダーに対して確認する必要があります。
