フレームワーク全体を理解しなくても、改善に貢献できます。分かりにくいインストール手順、抜けている境界ケース、もうコンパイルできない例は、役に立つ出発点です。NeoHaskell を学んだ経験やアプリケーションを構築した経験は、次の読者がどこで困るかを示す証拠になります。

貢献はアプリケーションの道のりから分岐します。自分のアプリケーションを自信を持って運用することは、フレームワークメンテナーになることを要求しません。

## 範囲を限定した改善から始める

よい最初の報告には、達成しようとしたこと、最小の再現手順、期待する振る舞い、実際の結果、関係するバージョンが含まれます。共有する前に認証情報と個人データを削除します。

ドキュメントの変更では、段階的な学習経路を保ちます。まず状況を説明し、正確な例を示し、読者が結果を確認する方法を伝えます。バグでは、実装を変更する前に、報告された理由で失敗する回帰ケースを追加します。

## 所有するコンポーネントを見つける

| 関心事 | リポジトリの領域 |
| --- | --- |
| 言語の語彙とサービスフレームワーク | `core/` |
| 実行可能な Cart/Stock の例と HTTP 受け入れテスト | `testbed/` |
| プロバイダーインテグレーション | `integrations/` |
| Rust CLI と組み込み視覚 IDE | `neo/` |
| 人が読むドキュメント | `website/` |
| アーキテクチャ上の決定 | `docs/decisions/` |

[コントリビューター README](https://github.com/neohaskell/NeoHaskell/blob/main/README.md)と[機能マップ](https://github.com/neohaskell/NeoHaskell/blob/main/codemap/README.md)を読みます。マップは概念を実装とテストにつなぐため、小さな修正が範囲のないリポジトリ調査になるのを防ぎます。

## リポジトリのツールチェーンを使う

NeoHaskell リポジトリのチェックアウトから、`./dev` コマンドは必要に応じて固定環境に入ります。

```sh
./dev watch
```

編集中はウォッチャーを動かしたままにします。別のターミナルで次を実行します。

```sh
./dev check
./dev test "EventStore" nhcore-test-service
./dev lint
```

`./dev test "EventStore" nhcore-test-service` は、焦点を絞ったテスト選択の例です。変更を確立するテストを選びます。修正と無関係な選択では、証拠が得られません。サービスのテストには PostgreSQL が必要なことがあり、HTTP 受け入れテストには実際のフィクスチャが必要です。セットアップはコントリビューター README にあります。

これらのリポジトリコマンドは、生成されたアプリケーションを操作する `neo build` や `neo test` とは異なります。Rust CLI と IDE の変更には、`neo/` の下に独自のスコープ付き指示とテストレイヤーがあります。

## 広い実装の前に公開振る舞いを提案する

リポジトリでは、管理された変更に変更仕様とドラフトプルリクエストを使います。仕様では、約束する API の差分を説明し、各基準を証明するテストを名前で示します。大きな実装の前に、その提案をメンテナーがレビューします。最終レビューでは、実装された結果と検証を確認します。

正確な範囲、ブランチ・スタックのワークフロー、レビューゲート、例外については、現在の[リポジトリの貢献契約](https://github.com/neohaskell/NeoHaskell/blob/main/AGENTS.md)を読みます。失敗をグリーンにするためだけに既存のテスト期待を変えないでください。ユーザーから見える振る舞いが何に変わったかを説明し、必要なメンテナーレビューを得ます。

## 変更に必要ならさらに深く進む

コアサービスのアーキテクチャは、コマンドの決定、イベントの永続化、エンティティの再構築、クエリ、トランスポート、インテグレーションを分けます。公開イベントや導出を 1 つ変更すると、複数に影響することがあります。所有するテストとアーキテクチャ決定を追い、ローカルのユニットだけでなく公開のリファレンスアプリケーションも確認します。

CLI の変更は、新しく生成されるすべてのアプリケーションにも影響する可能性があります。組み込みスターターと、スターターとフレームワークの互換性確認も、その責任の一部です。

**最初の貢献を試す：**学習の道のりや自分のプロジェクトから、分かりにくかった場面を 1 つ選びます。必要だった説明を書き、それを支える公開ソースを特定し、別の読者にたどってもらいます。フレームワークの内部に触れる前でも、具体的な改善になります。
