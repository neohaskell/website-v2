変更を保存することと、その後の作業を完了することは別です。プレビューを生成する前に書類を保存することもあれば、通知を送る前にメッセージを記録することもあります。アプリケーションでは、受け入れた変更と、まだ行う必要がある作業の両方を表す必要があります。

**インテグレーション**は、アプリケーション内の事実を別の作業につなぎます。NeoHaskell では、リクエストを記述し、その結果をコマンドに戻せます。成功の意味、失敗を人にどう見せるか、安全に繰り返せる操作はどれかを決めるのは、引き続きあなたです。

インテグレーションを実装する前に、[コマンドとイベント](/ja/build/commands-and-events/)と[クエリ](/ja/build/queries/)に慣れておきます。例では EC の練習用プロジェクトを拡張しますが、同じインテグレーションのライフサイクルはほかのアプリケーションにも適用できます。評価する人は、例を実装せずに冒頭と決定のセクションを追えます。

`neo new` で作った `mug-shop` プロジェクトで続けます。`src/Shop/Cart/` と `src/Shop/Stock/` のモジュール、`src/App.hs` の登録を使います。先に[在庫とチェックアウト](/ja/build/stock-and-checkout/)を完了し、効果を追加するときも既存のテストを残します。このセクションのすべてのコマンドは、そのプロジェクトディレクトリから実行します。

## プロジェクトを準備する

`neo new` が生成するプロジェクトには、NeoHaskell のコアライブラリとインテグレーションライブラリがすでに含まれています。下で使う HTTP、メール、書類、AI モジュールとともに、`Integration.Command` と `Integration.Timer` は、プロバイダーごとにパッケージを追加せず利用できます。

プロジェクト設定として `neo.json` を保ちます。組み込みインテグレーションには、依存関係リストへの新しいエントリは必要ありません。カスタムアダプターに追加ライブラリが必要なら、[CLI リファレンス](/ja/reference/cli/)で説明する依存関係設定を使います。生成されたビルドファイルは Neo に管理させます。

アプリケーションコードは `src/Shop/` の下に追加し、ハンドラーとサービスを `src/App.hs` に登録し、確認を `tests/` の下に置きます。プロジェクトルートから次を使います。

```sh
neo build
neo test
neo run
```

置き換える前に、動いているサーバーを停止します。HTTP リクエストと IDE 用に別のターミナルを残します。プロバイダーの認証情報は実行中のプロセスの[設定](/ja/build/configuration/)に置きます。ライブラリをインストールしても、アカウント、認証情報、完成したワークフローは提供されません。

コードの抜粋では、教えるルールやリクエストに焦点を当てます。実装モジュールでは `import Core` を使いますが、ここではモジュールヘッダーとその他の import を省略しています。[インテグレーションの完全なチェックポイント](/examples/mug-shop-connect.tar.gz)には、調整、アップロード、タイマー演習の実行可能なファイルがあります。完全な配線を確認したい場合は、既存のプロジェクトに適用します。

まず、外部サービスを必要としない[Cart と Stock の調整](/ja/connect/workflows/)から始めます。後の章では、プロバイダーのビルダーをプロジェクトに置き、接続前に定義する必要がある新しいコマンドとコールバックを特定します。

## インテグレーションを通してイベントを追う

練習用プロジェクトで、注文確認を考えます。ワークフローは、次のインテグレーションプリミティブから作るアプリケーション設計です。

1. コマンドが注文を受け入れ、注文作成イベントを記録する。
2. アウトバウンドハンドラーがそのイベントを認識し、メールリクエストを記述する。
3. インテグレーションが注文の決定関数の外でリクエストを実行する。
4. コールバックが、プロバイダーの受け入れまたは失敗を記録するコマンドを生成する。
5. クエリが結果の状態を見えるようにする。

4 つ目のステップを意図的に**コマンド**にしています。新しい情報は、引き続きアプリケーションのルールを通って入ります。プロバイダーを呼び出しても、エンティティやクエリを直接編集することはありません。

**アウトバウンド**インテグレーションはアプリケーションイベントに反応します。**インバウンド**インテグレーションは、タイマーなどイベントフローの外部から始まり、コマンドを送信します。

## 小さな語彙を読む

ハンドラー内の作業を整理するには、2 つの小さな操作を使います。

```haskell
batch :: Array Action -> Outbound
none :: Outbound
```

`Integration.outbound` は、サポートされたリクエストレコードを 1 つのアクションに変えます。`Integration.batch` は、イベントに対して実行するアクションを集めます。`Integration.none` は、そのイベントに対してこのハンドラーに作業がないことを示します。バッチはコレクションであり、外部システムにまたがるトランザクションではありません。

具体的なリクエスト型によって、利用可能なフィールドが決まります。ほとんどのプロバイダーインテグレーションには `onSuccess` と `onError` があります。どちらのコールバックも、**同じコマンド型**を生成しなければなりません。成功・失敗の選択肢を持つ 1 つのコマンドは選択肢になります。関係のない 2 つのコマンド型では、1 つの `Request command` を満たせません。

## 両端を登録する

ハンドラーを定義しただけでは登録されません。アプリケーションは、アウトバウンドハンドラーと、それが生成できる各コマンドを含むサービスを登録する必要があります。

生成されるコマンドは `InternalTransport` を宣言しなければなりません。インテグレーションディスパッチャーは、公開 HTTP エンドポイントとは別にそれらのコマンドを集めます。1 つのコマンドに内部トランスポートと公開トランスポートを混在させることはできません。人とインテグレーションが同じルールを必要とするときは、[タイマーの例](/ja/connect/timers/)のように決定ロジックを共有する別々の入り口を使います。[ワークフロー](/ja/connect/workflows/)で、Cart と Stock の完全なハンドラーを自分のプロジェクトに追加します。

コールバックハンドラーがない場合、ディスパッチャーがログに記録します。それは元の外部操作が失敗した証拠ではありません。プロバイダーはすでに受け入れている可能性があります。

## 自信の根拠を知る

3 つの境界を別々にテストします。

- **選択：** 意図したイベントがアクションを生成し、関係のないイベントが何も生成しないか？
- **変換：** プロバイダーの結果が、壊れた結果や拒否を含め、正しいコマンドを生成するか？
- **完了：** そのコマンドが登録済みサービスに届き、期待するクエリ状態を生成するか？

インテグレーションランタイムは、エンティティごとのワーカーと上限付きキューを使います。エラー処理と設定可能なタイムアウトを含みます。これらの仕組みは、プロセスのクラッシュと外部プロバイダーをまたぐ永続配送や exactly-once 実行を確立しません。重要な未完了作業には、アプリケーションレベルの復旧設計が必要です。

型付きハンドラーは処理中にストリームからエンティティを再構築します。トリガーとなったイベント時点のスナップショットが保証されて渡されるわけではありません。特定の発生を説明する必要がある情報は、イベント自体に置きます。
