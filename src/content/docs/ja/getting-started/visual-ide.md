[最初のカートの演習](/ja/build/first-cart/)でカートを作り、そのサマリーを読みました。次は、同じ振る舞いを Neo IDE で追います。送ったリクエスト、記録された事実、読み戻した情報を確認します。セットアップで作った `mug-shop` で作業を続けてください。

振る舞いの確認と一緒に使います。まとまりのあるグラフは変更を理解する助けになりますが、アプリケーションが意図したポリシーを実行する証明にはなりません。

## コードを開く前にモデルを見る

![mug-shop の Neo IDE に、最初のカート機能で青い CreateCart コマンド、オレンジの CartCreated イベント、緑の CartSummary クエリが接続されて表示されています。](/screenshots/neo-ide-overview.png)

*最初のカート機能です。作成、記録された事実、サマリーを示します。どちらのスクリーンショットも選択すると、このページを離れずに拡大できます。*

図を 3 回に分けて読みます。

1. **リクエストを見つける。** 青い `CreateCart` カードは、カートを求めることを表します。下向きの矢印をたどり、オレンジの `CartCreated` という事実を見つけます。
2. **人が見る情報を見つける。** 緑の `CartSummary` カードは、`CartCreated` から情報を受け取ります。フィールドには `itemCount` と `isEmpty` があります。IDE では、これらの緑のカードを**クエリ**と呼びます。アプリケーションのリードモデル側を表します。
3. **作業場所を見つける。** 左パネルには章とスライスが一覧表示されます。ここでは `CreateCart` と `CartSummary` が Cart 章を、エージェントと話し合える小さな部分に分けています。

[実装済みのイベントモデル](/ja/start/event-modeling/)と比べてください。そちらの図は、続いていく画面や具体的な値を含め、時間の中で 1 つの例を追います。IDE のグラフは、再利用可能なコマンド、イベント型、クエリを示します。1 つの `CartSummary` カードが、さまざまな履歴の後のビューを表せます。その矢印はモデル内の関係を表し、実行中のリクエストのライブトレースではありません。

## カートプロジェクトで続ける

カートの演習中にすでに IDE を開いているなら、そのウィンドウを開いたままにします。まだなら、カートアプリケーションの `src/` があるディレクトリで次を実行します。

```sh
neo ide
```

セットアップで作成した `mug-shop` ディレクトリを使います。以下では、`src/Shop/Cart/` に追加したカートのコードとモデルを同期します。

表示されたアドレス（通常は `http://127.0.0.1:2323`）を開きます。IDE は起動したプロジェクトディレクトリにバインドします。編集する前に、接続状態に表示されたワークスペースが正しいことを確認します。IDE とアプリケーションの HTTP サーバーは、ポートも別々の別プロセスです。

モデルはプロジェクトルートの `event-model.json` にあります。新しいプロジェクトにはまだ存在しない場合があります。キャンバスの操作でモデルを作り、小さな編集を行って自動保存させます。新しいワークスペースでは、古いブラウザー内モデルを見ていないか確認します。**New** は空のモデルを開始し、**Open** は現在のワークスペースファイルを読みます。

接続中は変更が自動保存されます。閉じる前に保存状態を待ち、意味のあるバージョンを Git で管理します。Cmd/Ctrl-S は保留中の自動保存を書き出しますが、Git のコミットは作成しません。

## 図をソースにつなぐ

ワークスペースにモデルファイルができたら、同じプロジェクトの別のターミナルで次を実行します。

```sh
neo inspect
neo inspect sync
neo validate
```

`neo inspect` は、見つかったドメイン構造を報告します。`neo inspect sync` はソースからモデルを更新し、モデルファイルを書き込みます。`neo validate` は変更せずにスキーマと参照を確認します。CLI で同期した後、IDE の **Open** をクリックするか再読み込みして、保存したモデルを読みます。CLI だけで書き込んでも、ソースファイルウォッチャーを通して更新が通知されるわけではありません。モデルファイルがないと検証に失敗するため、先にモデルを作成して保存します。

IDE はソースの変更も監視し、同じ同期を試みます。既存ノードのフィールド変更ではレイアウトを保つように設計されています。新しく見つかった構造では、より広いレイアウト更新が起きることがあります。大きなリファクタリングの後は結果を確認します。

現在、同期は**コードからモデルへ**行われます。図を編集しても、対応するアプリケーションコードは生成されません。望むモデルをコーディングエージェントと話し合い、エージェントにソースを変更させ、更新された図を意図と比べます。

## 小さな振る舞いを読む

`CreateCart` を見つけ、`CartCreated`、さらに `CartSummary` へたどります。その名前を、前の演習で送ったリクエストと観測した空のカートのサマリーにつなげます。カート識別子がその経路をどう通るか、エージェントに示してもらいます。

## カートの成長に合わせて戻る

[コマンドとイベント](/ja/build/commands-and-events/)で `AddItem` を追加したら、同じプロジェクトをもう一度同期して、そのコマンドを選択します。何の情報が必要で、受け入れられたら何を記録するでしょうか？下の詳しいビューでは、そのとき確認できる内容を示します。

![青い AddItem コマンドを選択すると、オレンジの ItemAdded イベントへの矢印が強調表示されます。AddItem は cartId、stockId、quantity を持ち、ItemAdded は entityId、stockId、quantity を持ちます。ほかのノードは薄く表示されます。](/screenshots/neo-ide-detail.png)

*`AddItem` を選択すると、`ItemAdded` への接続が強調されます。拡大するとフィールドが読みやすくなり、周囲のモデルはコンテキストとして表示されたままです。*

ここでは、特定の情報を追えます。`quantity` はコマンドに入り、受け入れられたイベントに現れます。要求された `cartId` は、イベントが `entityId` として持つカートを識別します。対応するルールがソースのどこにあるかをエージェントに示してもらい、0 が拒否されることを実演してもらいます。`quantity` という名前のフィールドを見れば、どの情報が運ばれるかは分かりますが、ルールがどの値を受け入れるかまでは分かりません。

キャンバスの **+** と **−** の操作でズームを変更します。ノードを選択すると、その接続が強調されます。図が表示領域の外にある場合は **Fit View** を試します。保存したモデルを開き直すか再読み込みすると、使いやすい開始位置にも戻せます。

アプリケーションモデルが大きくなったら、機能と章を使って 1 つの振る舞いに集中します。別のドメインや外部プロバイダーを調べるときは、境界をまたぐ接続をたどります。**Tidy by flow** は表示を整えるだけで、ビジネスルールは直しません。Problems パネルはモデル検証の問題を見つける助けになります。

**Heal with AI** は、設定された Claude CLI のフローを呼び出す、任意のモデル修復操作です。通常の表示、調査、検証、決定的な同期にこの操作は必要ありません。別のエージェントの提案と同じように変更をレビューします。実行時の振る舞いを証明するものではありません。

## 現在の範囲を知る

Model キャンバスは実装済みです。Schema、Logs、Emulate の各レンズは、現在は将来の作業向けのプレースホルダーを表示します。[運用上の証拠](/ja/operate/observability/)には、実際のアプリケーションログとテストを使います。

ローカル作業ではデフォルトのループバックバインドを保ちます。`--host 0.0.0.0` でバインドすると、ほかのネットワークインターフェースから IDE が見えるようになります。ローカルのワークスペースツールを本番の顧客向けインターフェースとして扱ってはいけません。

## 確認する

今ある機能で、2 回目の `CreateCart` リクエストがどうなるか予測します。送信し、サマリーで両方の識別子を見つけます。グラフに `CreateCart` ノードが 1 つしかないのは、それが各発生ではなく、リクエストの種類を表すためです。新しい識別子を選ぶコードをエージェントに見つけてもらい、そのフィールドをコマンドからイベント、クエリへたどります。

次のレッスンの後で戻り、数量 0 の拒否も確認します。`AddItem` カードはリクエストを示し、どの値を受け入れるかはその決定関数が決めます。

次は、[コマンドとイベント](/ja/build/commands-and-events/)でこれらの接続の背後にある決定を説明します。個別のコマンドについては、[CLI リファレンス](/ja/reference/cli/)を参照してください。

実装の証拠：[IDE サーバー](https://github.com/neohaskell/NeoHaskell/blob/main/neo/src/commands/ide.rs)、[ソース同期](https://github.com/neohaskell/NeoHaskell/blob/main/neo/src/ide/sync.rs)、[現在のレンズ](https://github.com/neohaskell/NeoHaskell/blob/main/neo/assets/ide/src/ui/lenses/lenses.tsx)。
