最初のマイルストーンは、自分のプロジェクトです。`neo`（NeoHaskell のコマンドラインツール）で作成し、後の章で発展させます。同じディレクトリに、コード、テスト、設定、視覚モデルを置きます。

練習用プロジェクトを `mug-shop` と呼びます。これから構築する小さなアプリケーションです。別の名前を選び、ガイドで `mug-shop` と書かれている場所ではそのディレクトリを使ってもかまいません。

## ツールを準備する

macOS または Linux を使います。Windows では WSL2 の中で作業してください。Git と[お使いの OS 用の Nix](https://nixos.org/download/)をインストールします。Nix が、プロジェクトで選択されたコンパイラとビルド依存関係を提供します。GHC や Cabal を別にインストールする必要はありません。

新しいターミナルで、両方のコマンドが利用できることを確認します。

```sh
git --version
nix --version
```

Neo は Nix flakes を使います。Nix のインストールで flakes が有効になっていない場合は、既存の設定を残したまま `~/.config/nix/nix.conf` に次の行を追加します。

```ini
experimental-features = nix-command flakes
```

## Neo をインストールする

[Neo のリリース](https://github.com/neohaskell/NeoHaskell/releases/latest)から、コンピューター用の実行ファイルをダウンロードします。

:::note[バージョン要件]

この例には、スターターフレームワークの pin が `deriveEntity` を含む 5 つすべての `derive…` ヘルパーを `Core` 経由でエクスポートし、対応する Neo コンパイラープリセットを使う Neo リリースが必要です。`neo new` の後は、生成された `neo-version` pin を維持してください。スターターがこれらのヘルパーを提供しない場合は、ソースファイルを変更する前に、対応するフレームワーク pin を持つリリースをインストールします。ソースファイルに言語設定を追加する必要はありません。

:::

| コンピューター | ダウンロード |
| --- | --- |
| macOS、Apple シリコン | `neo-aarch64-apple-darwin` |
| macOS、Intel | `neo-x86_64-apple-darwin` |
| Linux または WSL2、Intel/AMD 64 ビット | `neo-x86_64-unknown-linux-gnu` |
| Linux、ARM 64 ビット | `neo-aarch64-unknown-linux-gnu` |

たとえば Apple シリコンの Mac では、次のようにします。

```sh
mkdir -p "$HOME/.local/bin"
curl -fL https://github.com/neohaskell/NeoHaskell/releases/latest/download/neo-aarch64-apple-darwin -o "$HOME/.local/bin/neo"
chmod +x "$HOME/.local/bin/neo"
export PATH="$HOME/.local/bin:$PATH"
neo --version
```

別のプラットフォームでは、ダウンロード URL の末尾のファイル名を表のものに置き換えます。保存先のファイル名は `neo` のままにします。今後のターミナルでも Neo を使えるように、`export PATH` の行をシェルの起動ファイル（zsh なら `~/.zshrc`、bash なら `~/.bashrc`）にも追加します。リリースには `SHA256SUMS` が含まれているため、ダウンロードしたファイルのチェックサムを確認できます。

コマンドはインストールされた Neo のバージョンを表示します。`command -v neo` で、シェルが見つけた実行ファイルを確認できます。アップグレードするときは両方を確認し、古いインストールが `PATH` で優先されないようにします。

## アプリケーションを作る

プロジェクトを保存しているディレクトリから実行します。

```sh
neo new mug-shop
cd mug-shop
neo build
```

Neo の質問でプロジェクトの詳細を受け入れるか、自分で選びます。`neo new` は、小さなスターター、テストスイート、固定された依存関係を持つアプリケーションを作ります。`neo build` はそれをコンパイルします。依存関係のダウンロードやビルド中は、最初のビルドに時間がかかることがあります。後のビルドではその作業を再利用します。Nix から、プロジェクトが宣言したバイナリキャッシュを信頼するか尋ねられることがあります。

スターターにはサンプルコードとしてカウンターが含まれています。次の章では、同じプロジェクト内で、アプリケーションの配線を最初のカート機能に置き換えます。先にカウンターの演習を完了する必要はありません。

## 変更する部分を見つける

| 場所 | そこで行うこと |
| --- | --- |
| `src/App.hs` | サービス、クエリ、イベントストア、Web トランスポートを接続します。 |
| `src/Shop/` | このガイドで作るアプリケーションの機能を追加します。 |
| `tests/` | 振る舞いを記述し、繰り返し確認します。 |
| `neo.json` | プロジェクトの詳細を設定し、追加の依存関係を宣言します。 |
| `flake.lock` と `neo.json` の `neo-version` | 解決済みの依存関係のバージョンを再現可能に保ちます。 |
| `event-model.json` | IDE を使い始めたときに視覚モデルを保存します。 |

`src/Shop/` と `event-model.json` は次の手順で登場します。新しいスターターにまだ存在する必要はありません。Neo は設定とソースモジュールから低レベルのビルドファイルを生成します。生成されたビルドファイルを手で管理するのではなく、`neo.json` を通してプロジェクトを変更し、`neo build` を再実行します。

`neo new` が用意した依存関係の pin は維持します。これらは、スターターと互換性のあるフレームワークのリビジョンを識別します。アップグレードは、独自のビルドと振る舞いの確認を伴う、意図的なプロジェクト変更です。

## 日常のループを学ぶ

プロジェクトのルートから、次のコマンドを繰り返し使います。

| コマンド | 得られるもの |
| --- | --- |
| `neo build` | アプリケーションとその配線のコンパイラーチェック。 |
| `neo run` | リクエストを試せる実行中のアプリケーション。 |
| `neo test` | プロジェクトの繰り返し可能な振る舞いの確認。 |
| `neo ide` | アプリケーションのモデルを探索する視覚的なワークスペース。 |

今は、ビルドの成功がセットアップの確認になります。次の章では、カートを作り、リクエストを送り、結果を読み戻します。これで、コンパイルと実際に調べられる振る舞いがつながります。

コマンドが失敗したら、完全なエラーを残して[トラブルシューティング](/ja/reference/troubleshooting/)を使います。すでにアプリケーションがある場合は、`neo new` をもう一度実行するのではなく、そこで新しい機能を適用します。
