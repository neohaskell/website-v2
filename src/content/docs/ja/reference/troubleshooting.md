まず、起きると期待したことを明確にします。プロジェクトがビルドされる、プロセスが起動する、受け入れられた変更が見える、プロバイダーがアクションを確認する、といったことです。その後、証拠が最初に食い違った地点を見つけます。これにより、あなたとエージェントにとって「アプリケーションが壊れている」より小さな問題になります。

## 役に立つ診断記録を保つ

コマンドまたはリクエスト、リビジョン、期待する結果、実際の結果、最小限で安全な再現手順を記録します。関係する完全なエラーを含めますが、シークレットと個人データは削除します。ここにあるコマンドは、`neo.json` を含むアプリケーションディレクトリから実行します。この道のりでは `mug-shop` です。

| 症状 | 最初の確認 | 次のアクション |
| --- | --- | --- |
| `neo` が Nix を起動できない | Nix がインストールされ、現在のシェルから利用できるか | インストール後にシェルを開き直し、[はじめに](/ja/getting-started/)を読む |
| ビルドが `neo.json` の不足を報告する | 現在のディレクトリ | 生成されたプロジェクトルートから実行する |
| 生成された Cabal/Nix の編集が消える | 再照合のソース | サポートされる設定を `neo.json` に記述する |
| ビルドがロックされたファイルを拒否する | `.locked-files` と作業ツリーの変更 | 意図したドメイン変更をレビューし、[進化](/ja/operate/evolution/)を読む |
| HTTP のバインド前にアプリケーションが失敗する | 最初の起動・設定・データベースエラー | プローブ時間を変更する前にエラーを直す |
| `/health` は成功し、`/ready` は `503` を返す | レディネス本文とリプレイログ | 再構築中か失敗かを区別する |
| 受け入れられたコマンドが見えない | クエリの追随、識別情報、正しいリビジョン | イベントからクエリへの経路を追う |
| インテグレーションがタイムアウトする | プロバイダー結果とローカル相関識別子 | 外部アクションを再送する前に不確実性を解決する |

## 新しいモジュールまたは依存関係が見つからない

アプリケーションのモジュールは `src/` の下に置き、パスをモジュール名と一致させます。`Shop.Cart.Core` は `src/Shop/Cart/Core.hs` に置きます。import の綴りと、意図したプロジェクトをビルドしているかを確認します。ファイルを保存して、次を実行します。

```sh
neo --ci build
```

CLI はソースモジュールを見つけ、管理対象のプロジェクトファイルを再生成します。外部パッケージでは `neo.json` の `dependencies` を編集します。生成されたビルドファイルだけに追加しないでください。裸の依存関係名は NeoPackages レジストリで検索されます。Hackage のパッケージを意図するときは、明示的な `hackage:` キープレフィックスを使います。[依存関係の構文](/ja/reference/cli/#manage-project-dependencies)を参照してください。

レッスンが、プロジェクトの固定したフレームワークリビジョンでは使えない API を使っている場合は、`neo --version` と `neo.json` の `neo-version` をレッスンのバージョンコンテキストと比べます。意図的にアップグレードし、`neo build` と `neo test` を再実行します。ローカルのフレームワークチェックアウトはアプリケーションのワークフローには含まれません。

## モデルがないことと無効なモデルは異なる

プロジェクトルートで次を実行します。

```sh
neo validate --json
```

終了コード `4` はファイルがないこと、`3` は JSON を解析できないこと、`2` は解析したモデルがスキーマまたは参照に違反することを意味します。編集する前に、報告された場所を調べます。視覚モデルを扱うには `neo ide` を開きます。保存モデルをソースから更新する意図があるときだけ `neo inspect sync` を使います。

有効なグラフでも、アプリケーションが意図したキャンセルポリシーを実装しているとは限りません。[振る舞いのテスト](/ja/build/testing/)で確認します。

## Hurl が接続拒否を報告する

Hurl テストがある場合、`neo test` はアプリケーションを起動し、実行前にポート 8080 を調べます。プロセスがクラッシュしたか、別のプロセスがポートを使っているか、アプリケーションのポートを変更したかを確認します。現在の実装では起動プローブが 8080 に固定されているため、Hurl の URL だけ変更してもプローブは更新されません。

既存のアプリケーションプロセスを先に停止します。ローカルで `neo run` を実行して起動エラーを読み、その診断実行を停止してから `neo test` を再試行します。test コマンドが独自のプロセスを起動するためです。別にサーバーが動いていると、どのリビジョンをテストしたかが分かりにくくなります。サーバーが応答してもクエリ依存のテストがリプレイと競合するなら、`/ready` も確認します。CLI の起動待ちは任意の HTTP 応答を受け入れます。

Nix のコールドスタートで、アプリケーションが提供を始める前に現在の 60 秒待ちを使い切ることもあります。診断用の `neo run` が起動を完了するまで待ち、応答を確認して停止し、ビルド環境が温まった状態でテストを再試行します。実際の設定・アプリケーションエラーと遅延を分けて扱います。

## クエリの追随に失敗する

[レディネスとログのガイド](/ja/operate/observability/)を使います。クエリ名、位置、リビジョン、サニタイズした失敗情報を残します。データベース接続とイベントのデコードを、データ変更を考える前に確認します。

Postgres のイベントストレージが、クエリ状態の永続化を意味するわけではありません。永続化されたクエリ状態も、通常のアプリケーション配線でチェックポイント再開を意味するわけではありません。[永続化](/ja/operate/persistence/)でこれらの境界を説明します。ビューを空で健全に見せるために、イベント履歴を削除しないでください。

## データベース接続が断続的に失敗する

動いているすべてのリビジョンで、プールとリスナーを一覧にします。設定したプールサイズと、データベースの利用可能な容量を確認します。リスナー接続にはセッションを維持する直接エンドポイントが必要です。トランザクションモードのプーリングでは、必要な `LISTEN/NOTIFY` の振る舞いを提供できません。

配線した各ストアの TLS 設定を確認します。[永続化](/ja/operate/persistence/)で追加した `DB_SSL_MODE` フィールドは、値を渡したストアだけに影響します。すべての Postgres クライアントの共通スイッチではありません。

## エージェントへ焦点を絞った作業を返す

たとえば、EC の練習用プロジェクトでの診断タスクは次のようになります。

> 「リビジョン A ではコマンドが受け入れられます。レディネスも ready になりますが、このユーザーのクエリから Cart が抜けています。クエリとアクセス制御を見つけ、ポリシーを保ったまま、プロジェクションエラーと所有権エラーを区別するテストを示してください。」

これで証拠を示し、ビジネス上の制約を保てます。エージェントが修正を提案したら、元の再現手順と、近い拒否ケースを繰り返します。
