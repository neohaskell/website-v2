Neo CLI-ն օգնում է ստեղծել, կառուցել, թեստավորել և ուսումնասիրել NeoHaskell նախագիծը։ Օգտագործեք Ձեր անմիջական նպատակին համապատասխան հրամանը. տեսողական IDE-ն նույն նախագիծը հասկանալու մեկ այլ եղանակ է։

Նախագծի հրամանները գործարկեք այն գրացուցակից, որը պարունակում է `neo.json`-ը։ Տեղադրված երկուականի սեփական օգնության համար գործարկեք `neo --help` կամ որևէ հրամանի `--help`։ Այս էջը նկարագրում է Neo 0.10.0-ը՝ [կարգավորման](/hy/getting-started/) մեջ օգտագործված թողարկումը. հին տեղադրված թողարկումը կարող է տարբերվել։

## Ընդհանուր դրոշներ

| Դրոշ | Ազդեցություն |
| --- | --- |
| `-v`, `--verbose` | Միացնում է CLI-ի debug մակարդակի ելքը |
| `--ci` | Անջատում է ինտերակտիվ հուշումները, անիմացիաներն ու գույները |
| `--help` | Ցույց է տալիս օգնությունը |
| `--version` | Ցույց է տալիս տարբերակը |

`--ci`-ն օգտակար է կրկնելի սկրիպտներում։ Այն տեղային թեստը արտադրական տեղակայում չի դարձնում։

## Ստեղծել, կառուցել, գործարկել և թեստավորել

Այս հաջորդականությունն օգտագործում է `mug-shop`-ը՝ կրկնվող ուսումնական նախագծի անունը։ Փոխարինեք Ձեր նախագծի անունով. հրամանները նույն կերպ են աշխատում։

```sh
neo --ci new mug-shop
cd mug-shop
neo build
neo run
```

`neo run`-ը շարունակում է մատուցել, մինչև Ctrl-C-ով կանգնեցնեք այն։ Թեստերից առաջ կանգնեցրեք, քանի որ `neo test`-ն ինքն է սկսում ծրագիրը․

```sh
neo test
```

| Հրաման | Ընտրանքներ | Վարքագիծ |
| --- | --- | --- |
| `neo new [project_name]` | `--library` | Սկաֆոլդավորում է ներկառուցված starter-ից. CI ռեժիմում անունը պարտադիր է։ Գրադարանը չի ներառում գործարկիչն ու գործարկվող ֆայլի stanza-ն։ |
| `neo build` | `--watch`, `--skip-lock-check` | Հաշտեցնում է կազմաձևումն ու կառուցում. watch-ը օգտագործում է GHCi-ի հետադարձ կապը, skip-ը միայն շրջանցում է build-ի lock ստուգումը։ |
| `neo run` | `--watch` | Հաշտեցնում, կառուցում և գործարկում է. watch-ը փոփոխությունների դեպքում նորից կառուցում/վերագործարկում է։ |
| `neo test` | `--watch` | Գործարկում է նախագծի միավորային թեստերը, ապա հայտնաբերված Hurl HTTP թեստերը։ |

Build-ը, run-ը և test-ը `neo.json`-ից վերաստեղծում են կառավարվող կառուցման ֆայլերը և հայտնաբերում մոդուլներ `src/` ու `tests/`-ի տակ։ Ձեր `Shop.Cart` և `Shop.Stock` մոդուլները մնում են ծրագրում, իսկ CLI-ն զբաղվում է դրանք կառուցման մեջ ներառելով։

Երբ Hurl թեստեր կան, test հրամանը սկսում է ծրագիրը և սպասում `127.0.0.1:8080`-ի HTTP պատասխանին։ Այդ սպասումը ընդունում է ցանկացած HTTP պատասխան, բայց չի սպասում `/ready`-ի պրոյեկցիայի պայմանագրին։ Նախագծի թեստային պորտը ազատ պահեք և պրոյեկցիայի վերակառուցումից կախված սցենարներին ավելացրեք պատրաստականության ստուգումներ։ Անհատական ծրագրի պորտը պահանջում է ուշադրություն և՛ թեստերի թիրախներին, և՛ ընթացիկ ֆիքսված գործարկման ստուգմանը։

## Կառավարեք նախագծի կախվածությունները

`neo.json`-ը Ձեր նախագծի կախվածությունների ընտրության աղբյուրն է։ Պահեք դրա առկա `name`, `version` և `neo-version` դաշտերը, իսկ ծրագրին լրացուցիչ փաթեթ պետք լինելու դեպքում խմբագրեք `dependencies` օբյեկտը։ `neo-version`-ը ընտրում է շրջանակի վերանայումը. այն առանձին է `neo --version`-ով ցուցադրվող տեղադրված CLI-ի տարբերակից։

Հետևյալ աղյուսակը ցույց է տալիս աջակցվող շարահյուսությունը։ Փաթեթների անուններն ու պահոցները հայտարարության ձևի օրինակներ են, ոչ թե Cart-ի դասի պահանջվող կախվածություններ։

| Կախվածության գրառում | Իմաստ |
| --- | --- |
| `"package-name": "^1.2.3"` | Լուծել NeoPackages գրանցամատյանի փաթեթ՝ միջակայքին համապատասխան տարբերակով |
| `"hackage:package-name": "^1.2.3"` | Բացահայտորեն լուծել փաթեթ Hackage-ից |
| `"package-name": "github:owner/repository#revision"` | Օգտագործել նշված GitHub սկզբնաղբյուրն ու վերանայումը |
| `"package-name": "git:https://host/repository.git#revision"` | Օգտագործել մեկ այլ Git սկզբնաղբյուր |
| `"package-name": "file:../package-directory"` | Օգտագործել Ձեր պահպանած տեղային փաթեթը՝ ծրագրի կողքին |

Տարբերակների միջակայքերը օգտագործում են օրինակներ, ինչպիսիք են `^1.2.3`, `~1.2.3` և `>=1.2.3 <2.0.0`։ Մերկ փաթեթի անունը գնում է NeoPackages գրանցամատյան, այն լուռ Hackage-ի վրա չի ընկնում։ Երբ Hackage փաթեթ եք նախատեսում, օգտագործեք `hackage:` բանալու հստակ նախածանցը։ Առանց վերանայման Git սկզբնաղբյուրները լռելյայն ընտրում են `main`-ը, այնպես որ կրկնելիության կարևորության դեպքում նշեք վերանայված տարբերակը։

`neo.json`-ը խմբագրելուց հետո `mug-shop`-ից գործարկեք․

```sh
neo build
neo test
```

Վերանայեք ստեղծված փոփոխությունները և կախվածության ընտրությունը commit արեք այն օգտագործող ծրագրի կոդի ու թեստերի հետ միասին։ Առանձին խմբագրումներ մի պահեք ստեղծված `.cabal`, `cabal.project` կամ `flake.nix` ֆայլերում։ Այս էջում նկարագրված տարբերակում CLI-ն `neo add` հրաման չունի։

## Ուսումնասիրեք ծրագիրը

IDE-ն սկսեք Ձեր նախագծի գրացուցակից․

```sh
neo ide
```

IDE-ի այլ պորտի համար օգտագործեք `neo ide --port 2324`։ Այդ գործընթացը թողեք աշխատող և նույն նախագիծը ուսումնասիրեք երկրորդ տերմինալից․

```sh
neo inspect
neo inspect commands
neo inspect wiring
```

`neo ide`-ի լռելյայնը `127.0.0.1:2323` է։ `--host`-ը ընդունում է IP հասցեի բառացի արժեք, ոչ թե հոսթի անուն։ Օրինակ՝ `--host 0.0.0.0`-ը IDE-ն հասանելի է դարձնում այլ IPv4 միջերեսներում. դա ընտրեք գիտակցված։ Սերվերը կանգնեցրեք Ctrl-C-ով։

`neo inspect`-ը տպում է JSON։ Դրա ներկայացումներն են `domains`, `commands`, `events`, `queries`, `integrations` և `wiring`։ Առանց ներկայացման այն տպում է ուսումնասիրված ամբողջ նախագիծը։

`neo inspect sync`-ը **փոփոխություն է**. այն սկզբնաղբյուրից թարմացնում է `event-model.json`-ը։ Գոյություն ունեցող դաշտերի փոփոխությունները կարող են պահպանել դասավորությունը, իսկ նոր հանգույցները գործարկում են դասավորության աշխատանք։ Օգտագործեք այն, երբ մտադիր եք թարմացնել մոդելը, ոչ թե միայն կարդալու հաշվետվության համար։

Այդ մոդելը կարդալու համար տե՛ս [տեսողական IDE-ի ուղին](/hy/getting-started/visual-ide/)։

## Վավերացրեք պահված մոդելը

```sh
neo validate
neo validate ./event-model.json --json
```

Վավերացումը միայն կարդում է։ Ընտրովի ուղին լռելյայն դառնում է ընթացիկ գրացուցակի `event-model.json`-ը։ Այն ստուգում է սխեման ու հղումների ամբողջականությունը, ոչ թե Ձեր բիզնեսային կանոնների ճիշտ լինելը։

| Ելքի կոդ | Իմաստ |
| --- | --- |
| `0` | Վավեր մոդել |
| `1` | I/O կամ գործիքի ձախողում |
| `2` | Մոդելը չի անցնում վավերացումը |
| `3` | Սխալ ձևավորված JSON |
| `4` | Ֆայլը բացակայում է |

`--json`-ը արտածում է կառուցվածքային վավերացման արդյունքը՝ առանց մարդու համար նախատեսված մատյանային նախածանցների. ելքի կոդերը պահպանում են նույն իմաստը։

## Պաշտպանեք տիրույթի ֆայլերը

```sh
neo lock --all
neo lock Cart
neo lock install
neo lock check
```

`neo lock [search]`-ը օգտագործում է տիրույթի ֆայլերի մոտավոր որոնում։ `--all`-ը կամ առանց որոնման բոլոր հայտնաբերված տիրույթի ֆայլերն է ընտրում։ Մանիֆեստը գտնվում է `.locked-files`-ում։ `install`-ը գրում է Git pre-commit hook-ը՝ այդ ուղու առկա hook-ը վերագրելով, իսկ `check`-ը հայտնաբերում է փոփոխված lock արված ֆայլերը՝ ներառյալ աշխատանքային ծառի փոփոխությունները։ Տե՛ս [զարգացումը](/hy/operate/evolution/)՝ հնարավորության հիմքում ընկած պատմական համատեղելիության խնդրի համար։

Lock-ը stage է անում ընտրված ուղիներն ու `.locked-files`-ը և ստեղծում Git commit։ Նախ ստուգեք `git status`-ը. արդեն staged կապ չունեցող բովանդակությունը կարող է ներառվել commit-ում։ Lock hook-ը տեղադրելուց առաջ պահեք առկա pre-commit hook-ը։

## Տեղադրեք գործակալի առանձին հմտությունները

```sh
neo skills setup --tool codex --dry-run
neo skills setup --tool codex
```

Այս հրամանը բերում է համօգտագործվող հմտությունների գրադարանը և այն տեղադրում ընտրված գործիքների համար։ Մարդկանց համար փաստաթղթերը շարունակում են առանձին մնալ այդ հրահանգներից։

Կարգավորման ընտրանքներն են՝ կրկնելի `--tool` (`claude`, `codex`, `kiro`, `cursor`), `--all-tools`, կրկնելի `--skill`, `--force`, `--dry-run`, `--refresh` և `--no-primer`։ `--dry-run`-ը տպում է պլանը՝ առանց ծրագրում տեղադրելու, բայց գրադարանը բերելը կարող է լրացնել տեղային քեշը։ `--force`-ը թույլ է տալիս վերագրել նպատակակետերը, `--refresh`-ը նորից կլոնավորում է գրադարանը, իսկ `--no-primer`-ը բաց է թողնում միշտ միացված primer-ը և դրա հրահանգների ֆայլի կապակցումը։ Մերկ `neo skills`-ը կատարում է կարգավորում։

Ճշմարտության աղբյուրը [CLI-ի սահմանումն է](https://github.com/neohaskell/NeoHaskell/blob/main/neo/src/cli.rs)։ Ձախողման դեպքում օգտագործեք [խնդիրների վերացումը](/hy/reference/troubleshooting/)։
