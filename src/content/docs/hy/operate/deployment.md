Թողարկումը հաջող է, երբ նախատեսված տարբերակը մատուցում է ճիշտ վարքագիծ, ոչ թե միայն երբ տեղակայման հրամանն է ավարտվում։ Իրադարձությունների աղբյուրավորմամբ ծառայության դեպքում երթևեկությունը հեռու պահեք թարմ գործընթացից, քանի դեռ դրա կարդալու մոդելները հասնում են պատմությանը։ Նույն կանոնը վերաբերում է ամրագրման ներկայացմանը, փաստաթղթերի հերթին կամ ուսումնական նախագծի զամբյուղի ամփոփմանը։

NeoHaskell-ը տրամադրում է գործարկվող ծրագիր և HTTP ստուգման endpoint-ներ։ Ձեր հոսթինգի միջավայրն է տրամադրում գործընթացի վերահսկիչը, երթևեկության ուղղորդումը, գաղտնիքները, կայուն պահեստը և վերագործարկման քաղաքականությունը։ Ընթացիկ CLI-ում `neo deploy` հրաման չկա։

## Նույն ծրագիրը պատրաստեք հոսթի համար

Շարունակեք Ձեր `mug-shop` նախագծով՝ ներառելով `neo.json`, `src/Shop/Cart/`, `src/Shop/Stock/` և թեստերը։ Նախքան ընդունված փոփոխությունները վերագործարկումից հետո պահպանելու խոստումը ավարտեք [պահպանումը](/hy/operate/persistence/)։ Սկզբնական `SimpleEventStore`-ի կարգավորումը միտումնավոր հիշողության մեջ է։

Կոնկրետ ճանապարհ է Linux հոսթը, որի հաշվում տեղադրված են Neo CLI-ն, Nix-ը և Git-ը, և որը գործարկում է ծրագիրը։ Տեղադրեք **Ձեր ծրագրի** թեստավորված տարբերակը, պահեք դրա շրջանակի ամրակը և lock ֆայլերը, ապա կառուցեք այդ կամ համապատասխան կառուցման հոսթի վրա։ [Պահպանումից](/hy/operate/persistence/) staging-ի `DB_*` միջավայրի արժեքները տրամադրեք՝ մեկուսացված staging տվյալների բազայի դեմ այս ստուգումները գործարկելուց առաջ․

```sh
neo --ci build
neo --ci test
```

Թեստի հրամանը ստեղծում է իրական ծրագրի վիճակ և ինքն է սկսում սերվերը։ Այն մի գործարկեք արտադրական տվյալների բազայի դեմ կամ այն ժամանակ, երբ մեկ այլ գործընթաց զբաղեցնում է 8080 պորտը։ Արտադրական տվյալների բազան կազմաձևեք միայն staging-ի ստուգումներն անցնելուց հետո։

Ծրագրի գրացուցակից սա սկսում է սերվերը՝ առանց ինտերակտիվ ելքի․

```sh
neo --ci run
```

Փոքր հոսթավորված տեղակայման դեպքում գործընթացի վերահսկիչը կազմաձևեք այդ գործարկման հրամանով և նախագծի գրացուցակով որպես աշխատանքային գրացուցակ։ Ստորև `/opt/mug-shop`-ում տեղադրված ծրագրի **systemd unit-ի ձևանմուշն** է։ Neo-ի ուղին փոխարինեք սպասարկող հաշվի համար `command -v neo`-ի արդյունքով և համոզվեք, որ դրա `PATH`-ը պարունակում է այդ հաշվի Nix-ի ու Git-ի գործարկվողները․

```ini
[Unit]
Description=Mug shop application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=mug-shop
WorkingDirectory=/opt/mug-shop
EnvironmentFile=/etc/mug-shop.env
Environment=PATH=/home/mug-shop/.nix-profile/bin:/nix/var/nix/profiles/default/bin:/usr/local/bin:/usr/bin:/bin
ExecStart=/usr/local/bin/neo --ci run
Restart=on-failure
RestartSec=5
KillMode=control-group

[Install]
WantedBy=multi-user.target
```

Հաշվին պետք է հասանելի լինեն նախագիծն ու ստեղծված կառուցման գրացուցակները։ `/etc/mug-shop.env`-ը ստեղծեք հոսթի պաշտպանված կազմաձևման մեխանիզմով՝ օգտագործելով ստորև դաշտերը։ Հարմարեցված unit-ը պահեք `/etc/systemd/system/mug-shop.service`-ում, ապա օգտագործեք հոսթի վարչական հաշիվը․

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now mug-shop
sudo journalctl -u mug-shop -f
```

Այս գործարկման ճանապարհը վերագործարկման ժամանակ դեռ CLI-ով հաշտեցնում ու կառուցում է. այն գործիքաշարի կարիք ունի և կարող է ցանցային մուտք պահանջել։ Սա նախապես կառուցված նվազագույն գործարկման պատկեր չէ։ Տարբերակն ու կախվածությունները պահեք ֆիքսված, երթևեկություն ընդունելուց առաջ նախապես կառուցեք և ստուգեք կանգնեցում/վերագործարկումը։ Ավելի մասնագիտացված փաթեթավորումը տեղակայման ընտրություն է. CLI-ն պատրաստի ծրագիր-կոնտեյներ կամ ամպային միջավայր չի ստեղծում։

## Տրամադրեք գործարկման ռեսուրսները

Տարբերակը սկսելուց առաջ հաստատեք․

- [Պահպանումում](/hy/operate/persistence/) միացված `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_POOL_SIZE`, `DB_SSL_MODE` և `DB_SSL_ROOT_CERT` դաշտերը և հասանելի տվյալների բազան։
- Կայուն վերբեռնման ծավալ, եթե օգտագործում եք տեղային blob պահոց։
- Մատակարարի հավատարմագրեր և նույնականացման կազմաձևում՝ Ձեր տեղակայման գաղտնիքների մեխանիզմով տրամադրված։
- Փաստացի տրանսպորտին փոխանցված HTTP պորտը։
- Թողարկման համակարգում գրանցված տարբերակի նույնացուցիչ՝ մատյանների ու smoke թեստերի արդյունքների կողքին։

Ստուգեք ոչ միայն հայտարարությունը, այլև կապակցումը։ Հայտարարված պորտի դաշտը ազդեցություն չունի, եթե ծրագիրը այն չի օգտագործում սերվերը կազմաձևելու համար։

## Առանձնացրեք գործարկումը, կենդանությունն ու պատրաստականությունը

Ստանդարտ ծրագրային/վեբ կապակցմամբ․

| Հարցում | Իմաստ | Սովորական պատասխան |
| --- | --- | --- |
| `GET /health` | HTTP գործընթացը պատասխանում է | `200` |
| `GET /ready` | Գրանցված հարցումների պրոյեկցիաները հասել են վերջին փոփոխությանը | Պատրաստ լինելու դեպքում `200`, վերակառուցման կամ ձախողման ընթացքում `503` |

Առողջությունը չի ապացուցում, որ վճարման մատակարարն աշխատում է։ Պատրաստականությունը չի հավաստում յուրաքանչյուր բիզնեսային աշխատանքային հոսք։ Անհատական կապակցումը կարող է փոխել կամ բաց թողնել այս երթուղիները. ստուգեք փաստացի տարբերակը։

Kubernetes-ի համար սա **ցուցադրական ստուգման հատված** է, ոչ թե ամբողջական տեղակայման մանիֆեստ․

```yaml
startupProbe:
  httpGet:
    path: /health
    port: 8080
  periodSeconds: 5
  failureThreshold: 12
  timeoutSeconds: 2
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
  timeoutSeconds: 2
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 5
  failureThreshold: 3
  timeoutSeconds: 2
```

Օրինակային գործարկման բյուջեն `5 × 12 = 60` վայրկյան է։ Այն չափեք սահմանափակված գործընթացի և տվյալների բազայի սկզբնավորման համար։ Պատմական հարցումների վերարտադրումը կատարվում է կենդանի բաժանորդագրության գրանցումից հետո և չպետք է ուշացնի HTTP կապումը. պատրաստականությունը մնում է `503`, մինչև վերարտադրությունն ու դրան զուգահեռ եկած կենդանի իրադարձությունները չսպառվեն։ Գործարկման ստուգումը կայուն վիճակի կենդանության քաղաքականությանը թույլ չի տալիս բազմիցս սպանել սկզբնավորումը։

## Երթևեկությունը ընդունեք մտածված

1. Սկսեք տարբերակը՝ առանց օգտատերերի երթևեկությունն այնտեղ ուղարկելու։
2. Դիտարկեք `/health`-ը, ապա սպասեք, մինչև `/ready`-ը վերադարձնի `200`։
3. Ներկայացուցչական smoke թեստերն աշխատեցրեք **նոր տարբերակի նույնականացուցիչի** դեմ։
4. Ընդունեք երթևեկությունը և դիտարկեք ձախողումները, ուշացումը և բիզնեսային արդյունքները։

Ընդհանուր ingress-ը դեռ կարող է հասնել հին տարբերակին։ Դրա հաջող պատասխանը միայնակ չի ապացուցում, որ նոր տարբերակն աշխատում է։

`mug-shop`-ի համար ստեղծեք Cart, ավելացրեք թույլատրելի քանակ, ուսումնասիրեք դրա Cart-ի ու Stock-ի հարցման արդյունքները, ապա ստուգեք, որ զրոն մերժվում է։ [HTTP և frontend-ներ](/hy/build/http-and-frontend/) բաժնի հարցման ձևերն օգտագործեք նոր տարբերակի դեմ։ Արտաքին արդյունքը ստուգեք միայն այն դեպքում, երբ այդ ինտեգրումն իրականացրել եք՝ վերահսկվող մատակարարի միջավայրում։ Ներկառուցված ստուգումները ավելի նեղ փաստեր են հաստատում։ Այս ուղեցույցը ամբողջական ամպային, վճարման կամ AI տեղակայում չի տրամադրում և չի հավաստում։

8080 պորտով տեղային օրինակին․

```sh
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/ready
```

## Հաշվի առեք ընթացիկ շահագործման սահմանները

Postgres-ի հաճախորդներն օգտագործում են սահմանափակված լողավազաններ։ `LISTEN/NOTIFY`-ի listener կապերին պետք է ուղղակի, նստաշրջանը պահպանող կապ. դրանք transaction-mode PgBouncer-ով մի ուղղեք։ Pooled/direct endpoint-ների բաժանված աջակցությունն ու Neon scale-to-zero-ի մշակումը հետևվում են [#857 խնդրում](https://github.com/neohaskell/NeoHaskell/issues/857)։

Ակտիվ վերակառուցման ընթացքում SIGTERM-ի չեղարկումն ու checkpoint-ի մաքրումը շարունակում են հետևվել [#662 խնդրում](https://github.com/neohaskell/NeoHaskell/issues/662)։ Մի երկարացրեք ավարտման արտոնյալ ժամանակը անվերջ՝ վերարտադրմանը սպասելու համար։ Staging-ում վարժվեք ընդհատմանը և վերագործարկմանը, իսկ երթևեկությունը վերահսկելու համար օգտագործեք պատրաստականության պայմանագիրը։
