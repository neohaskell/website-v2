Պահանջները փոխվում են, մինչ առկա տվյալները պահպանում են իրենց իմաստը։ Նոր կոդը պետք է սպասարկի երկու իրողությունները։ Օրինակ՝ նոր գրառումներին ընտրովի տեքստ ավելացնելը չպետք է ձևացնի, թե նախկին օգտատերերն էլ էին այն տրամադրել։ Էլեկտրոնային առևտրի ուսումնական նախագծում փորձեք նոր ստեղծվող զամբյուղներին կամընտրական նշում ավելացնել, մինչ հին զամբյուղները պահպանում են այդ տեղեկության բացահայտ բացակայությունը։

Իրադարձությունների աղբյուրավորմամբ համակարգը պատմությունը բացահայտ է դարձնում։ Դա արժեքավոր է որոշումները բացատրելու համար և ստեղծում է մեկ պատասխանատվություն. ապագա կոդը դեռ պետք է հասկանա արդեն ընդունած փաստերը։

## Կոդից առաջ դասակարգեք փոփոխությունը

| Փոփոխություն | Հիմնական հարց |
| --- | --- |
| Ապագա գործողությունների նոր կանոն | Նոր որոշումից առաջ առկա վիճակը դեռ կարելի՞ է վերակառուցել։ |
| Իրադարձության նոր տեսակ | Հին ու նոր ծրագրի տարբերակները կարո՞ղ են կարդալ այն պատմությունները, որոնց կհանդիպեն։ |
| Պահված իրադարձության ձևի փոփոխություն | Ինչպե՞ս է պատմական JSON-ը մնալու վերծանելի և իմաստալից։ |
| Նոր կամ փոխված հարցում | Այն կարո՞ղ է ճիշտ վերակառուցվել բոլոր աջակցվող պատմություններից։ |
| Նոր արտաքին աշխատանքային հոսք | Թողարկումը կամ վերարտադրումը կարո՞ղ է կրկնել արտաքին գործողությունը։ |

Օգտագործեք [իրադարձությունների մոդելավորումը](/hy/start/event-modeling/) և [տեսողական IDE-ն](/hy/getting-started/visual-ide/)՝ ազդված սպառողներին գտնելու համար։ Մեկ իրադարձություն փոխելը կարող է տարբեր ձևով ազդել հրամանների, հարցումների և ինտեգրումների վրա։

## Պահպանեք պատմական ֆիքսված օրինակ

Փոփոխությունն ընդունելուց առաջ Ձեր թեստերում պահեք փոքր ներկայացուցչական պատմություն։ Ներառեք վարքագիծ փոփոխությունից առաջ և հետո, ինչպես նաև մերժված գործողություն։ Էլեկտրոնային առևտրի օրինակի համար օգտագործեք հին զամբյուղ և նշումով նոր զամբյուղ։ Ստուգեք, որ նոր կոդը․

- Վերծանում է հին և նոր պահպանված իրադարձությունները։
- Յուրաքանչյուրի համար վերակառուցում է նախատեսված վիճակը։
- Նոր կանոնը կիրառում է միայն այնտեղ, որտեղ դա բիզնեսն է նախատեսում։
- Վերարտադրումից հետո կառուցում է սպասվող հարցման արդյունքները։
- Վարժության ընթացքում արտաքին ազդեցությունը չի կրկնում։

JSON-ի տիպի հաջող կոմպիլյացիան չի ապացուցում, որ պատմական JSON-ը հաջող վերծանվում է։ Պատմական դեպքերը պահեք `Shop.Cart`-ի թեստերի կողքին և `mug-shop`-ից `neo test`-ը գործարկեք միանգամյա տվյալների բազայի դեմ։ Գործարկվող ապացույցի համար հետևեք [թեստավորմանը](/hy/build/testing/)։

## Տիրույթի lock-ը օգտագործեք որպես հիշեցում

Ստեղծված ծրագրի արմատից CLI-ն կարող է lock անել հայտնաբերված տիրույթի ֆայլերը․

```sh
neo lock --all
neo lock install
neo lock check
```

Lock անելուց առաջ ստուգեք `git status`-ը և մաքրեք կապ չունեցող staged աշխատանքը։ Lock-ը staged է անում ընտրված ֆայլերն ու `.locked-files`-ը և ստեղծում Git commit. արդեն staged բովանդակությունը կարող է ներառվել։ `neo lock install`-ը գրում է pre-commit hook-ի ուղին, այնպես որ առկա hook-ը պահպանեք և գիտակցված միացրեք։

Մանիֆեստը `.locked-files`-ն է, իսկ տեղադրված Git hook-ը և `neo build`-ը ստուգում են lock արված ուղիների փոփոխությունները։ `neo lock check`-ը ներառում է staged, unstaged և untracked փոփոխությունները։ Lock-ը օգնում է հետևանքային խմբագրումը դարձնել գիտակցված։ Այն չի հաստատում սխեմայի համատեղելիությունը և միգրացիայի իրականացում չի տրամադրում։

`neo build --skip-lock-check`-ը գոյություն ունի կառուցման ժամանակ միտումնավոր շրջանցման համար։ Հիմքում ընկած պատմական համատեղելիության հարցը դիտարկեք առանձին. ստուգումը շրջանցելը դրան պատասխան չի տալիս։

## Մի ենթադրեք, որ հարցման փոփոխություններն իրենք են տեղափոխվում

Postgres-ի հարցումների պահոցն ու բաժանորդը տրամադրում են hash/checkpoint գործողություններ։ Դրանց գոյությունը չի նշանակում, որ հարցման ֆունկցիայի յուրաքանչյուր փոփոխություն ինքնաբերաբար հայտնաբերվում կամ տեղափոխվում է, կամ որ ծրագրի սովորական գործարկումը միացնում է checkpoint-ի շարունակումը։ Իրական ծրագրային կապակցմամբ պլանավորեք ու թեստավորեք վերակառուցումը։

Անհամատեղելի պահպանված հարցման սխեմայի դեպքում անցումը դարձրեք բացահայտ։ Հեղինակավոր իրադարձությունների պատմությունը պահեք անփոփոխ և վերականգնված պատճենի վրա փորձարկեք անցումը։ Ներառեք՝ արդյոք նախորդ տարբերակը կարող է աշխատել ստացված տվյալների դեմ. տվյալների փոփոխությունից հետո «վերադարձնել բինարը» միշտ բավարար չէ։

## Վարժություն․ Cart-ի նշումներ ավելացրեք

Էլեկտրոնային առևտրի ուսումնական նախագծում խնդրեք գործակալին առաջարկել, թե նոր զամբյուղները ինչպես են ստանում ընտրովի նշում և հին զամբյուղներն ինչ են ցուցադրում։ Կոդն ընդունելուց առաջ ինքներդ բացատրեք հին պատմության վարքագիծը։
