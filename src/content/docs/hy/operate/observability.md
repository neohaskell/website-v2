Օգտատերը հայտնում է, որ ընդունված փոփոխությունը տեսանելի չէ։ Պետք է տարբերակել մերժված հարցումը, ուշացած ներկայացումը, սխալ հաշիվը և արտաքին ձախողումը։ «Սերվերը աշխատում է» այդ հարցի միայն մի փոքր մասին է պատասխանում։ Էլեկտրոնային առևտրի ուսումնական նախագծում հաղորդումը կարող է լինել՝ «Ապրանք ավելացրի, բայց զամբյուղս չի փոխվել»։

Ծրագիրը դիտարկեք շերտերով՝ գործընթաց, պահպանված փաստեր, ներկայացումներ և արտաքին արդյունքներ։ Յուրաքանչյուր ահազանգին տվեք հարց, որի հիման վրա մարդը կարող է գործել։

## Սկսեք երկու ներկառուցված ազդանշաններից

8080 պորտում լռելյայն վեբ կապակցմամբ ծրագիր օգտագործելիս․

```sh
curl -i http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/ready
```

Պատրաստականության պատասխանը համակցված վիճակ է․

```json
{"status":"ready"}
```

Հասնելու ընթացքում այն `{"status":"rebuilding"}` է՝ HTTP `503`-ով։ Ձախողումը նույնպես վերադարձնում է `503`՝ `status`-ը `failed` և `reason` պարունակելով։ Ընթացիկ HTTP պատասխանը յուրաքանչյուր հարցման ուշացման արժեքների վահանակ չէ։

Առողջ գործընթացը կարող է վերակառուցել հարցումները։ Պատրաստ գործընթացը դեռ կարող է հանդիպել արտաքին մատակարարի խափանման։ Բիզնեսային գործողությունը դիտարկեք առանձին։

## Կարդացեք ծրագրի մատյանները

`Log` մոդուլը JSON գրառումներ է գրում ստանդարտ ելք՝ `time`, `level` և `message` դաշտերով, ինչպես նաև կանչի տեղանքի և շրջանակի սահմանների դաշտերով, երբ դրանք հասանելի են։ Ձեր հոսթը պետք է հավաքի, պահի և որոնելի դարձնի այդ գրառումները։

Տեղային ախտորոշիչ գործարկման համար․

```sh
LOG_LEVEL=debug neo run
```

Լռելյայն մակարդակը `Info` է։ Իրականացումը ճանաչում է debug, info, warn, error և critical գրությունները՝ փոքրատառ, Title Case կամ մեծատառ ձևերով։ Միջավայրի փոփոխությունը նոր գործընթաց է պահանջում։ `neo --verbose`-ը կառավարում է CLI-ի խոսունությունը, իսկ `LOG_LEVEL`-ը՝ ծրագրի մատյանագրումը։

Շրջանակի մատյանները նույնացնում են հարցումների վերարտադրման առաջընթացն ու ձախողումները։ Առաջընթացի հաղորդագրությունների տեքստում կան `events_replayed`, `lag_from_head` և `duration_seconds`։ Մի ենթադրեք, որ դրանք առանձին արտահանված չափիչներ են։ Cold-start թեստը ստուգում է առաջընթացի հաղորդագրություններն ու ձախողման մատյաններում հարցման ինքնությունն ու դիրքը՝ առանց իրադարձության բեռը արտահոսելու։

[Ուսումնասիրեք մատյանագրման իրականացումը](https://github.com/neohaskell/NeoHaskell/blob/main/core/core/Log.hs) և [cold-start ստուգումը](https://github.com/neohaskell/NeoHaskell/blob/main/testbed/scripts/cold-start-readiness.sh)։

## Հետևեք մեկ գործողության ամբողջ համակարգով

Գրանցեք տարբերակը, մոտավոր ժամանակը և գործողության կամ էության անվտանգ նույնացուցիչը։ Պահեք Ձեր `mug-shop` հարցման վերադարձած Cart-ի նույնացուցիչը։ Ապա հարցրեք․

1. Հրամանը հաջողվե՞ց, թե՞ մերժում հաղորդեց։
2. Պահպանված պատմությունը պարունակո՞ւմ է սպասված փաստը։
3. Համապատասխան հարցումը հասե՞լ է վերջին փոփոխությանը, և ընթերցողը լիազորվա՞ծ է այն տեսնել։
4. Եթե ինտեգրում էր սպասվում, ի՞նչ արդյունք հաղորդեց այն։
5. Արդյունքը դարձա՞վ հաջորդ բիզնեսային փաստ, թե՞ հաջորդող աշխատանքը դեռ սպասում է։

Օգտագործեք [IDE-ի գրաֆը](/hy/getting-started/visual-ide/)՝ պատասխանատու հրամանը, իրադարձությունը, հարցումն ու ինտեգրումը գտնելու համար։ Այն բացատրում է սկզբնաղբյուրի հարաբերությունները, բայց չի ցույց տալիս գործող տվյալների բազայի պատմությունը և չի փոխարինում արտադրական դիտարկմանը։

Ընտրեք անվտանգ ախտորոշիչ նույնացուցիչներ։ Անձնական հասցեները, մուտքի token-ները, վերբեռնված փաստաթղթերն ու մատակարարի ամբողջական պատասխանները սովորաբար չեն պատկանում սովորական մատյաններին։ Տիպավորված կազմաձևման դաշտի թաքցնելը չի թաքցնում կամայական տեքստը, որը հետո մատյանում եք գրում։

## Վարժություն․ կանաչ գործընթաց՝ սպասող արդյունքով

`mug-shop`-ին արտաքին ինտեգրում ավելացնելուց հետո նախագծեք staging սցենար, որտեղ գործարկող փոփոխությունն ընդունվում է, բայց արտաքին հաստատումը ուշանում է։ Գործարկելուց առաջ նկարագրեք հաճախորդի տեսանելի կարգավիճակն ու օպերատորի տեսանելի ազդանշանը։
