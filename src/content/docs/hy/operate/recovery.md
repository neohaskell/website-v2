Տվյալների բազայի վերականգնումը ծրագրի մեկ մասն է վերականգնում։ Արտաքին համակարգերը կարող են դեռ հիշել աշխատանք, որը վերականգնված պատճենը չունի։ Վերականգնումը պետք է հաշվի առնի երկու պատմություններն էլ՝ առանց ավարտված գործողությունները կրկնելու կամ չավարտվածները լուռ մոռանալու։ Էլեկտրոնային առևտրի օրինակում դա կարող է նշանակել վճարումը հաշտեցնել՝ հաճախորդից նորից գումար չգանձելով։

Իրադարձությունների պատմությունն օգնում է վերակառուցել ծրագրի վիճակը։ Այն ինքնուրույն չի կարող վերստեղծել մետատվյալից կորած կցորդը կամ հակադարձել արտաքին վճարումը։ Վերականգնումը ներառում է ծրագրի շուրջ գտնվող ռեսուրսներն ու կազմակերպությունները։

## Նախ նույնացրեք ձախողվածը

| Դիտարկում | Ուսումնասիրեք՝ նախքան տվյալները փոխելը |
| --- | --- |
| `/health` պատասխանը բացակայում է | Գործընթացի գործարկում, կազմաձևում, տվյալների բազայի կապ, պորտի կապում |
| `/health`-ն աշխատում է, `/ready`-ը մնում է `503` | Հարցման վերակառուցման առաջընթաց կամ ձախողում |
| Պատրաստ է, բայց մեկ ներկայացում սխալ է | Պրոյեկցիայի տրամաբանություն, պահված իրադարձություններ, լիազորում, գործող տարբերակ |
| Ֆայլի մետատվյալը կա, ներբեռնումը ձախողվում է | Blob ծավալ և ֆայլի կյանքի ցիկլի վիճակ |
| Մատակարարը հաջողել է, ծրագրի արդյունքը անորոշ է | Մատակարարի գործարքի նույնություն և տեղային հաջորդող պատմություն |

Պահեք օգտակար մատյաններն ու ձախողված տարբերակի նույնացուցիչը։ Տվյալների կույր զրոյացումը կարող է ոչնչացնել այս դեպքերը տարբերելու համար անհրաժեշտ ապացույցը։

## Վերականգնումը փորձեք մեկուսացված միջավայրում

Նախ ավարտեք [պահպանումը](/hy/operate/persistence/). հիշողության մեջ սկզբնական պահոցը վերականգնվող պատմություն չունի։ Մինչև մարդիկ չհենվեն պահպանված տվյալների վրա, ներկայացուցչական գործողություններով փորձ կատարեք․

1. Ստեղծեք փոքր հայտնի պատմություն՝ ընդունված փոփոխություն, մերժված փոփոխություն և Ձեր աջակցած ցանկացած կցորդ կամ ինտեգրման արդյունք։ `mug-shop`-ում ստեղծեք Cart, ավելացրեք դրական քանակ և հաստատեք, որ զրոն մերժվում է։
2. Ձեր հոսթինգի միջավայրի տվյալների բազայի և ֆայլերի պահեստավորման ընթացակարգերով ստեղծեք պահուստային պատճեն։
3. Վերականգնեք մեկուսացված միջավայրում՝ արտադրական արտաքին ազդեցություններն անջատած կամ վերահսկվող թեստային endpoint-ներով փոխարինած։
4. Վերականգնված ծրագրի նախագծից `neo run` գործարկեք մեկուսացված պահեստի կարգավորմամբ և սպասեք `/ready`-ին։
5. Վերակառուցված էություններն ու ներկայացումները համեմատեք հայտնի պատմության հետ։
6. Ստուգեք կցորդների բայթերը, լիազորման սահմանները և չավարտված արտաքին աշխատանքի մշակումը։
7. Գրանցեք վերականգնման տևողությունը և պահուստում ներառված վերջին ընդունված գործողությունը։

Այդ փորձի մեջ ներառեք լքված վերբեռնումները։ Ֆայլերի վերբեռնման մոդուլն ունի մաքրման աշխատող, բայց ծրագրի սովորական գործարկումը ներկայումս այն չի սկսում։ Մի ենթադրեք, որ կազմաձևված ժամկետը կամ մաքրման միջակայքը ապացուցում է ժամկետանց բայթերի հեռացումը։

Վերջին երկու չափումները պատասխանում են բիզնեսային հարցերի՝ որքան ժամանակ կարող էր ծրագիրը անհասանելի լինել, և որքան վերջին աշխատանք կարող էր հաշտեցման կարիք ունենալ։ NeoHaskell-ը այդ շեմերը Ձեր փոխարեն չի ընտրում։

## Փորձեք տեղային Postgres տվյալների բազայով

[Պահպանման](/hy/operate/persistence/) Docker Compose տվյալների բազայի համար կարող եք փորձարկել միայն տվյալների բազայի վերականգնումը՝ բնօրինակը չփոխարինելով։ Հայտնի Cart ստեղծելուց ու դրա ամփոփումը գրանցելուց հետո կանգնեցրեք `neo run`-ը։ `mug-shop`-ից արտահանեք տեղային տվյալների բազան պաշտպանված պահուստային ֆայլի մեջ․

```sh
docker compose exec -T postgres pg_dump -U neohaskell -d neohaskell --format=custom > mug-shop.backup
```

Նույն տեղային Postgres ծառայության մեջ ստեղծեք նոր տվյալների բազա և վերականգնեք դրա մեջ․

```sh
docker compose exec -T postgres createdb -U neohaskell mug_shop_restore
docker compose exec -T postgres pg_restore -U neohaskell --dbname=mug_shop_restore < mug-shop.backup
```

`createdb`-ը պետք է ձախողի, եթե այդ վերականգնման տվյալների բազան արդեն գոյություն ունի։ Հետագա փորձի համար ընտրեք նոր անուն՝ չուսումնասիրած տվյալները փոխարինելու փոխարեն։ Նախքան ծրագիրը սկսելը ստուգեք, որ երկու հրամաններն էլ հաջողվել են։

Եթե իրական ելքային ինտեգրումներ եք ավելացրել, նախ օգտագործեք վերահսկվող մատակարարի endpoint-ներ կամ մեկուսացված ծրագրային տարբերակում հեռացրեք դրանց գրանցումները։ Այնուհետև Ձեր ավելացրած կազմաձևմամբ ընտրեք վերականգնված տվյալների բազան․

```sh
DB_NAME=mug_shop_restore DB_PASSWORD=neohaskell neo run
```

Պահեք տեղային տվյալների բազայի համար օգտագործած `DB_PORT`-ը, եթե այն փոխել եք։ Մեկ այլ տերմինալում ստուգեք `/ready`-ը և նույն նույնացուցիչով ստացեք սկզբնական Cart-ի ամփոփումը՝ օգտագործելով [HTTP և frontend-ներ](/hy/build/http-and-frontend/) բաժնի հարցումները։ Համեմատեք այն՝ նախքան թեստեր գործարկելը կամ նոր տվյալներ ստեղծելը։ Պահուստը պարունակում է տվյալների բազայի տվյալներ, ներառյալ հնարավոր զգայուն իրադարձությունների պատմությունը. այն պահեք համապատասխան մուտքի պաշտպանությամբ։

Այս ընթացակարգը վերականգնում է իրադարձությունների տվյալների բազան։ Վերբեռնված բայթերին և մատակարարի առանձին հավատարմագրերի պահոցներին պետք են իրենց պահուստները։ `pg_restore`-ի հաջողությունը ծրագրի ստուգումների սկիզբն է, ոչ թե դրանց փոխարինումը։

## Հասկացեք վերակառուցման սահմանը

Հարցումների բաժանորդը կարող է իրադարձություններից վերակառուցել ներկայացումներ և տրամադրում է պատրաստականության վիճակներ։ Կան ցածր մակարդակի `rebuildAllAsync`, `rebuildFrom` և checkpoint API-ներ. դրանք ծրագրի/շրջանակի API-ներ են, ոչ թե `neo rebuild` հրաման։

Սովորական `Application` կապակցումը ներկայումս ստեղծում է `Subscriber.new`՝ առանց checkpoint-ի պահոցը ինքնաբերաբար միացնելու։ Կայուն հարցման տողերը միայնակ checkpoint-ով շարունակումը չեն ապացուցում։ Թեստավորեք Ձեր օգտագործած ստույգ պահոցը, գործարկման ճանապարհը և պրոյեկցիայի տրամաբանությունը. տե՛ս [պահպանումը](/hy/operate/persistence/)։

Postgres-ի հարցումների պահոցը իր աղյուսակը ստեղծում է, եթե այն բացակայում է։ Դա ընդհանուր սխեմայի միգրացիայի ծառայություն չէ։ Անհամատեղելի աղյուսակի սխեմայով առկա տեղադրումներին պետք է բացահայտ միգրացիայի ծրագիր։

## Արտաքին աշխատանքը վերականգնեք նույնացուցիչով

Պահեք բավարար տեղեկություն՝ ծրագրի գործողությունը արտաքին համապատասխան գործողության հետ կապելու համար։ Էլեկտրոնային առևտրի ապագա վճարման աշխատանքային հոսքի դեպքում դա նշանակում է պատվերը կապել մատակարարի գործողության հետ։ Որոշեք, թե ինչ է տեղի ունենում, երբ մատակարարը ընդունում է հարցումը, բայց կապը կտրվում է նախքան պատասխանի հասնելը։

Սա Ձեր վճարման ադապտերի նախագծային պահանջն է, ոչ թե պնդում, որ NeoHaskell-ն ուղարկում է ամբողջական վճարման/հաշտեցման համակարգ։ Մատակարարի աջակցած idempotency-ն և կարգավիճակի որոնումը կարող են տեղեկացնել նախագծմանը, բայց դրանց ճշգրիտ երաշխիքները պետք է ստուգվեն ընտրված մատակարարի դեմ։

## Վարժություն․ ընդհատեք փոխանցումը

Վերևի վճարման նախագծի համար կազմակերպեք վերահսկվող թեստ, որտեղ արտաքին գործողությունը հաջողվում է, բայց տեղային հաստատումն ընդհատվում է։ Վերագործարկեք և ուսումնասիրեք արդյունքը։ Նույն մեթոդը կիրառեք Ձեր ծրագրի կատարած արտաքին ազդեցություններից մեկի վրա։

<details>
<summary>Ինչ ստուգել</summary>

Հաճախորդը չպետք է երկրորդ գանձում ստանա միայն այն պատճառով, որ առաջին պատասխանը կորել է։ Ծրագիրը պետք է հասնի ճիշտ վերջնական վիճակի կամ բացահայտի հաշտելի սպասման վիճակ։ Ժամանակի ավարտը անորոշ պատասխանի ապացույց է, ոչ թե այն բանի, որ մատակարարը ոչինչ չի արել։
