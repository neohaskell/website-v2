Ձեր ծրագիրն հարցում է ուղարկում մեկ այլ ծառայության, բայց կապը փակվում է նախքան պատասխանի հասնելը։ Ծառայությունը մերժե՞ց աշխատանքը, թե՞ պատասխանը կորավ աշխատանքն ավարտելուց հետո։ HTTP ինտեգրումը պետք է մշակի այս անորոշությունը սովորական հաջողության և ձախողման հետ միասին։

NeoHaskell-ը տրամադրում է հարցումների մեխանիզմը, իսկ Ձեր ծրագիրը մեկնաբանում է մատակարարի պատասխանը և որոշում, թե որ գործողությունները կարելի է անվտանգ կրկնել։ Կսկսենք կարգավիճակի որոնումից, ապա էլեկտրոնային առևտրի նախագծում նմանակված վճարմամբ կվարժվենք ավելի հետևանքային փոխանցման վրա։

Նախապայմաններ՝ [ինտեգրման կյանքի ցիկլ](/hy/connect/) և [կազմաձևում](/hy/build/configuration/)։

## Մատակարարի կանչը տեղադրեք Ձեր նախագծում

Շարունակեք Ձեր `mug-shop` գրացուցակից և ավարտեք [ինտեգրման կարգավորումը](/hy/connect/#prepare-your-project)։ Արձանագրության օգնականը պահեք `src/Shop/Integrations/ProviderStatus.hs`-ում։ Այն կանչելու պահը ընտրող Cart-ի կողմի մշակիչը տեղադրեք `src/Shop/Cart/Integrations/`-ի տակ՝ հետևելով ամբողջական [մշակիչի մոդուլին](/hy/connect/workflows/#create-the-outbound-integration)։

Հարցումն ավելացնելուց առաջ սահմանեք կարգավիճակի արդյունքը գրանցող հրամանը և համապատասխան ծառայությունում գրանցեք այն `InternalTransport`-ով։ Դրան տվեք հաջողված, մերժված և չորոշված արդյունքներ՝ կայուն գործողության նույնացուցիչով։ Հետևյալ ֆակտորինը այդ հնարավորության հարցման մասն է. callback-ները արդյունքը կապում են Ձեր ծրագրի հրամանին։

## Կարդալով սովորեք հարցման ձևը

Սկսեք մատակարարի կարգավիճակը կարդացող գործողությունից։ Այս **մասնակի ինտեգրման ֆակտորինում** `statusUrl`, `recordReply` և `recordFailure`-ը Ձեր ծրագրի տրամադրած արժեքներն են։ Երկու callback-ներն էլ վերադարձնում են մեկ գրանցված հրամանի տիպ։

```haskell
-- Inside the event handler's Integration.batch:
Integration.outbound Http.Request
  { method = Http.GET
  , url = statusUrl
  , headers = []
  , body = Http.noBody
  , onSuccess = recordReply
  , onError = Just recordFailure
  , auth = Http.Bearer "${SHOP_PROVIDER_TOKEN}"
  , retry = Http.defaultRetry
  , timeoutSeconds = 15
  }
```

URL-ն ու վերնագրերի արժեքները աջակցում են միջավայրի փոխարինման։ Նույնականացումն աջակցում է `NoAuth`, `Bearer`, `Basic` և անունով վերնագրի `ApiKey`։ Միջավայրի բացակայող փոփոխականները նախապատրաստման ընթացքում առաջացնում են ինտեգրման նույնականացման սխալ. պարտադիր չէ, որ դրանք հասնեն `onError`-ին։

`Http.Response`-ը կրում է `statusCode`, JSON `body` և պատասխանի `headers`։ **Callback-ում ստուգեք կարգավիճակը։** `onSuccess` անունով callback-ը պատասխանի ճանապարհն է, ոչ թե հայտարարություն այն մասին, որ մատակարարն ընդունել է բիզնեսային գործողությունը։

Հարցման մարմինների համար օգտագործեք `Http.json`, `Http.form`, `Http.raw` կամ `Http.noBody`։ Ընթացիկ ադապտերը JSON է աջակցում POST, PUT և PATCH մեթոդների համար, իսկ form և raw մարմինները՝ POST-ի։ GET և DELETE մեթոդները տրամադրված մարմինը չեն օգտագործում։ Պատասխանները վերծանվում են JSON հաճախորդի միջոցով, ուստի դատարկ կամ ոչ JSON բովանդակություն վերադարձնող մատակարարը պահանջում է բացահայտ համատեղելիության թեստավորում կամ անհատական ադապտեր։

## HTTP-ից անցեք վճարման իմաստին

Ուսումնական նախագծում վճարումը մոդելավորելու համար օգտագործեք թեստային մատակարար․

1. Գրանցեք ծրագրի վճարման փորձը՝ կայուն նույնացուցիչով և պատվերի գումարով/արժույթով։
2. Մատակարարի հարցումը կառուցեք վստահելի ծրագրի վիճակից։
3. Եթե մատակարարն աջակցում է, օգտագործեք դրա փաստաթղթավորված idempotency մեխանիզմը։ Սա մատակարարին հատուկ աշխատանք է պահանջում։
4. Վերծանեք ու վավերացրեք պատասխանը՝ պահելով դրա գործողության նույնացուցիչը։
5. Հրամաններով գրանցեք հաստատված, մերժված կամ չորոշված արդյունքները։
6. Չորոշված փորձերը հաշտեցրեք՝ մատակարարին հարցնելով դրանց փաստացի կարգավիճակը։

Սրանք նախագծային քայլեր են, ոչ թե տրամադրված վճարման ադապտեր։ Մատակարարի ընթացիկ API-ն ընտրեք ու ստուգեք առանձին։ Հաճախորդի հաջողության էջ վերադառնալն ինքնին վճարման հաստատման ապացույց չէ։

Մատակարարի callback-ների դեպքում մուտքային տվյալները հրամանի վերածելուց առաջ վավերացրեք իսկությունը։ Ընդհանուր մուտքային աշխատողի աբստրակցիան Ձեզ համար վճարման մատակարարի ստորագրության ստուգիչ կամ webhook երթուղի չի տրամադրում։

## Հասկացեք կրկնության ընթացիկ սահմանը

Սկզբնաղբյուրի `Retry` գրառումը փաստաթղթավորում է `maxAttempts`-ը՝ առաջին փորձը ներառած։ Ընթացիկ կատարողը կրկին փորձելուց առաջ համեմատում է `attempt <= maxAttempts` պայմանը, ինչը կարող է թույլ տալ մեկ հավելյալ փորձ։ Ուստի դրա `noRetry` նախադրվածը չպետք է դիտարկել որպես երաշխիք, որ ձախողված հարցումը ուղարկվում է միայն մեկ անգամ։

Կատարողը հարցման սխալները նույնպես կրկին փորձում է իր կարգավիճակի կոդերի ցանկից առանձին։ Մի եզրակացրեք, որ միայն թվարկված կարգավիճակները կարող են բերել ևս մեկ հարցման։ Իրականացման այս սահմանափակումները կարևոր են գանձումների, վճարովի AI հարցումների և պիտակների գնումների համար. այդ գործողություններն ընդունելուց առաջ վերահսկվող endpoint-ով ստուգեք հարցումների փաստացի քանակը։

Ժամանակի ավարտը նույնպես չի ապացուցում, որ հեռավոր կողմը ոչինչ չի արել։ Պահեք չորոշված արդյունք, մինչև ապացույց ունենաք։

## Գործարկեք վերահսկվող կարգավիճակի ստուգում

Օգնականն ու callback-ի հրամանը ավելացնելուց հետո `mug-shop`-ից գործարկեք `neo build`։ `tests/` հավաքածուում `neo test`-ով ստուգեք կարգավիճակի քարտեզավորումը՝ ներառելով վավեր JSON սխալի պատասխանը։ `neo run`-ով սկսեք Ձեր ծրագիրը, հրամանով գործարկեք հարցումը և ուսումնասիրեք ստացված կարգավիճակի հարցումը։ Վճարման հավատարմագրերը միացնելուց առաջ օգտագործեք վերահսկվող endpoint։

## Վարժություն․ վճարման կորած պատասխան

Նկարագրեք ուսումնական ծրագրի վիճակը ժամանակի ավարտից հետո, թե ինչ է ցույց տալիս դրա էկրանը և ինչպես կլուծեիք անորոշությունը։ Ապա մտածեք, թե որ մասերն են կիրառվում նաև օրացույցի գրառում ստեղծելիս կամ փաստաթուղթ մշակման ուղարկելիս։
