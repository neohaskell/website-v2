Երբ ծրագրին անհրաժեշտ է արտաքին API կամ NeoHaskell-ի կողմից չփաթեթավորված տեղային գործիք, կարող եք այդ աշխատանքը փաթեթավորել որպես վերօգտագործելի ինտեգրում։ Կանչողները նկարագրում են հարցումը փոքր գրառմամբ, իսկ արձանագրության մանրամասները, հավատարմագրերն ու պատասխանի վերլուծումը մնում են մեկ իրականացման մեջ։

Սա ճանապարհի ավելի խոր ճյուղն է։ Դուք պատասխանատվություն եք ստանձնում ցանցային կամ ենթագործընթացի վարքագծի, ինչպես նաև ծրագրի կանոնների համար։ Եթե մատակարարին համապատասխանում է, սկսեք [ընդհանուր HTTP-ից](/hy/connect/http-and-payments/)։

## Ադապտերին տուն տվեք mug-shop-ում

Շարունակեք աշխատել Ձեր `mug-shop` նախագծից։ Սկսեք, օրինակ, `src/Shop/Integrations/Parcel.hs` մոդուլից. երբ պատասխանատվությունները առանձին տեղերի կարիք ունեն, այն բաժանեք հարցման, պատասխանի և ներքին մոդուլների։ Ստացված մոդուլների ներմուծումները մնան `Shop.Integrations.Parcel` և դրա երեխաները։ Մատակարարին հատուկ կախվածությունները պահեք Ձեր նախագծի `neo.json`-ում՝ հետևելով [ինտեգրման կարգավորմանը](/hy/connect/#prepare-your-project)։

Օգտակար կառուցվածքը բաժանում է․

- Ճակատային մոդուլ, որը ներմուծում են API-ի կանչողները։
- Հարցման տիպ, որը պարունակում է մուտք, կազմաձևում և արդյունքի callback-ներ։
- Պատասխանի տիպ, որը պարունակում է օգտակար մատակարարի արդյունքը։
- Ներքին մոդուլ, որն իրականացնում կամ համադրում է կատարումը։

Հորինված ծանրոցի պիտակի մատակարարի դեպքում ծրագրի հարցումը կարող է ներառել առաքման հղում և փաթեթի մանրամասներ։ Սա նախագծային օրինակ է, ոչ թե տրամադրված առաքման API։ Որոշեք՝ որ կոնկրետ մատակարարի կարգավիճակն է հաստատում պիտակի ստեղծումը և ինչ անել, եթե պատասխանը կորչի։

Երկու callback-ներն էլ թող վերադարձնեն `InternalTransport`-ով հայտարարված մեկ հրամանի տիպ։ Թող կանչողը callback-ների մեջ պահի իր աշխատանքային հոսքի նույնացուցիչը։ Խուսափեք վերօգտագործելի ինտեգրումը որոշակի ծրագրի էության հետ կապելուց։

## Հասկացեք կատարման պայմանագիրը

`Integration.ToAction`-ը հարցումը վերածում է `Action`-ի։ Դրա հիմնական մեթոդն է․

```haskell
class ToAction config where
  toAction :: config -> Action
```

Գործողությունը ստանում է `ActionContext` և վերադարձնում `Task IntegrationError (Maybe CommandPayload)`։ Հաջող աշխատանքը կարող է օգտագործել `Integration.emitCommand`, իսկ առանց հաջորդող հրամանի աշխատանքը՝ `Integration.noCommand`։

Դուք արդեն օգտագործել եք `Integration.Command.Emit`-ը [Cart-ի և Stock-ի համակարգման](/hy/connect/workflows/) մեջ։ Այն արտաքին գործողություն չի կատարում, այլ արտածում է կազմաձևված հրամանը։ Ձեր Parcel ադապտերը արդյունքի հրամանն ընտրելուց առաջ արձանագրության աշխատանք կավելացնի։

HTTP մատակարարների համար հարցումների մեխանիզմը կրկնօրինակելու փոխարեն համադրեք `Integration.Http.Request`-ը։ OpenRouter-ի `toHttpRequest`-ը կոնկրետ օրինակ է. այն կառուցում է endpoint-ը, մարմինը, վերնագրերը, նույնականացումը, callback-ները և ժամանակի սահմանը, ապա փոխանցում կատարումը։ Մատակարարի համատեղելիության թեստերում պահեք [ներկայիս կրկնության վարքագիծը](/hy/connect/http-and-payments/#understand-the-current-retry-boundary)։

## Ընտրեք սխալներ, որոնք օգնում են կանչողին վերականգնվել

Գործարկման սխալների բառապաշարը ներառում է `NetworkError`, `AuthenticationError`, `ValidationError`, `RateLimited`, `PermanentFailure` և `UnexpectedError`։

Որոշեք, թե որ ձախողումներն են դառնում արդյունքի հրաման, իսկ որոնք են ձախողում նախապատրաստումը՝ նախքան հարցման կատարումը։ Այդ սահմանը բացատրեք Ձեր ինտեգրման փաստաթղթերում։ Callback-ի սպասող կանչողին պետք է գործառնական միջոց՝ այդ callback-ը շրջանցող ձախողումները հայտնաբերելու համար։

Մատակարարի կամայական մարմինները մի վերադարձրեք որպես սխալի տողեր։ Դրանք կարող են պարունակել հաճախորդի տվյալներ կամ հավատարմագրեր։ Պահպանեք անվտանգ բացատրություն և հարաբերակցության նույնացուցիչ, երբ մատակարարն այն աջակցում է։

## Երկարակյաց ռեսուրսները կայուն վիճակից առանձին պահեք

Եթե ինտեգրմանը պետք է մեկ էության համար թանկ ռեսուրս, `Integration.Lifecycle.OutboundConfig state`-ը տրամադրում է․

```haskell
initialize :: StreamId -> Task Text state
processEvent :: state -> Event Json.Value -> Task Text (Array Integration.CommandPayload)
cleanup :: state -> Task Text Unit
```

Սրանք կյանքի ցիկլի տիպից առանձնացված **դաշտերի ստորագրություններ** են։ Աշխատողները սկզբնավորում են ռեսուրսները, մշակում իրադարձությունները և մաքրում են կանգնեցվելիս կամ հեռացվելիս։ Ավելի ուշ իրադարձությունը կարող է նոր աշխատող ստեղծել, ուստի այս վիճակը կայուն աշխատանքային հոսքի պատմություն չէ։

Աշխատողը կարող է պահել `ConcurrentVar`, կապի բռնակ կամ մեկ այլ ժամանակավոր ռեսուրս։ Աշխատողը վերաստեղծվելիս արժեքները կարող են զրոյացվել։ Չավարտված աշխատանքը պահեք կայուն ծրագրի վիճակում, ոչ միայն այդ փոփոխականում։ `mug-shop`-ում «պիտակի գնումը դեռ սպասում է» նման վիճակ է։

`shipmentLifecycle`-ը իրականացնելուց հետո այն և `CartEntity`-ը հասանելի դարձրեք `src/App.hs`-ում։ Այս **գրանցման հատվածը** այն կապում է Cart-ի իրադարձություններին․

```haskell
    |> Application.withOutboundLifecycle @() @CartEntity (\_ -> shipmentLifecycle)
```

`shipmentLifecycle`-ը պետք է լինի Ձեր `OutboundConfig state` արժեքը՝ վերևի երեք ֆունկցիաներով. այն տրամադրված Parcel իրականացում չէ։ Այս շերտն օգտագործեք միայն այն դեպքում, երբ դրա ռեսուրսի կյանքի ցիկլը օգտակար է։ Մատակարարների հարցումների մեծ մասը կարող է մնալ առանց վիճակի։

## Ստացեք արտաքին աշխատանք

`Integration.inbound`-ը փաթեթավորում է `InboundConfig`, որի `run` ֆունկցիան ստանում է emit callback։ Աշխատողը մուտքային տեղեկությունը վերածում է հրամանների։ Ծրագրի գործարկումը սկսում է գրանցված մուտքային աշխատողներին։

Webhook ինտեգրմանը դեռ պետք են իրական listener, մատակարարի նույնականացում/ստորագրության ստուգում, մուտքի սահմաններ և հաստատման ռազմավարություն։ Աբստրակցիան ինքնաբերաբար ստեղծված webhook սերվեր չէ։ Նույնպես հերթի սպառողին պետք է հաստատման, վերաառաքման և կայուն առաջընթացի մտածված քաղաքականություն։

## Ապացուցեք ադապտերը՝ նախքան այն թողարկելը

Օգտագործեք `Integration.getActions`՝ մշակիչի ընտրած գործողությունները ուսումնասիրելու համար, իսկ `Integration.runAction`-ը վերահսկվող `ActionContext`-ով՝ կատարումը փորձարկելու համար։ Մաքուր հարցում կառուցող ֆունկցիաները հատկապես օգտակար են արձանագրությունների քարտեզավորումը ստուգելու համար՝ առանց երթևեկություն ուղարկելու։

Ադապտերի թեստերը դրեք Ձեր `tests/` գրացուցակի մյուս թեստերի կողքին։ Մոդուլն ավելացնելուց հետո գործարկեք `neo build`, ապա `neo test`-ով ստուգեք դրա հարցման քարտեզավորումն ու սխալների դեպքերը։ Ստուգեք վավեր մուտքը, մատակարարի մերժումը, սխալ ձևավորված հաջողության տվյալները, բացակայող հավատարմագրերը, ժամանակի ավարտը, կրկնվող կանչը և հեռավոր հաջողությունից հետո կորած պատասխանը։ Վերահսկվող սերվերի դեմ հաշվեք հարցումները։ Վերջում sandbox-ի հավատարմագրերով գործարկեք `neo run` և մատակարարի պայմանագիրը ստուգեք Ձեր ծրագրի հրամանների ու արդյունքի հարցման միջով։

**Վարժություն․** ուսումնական նախագծի համար վերահսկվող թեստային մատակարարի դեմ փաթեթավորեք առաքման կարգավիճակի որոնում։ Թող մեկ այլ ընթերցող այն կազմաձևի՝ օգտագործելով միայն հանրային հարցման API-ն։ Եթե սովորական ընտրություն կատարելու համար նա պետք է հասկանա ներքին HTTP վերլուծումը, վերանայեք API-ն ու փաստաթղթերը միասին։

Գործարկման կախվածությունների, կազմաձևման և վերականգնման պլանավորման համար վերադարձեք [ծրագիրը գործարկելուն](/hy/operate/deployment/)։
