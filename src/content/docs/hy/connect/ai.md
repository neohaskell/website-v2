Գործակալին կոդ գրել տալը և այդ կոդին AI հնարավորություն ավելացնելը տարբեր հարաբերություններ են։ Ծրագրի հնարավորությունը կարող է ամփոփել նշումներ, նախագծել տեքստ կամ օգնել մեկնաբանել փաստաթուղթը։ Դրան պետք են իր մուտքերը, թույլտվությունները, ծախսերի սահմանները, ձախողման վիճակները և ընդունման կանոնները։

Օգտակար առաջին հնարավորությունը վերանայման համար տեքստ առաջարկելն է։ Էլեկտրոնային առևտրի ուսումնական նախագծում Jess-ը մատակարարված փաստերից կստեղծի ապրանքի նկարագրության սևագիր։ Նա կարող է ուսումնասիրել ու հաստատել սևագիրը՝ ծրագրի մնացած մասը օգտագործելի պահելով, երբ մատակարարը հասանելի չէ։

## Հնարավորությունը պահեք Ձեր ծրագրի ներսում

Աշխատեք `mug-shop`-ից և ավարտեք [ինտեգրման կարգավորումը](/hy/connect/#prepare-your-project)։ Հարցման օգնականը տեղադրեք `src/Shop/Integrations/ProductDraft.hs`-ում։ Սևագիր խնդրելու, գրանցելու և ընդունելու հրամաններն ու իրադարձությունները ավելացրեք այն ծրագրային հատվածում, որը տիրապետում է ապրանքի տեղեկությանը։ Cart-ը և Stock-ը դեռ այդ հնարավորությունը չեն տրամադրում։

Մատակարարի արդյունքի հրամաններին տվեք `InternalTransport`. օգտատիրոջ համար նախատեսված սևագրի հարցումը և հաստատումը թողեք առանձին հանրային հրամաններ։ Ծառայությունը, հարցումը և ելքային մշակիչը միացրեք `src/App.hs`-ում՝ հետևելով [հրամաններին](/hy/build/commands-and-events/) և [մշակիչների գրանցմանը](/hy/connect/workflows/)։ Ստորևի ֆակտորին տրամադրում է մատակարարի կանչը, իսկ Ձեր աշխատանքային հոսքն է տրամադրում մուտքերն ու callback-ները։

## Հարցում կատարելուց առաջ մոդելավորեք սևագիրը

Սևագրի աշխատանքային հոսքը գրանցում է հարցումը, կանչում մատակարարին և գրանցում կամ ստեղծված տեքստը, կամ ձախողումը։ Հաստատումը առանձին հրաման է։ Օրինակում պահեք ապրանքի նույնացուցիչն ու հարցման ինքնությունը, որպեսզի ուշացած պատասխանը չփոխարինի ավելի նոր սևագրին։

Մատակարարի callback-ը ասում է, որ պատասխանը հաջողությամբ վերծանվել է։ Այն չի հաստատում փաստացի ճշգրտությունը, հրապարակման համար պիտանի լինելը կամ ծրագրի կանոններին համապատասխանությունը։

## Կառուցեք OpenRouter-ի հարցում

Այս **մասնակի ֆակտորինը** կարճ սևագիր է խնդրում։ `modelName`-ը գալիս է Ձեր ընտրած մատակարարի կազմաձևումից, իսկ `productFacts`-ը պարունակում է միայն հաստատված մուտք։ `recordDraftResponse`-ը պետք է ուսումնասիրի պատասխանը և ստեղծի նույն հրամանի տիպը, ինչ `recordDraftFailure`-ը։

```haskell
Integration.outbound OpenRouter.Request
  { messages =
      [ OpenRouter.system
          "Draft a short product description using only the supplied facts."
      , OpenRouter.user productFacts
      ]
  , model = modelName
  , config = OpenRouter.defaultConfig
      { OpenRouter.maxTokens = Just 300
      , OpenRouter.timeoutSeconds = 30
      }
  , onSuccess = recordDraftResponse
  , onError = recordDraftFailure
  }
```

Ադապտերը bearer token-ը ստանում է `OPENROUTER_API_KEY`-ից։ Ընթացիկ հասանելի մոդելն ընտրեք ու ստուգեք առանձին. հին օրինակների մոդելի նույնացուցիչները ընթացիկ հասանելիության խոստում չեն։

Պատասխանը պարունակում է `choices` և ընտրովի `usage`։ Մշակեք դատարկ choices զանգվածը։ Choice-ը ներառում է իր հաղորդագրությունն ու ավարտի պատճառը. կտրատումը կամ զտումը կարող են նշանակել, որ տեքստը պիտանի չէ, նույնիսկ եթե HTTP հարցումը հաջողվել է։ Հաղորդագրության բովանդակությունը կարող է լինել պարզ տեքստ կամ բովանդակության բազմաթիվ մասեր։

Այս ինտեգրումը կատարում է ոչ հոսքային հարցում։ Այն հարմար է ֆոնային սևագրի աշխատանքային հոսքի համար, բայց ինքնուրույն չի իրականացնում հոսքային չաթի միջերես, զրույցների պահպանում կամ որոնման համակարգ։

## Օգտագործեք Azure AI-ը, երբ տեղին է

Azure-ի հարցումներն ունեն բացահայտ վավերացված endpoint և թաքցված API բանալի։ Օգնականը գտնվում է `Integration.AzureAI`-ում։ Նախ կանչեք․

```haskell
AzureAI.azureEndpoint endpointText
```

Այն վերադարձնում է `Result Text AzureEndpoint`. անվավեր endpoint-ը մշակեք որպես կազմաձևման խնդիր։ `azureEndpointAllowing`-ը թույլ է տալիս Ձեր տեղակայման համար լրացուցիչ վստահելի host suffix-ներ։ Այդ suffix-ները պահեք օպերատորի վերահսկողության ներքո։

Վավերացումից հետո, իրական implicit կազմաձևման կապակցմամբ **արտահայտության հատվածը** հետևյալն է․

```haskell
AzureAI.chatCompletion
  validatedEndpoint
  [AzureAI.system "Use only supplied product facts.", AzureAI.user productFacts]
  deploymentName
  recordDraftResponse
  recordDraftFailure
```

Օգնականը կարդում է `?config.azureAiApiKey :: Redacted Text`։ Հավատարմագրերի բացահայտ կապակցման համար կառուցեք `AzureAI.Request`՝ `apiKey`-ով և այն կազմաձևմամբ, որի `endpoint`-ը վավերացված արժեքն է։ Մերկ լռելյայն կազմաձևումը մի օգտագործեք որպես endpoint-ի ամբողջական կարգավորում։ Սկզբնաղբյուրը ամրացնում է API-ի տարբերակի լռելյայնը. ստուգեք դրա համատեղելիությունը Ձեր տեղակայման հետ։

## Սևագիրն անցկացրեք աշխատանքային հոսքով

`mug-shop`-ին սևագրի ծառայությունն ու մշակիչը ավելացնելուց հետո գործարկեք `neo build`։ Ֆիքսված պատասխանների ստուգումների համար օգտագործեք `neo test`. այդ ստուգումները չպետք է կենդանի մոդել պահանջեն։ Մատակարարի հավատարմագրերով սկսեք `neo run`, խնդրեք սևագիր և ուսումնասիրեք դրա հարցումը։ Հաստատեք, որ ստեղծված տեքստը չհաստատված սևագիր է մնում, մինչև առանձին հաստատման հրամանը հաջողվի։

## Jess-ին գեղեցիկ պարբերությունից ավելին ապացուցեք

> **Գործակալ․** «Մոդելը նկարագրություն վերադարձրեց, ուրեմն հրապարակում եմ»։
>
> **Jess․** «Ցույց տուր հրապարակումը հաստատող հրամանը։ Ստեղծված տեքստը պետք է սևագիր մնա, մինչև ես այն ընդունեմ»։

Կենդանի մոդել թեստավորելուց առաջ ֆիքսված պատճեններով ստուգեք պատասխանի մշակումը։ Ստուգեք բացակայող choices-ը, անցանկալի պնդումները, կտրատումը, մատակարարի մերժումը և ապրանքի փաստերի փոխվելուց հետո հասած պատասխանը։ Ապրանքի փաստերից ու անընդունելի արդյունքներից կազմեք գնահատման փոքր հավաքածու։ Կենդանի մատակարարի կանչերը ստուգում են կապն ու Ձեր աշխատանքի համար պիտանիությունը, իսկ միավորային թեստերը՝ դետերմինիստական կանոնները։

Համօգտագործվող [HTTP կրկնության վերապահումը](/hy/connect/http-and-payments/#understand-the-current-retry-boundary) կիրառվում է նաև մատակարարի կանչերի վրա։ Ժամանակի ավարտը ապացույց չէ, որ վճարովի աշխատանք չի կատարվել։ Սահմանեք ծրագրի ծախսերի քաղաքականություն և մատակարարի հարցման ժամանակի սահմանները համապատասխանեցրեք [դիսպետչերի բյուջեին](/hy/connect/documents/#budget-the-entire-operation)։

**Վարժություն․** ուսումնական նախագծին ավելացրեք վերականգնելու գործողություն։ Որոշեք՝ արդյոք ընթացքի մեջ գտնվող հին պատասխանը կարող է փոխարինել նորին, ապա թեստավորեք պատասխանները հակառակ հերթականությամբ հասնելիս։

Շարունակեք [AI գործիքներին](/hy/connect/ai-tools/) միայն այն ժամանակ, երբ պատրաստ եք, որ մոդելը առաջարկի կառուցվածքային գործողություններ։
