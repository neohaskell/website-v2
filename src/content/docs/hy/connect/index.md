Փոփոխություն պահելը և դրա հաջորդող աշխատանքն ավարտելը տարբեր բաներ են։ Փաստաթուղթը կարող է պահպանվել նախքան դրա նախադիտման ստեղծումը, հաղորդագրությունը՝ նախքան ծանուցման ուղարկումը։ Ծրագիրը պետք է ներկայացնի և՛ ընդունված փոփոխությունը, և՛ դեռ կատարվելիք աշխատանքը։

**Ինտեգրումը** Ձեր ծրագրի փաստը կապում է մեկ այլ աշխատանքի հետ։ NeoHaskell-ը թույլ է տալիս նկարագրել հարցումը և դրա արդյունքը նորից վերածել հրամանի։ Դուք դեռ եք որոշում, թե ինչ է նշանակում հաջողությունը, ինչպես են ձախողումները երևում մարդկանց և որ գործողությունները կարելի է անվտանգ կրկնել։

Ինտեգրումներ իրականացնելուց առաջ վստահ եղեք [հրամանների ու իրադարձությունների](/hy/build/commands-and-events/) և [հարցումների](/hy/build/queries/) իմացության մեջ։ Օրինակները ընդլայնում են էլեկտրոնային առևտրի ուսումնական նախագիծը, մինչ նույն ինտեգրման կյանքի ցիկլը կիրառելի է այլ ծրագրերի համար։ Գնահատողները կարող են հետևել ներածական և որոշումների բաժիններին՝ առանց օրինակներն իրականացնելու։

Շարունակեք `neo new`-ով ստեղծած `mug-shop` նախագծում՝ դրա `src/Shop/Cart/` և `src/Shop/Stock/` մոդուլներով և `src/App.hs` գրանցմամբ։ Նախ ավարտեք [պահեստ և վճարում](/hy/build/stock-and-checkout/) բաժինը, ապա ազդեցություններ ավելացնելիս պահեք գոյություն ունեցող թեստերը։ Այս բաժնի բոլոր հրամանները գործարկվում են այդ նախագծի գրացուցակից։

## Պատրաստեք նախագիծը

`neo new`-ով ստեղծված նախագիծն արդեն ներառում է NeoHaskell-ի հիմնական և ինտեգրումների գրադարանները։ `Integration.Command` և `Integration.Timer`-ը, ինչպես նաև ստորև օգտագործվող HTTP, էլեկտրոնային փոստի, փաստաթղթերի և AI-ի մոդուլները հասանելի են առանց յուրաքանչյուր մատակարարի համար առանձին փաթեթ ավելացնելու։

`neo.json`-ը պահեք որպես նախագծի կազմաձևում։ Ներկառուցված ինտեգրումները դրա կախվածությունների ցանկում նոր գրառում չեն պահանջում։ Եթե անհատական ադապտերին լրացուցիչ գրադարան է պետք, օգտագործեք [CLI տեղեկատուում](/hy/reference/cli/) նկարագրված կախվածությունների կարգավորումները և թույլ տվեք Neo-ին կառավարել ստեղծված կառուցման ֆայլերը։

Ծրագրի կոդը ավելացրեք `src/Shop/`-ի տակ, մշակիչներն ու ծառայությունները գրանցեք `src/App.hs`-ում, իսկ ստուգումները դրեք `tests/`-ում։ Նախագծի արմատից օգտագործեք․

```sh
neo build
neo test
neo run
```

Փոխարինողը սկսելուց առաջ կանգնեցրեք գործող սերվերը։ HTTP հարցումների և IDE-ի համար պահեք մեկ այլ տերմինալ։ Մատակարարի հավատարմագրերը պատկանում են գործող գործընթացի [կազմաձևմանը](/hy/build/configuration/). գրադարան տեղադրելը հաշիվ, հավատարմագրեր կամ ավարտված աշխատանքային հոսք չի տրամադրում։

Կոդի հատվածները կենտրոնանում են սովորեցվող կանոնի կամ հարցման վրա։ Իրականացման մոդուլներն օգտագործում են `import Core`. մոդուլի վերնագրերն ու մյուս ներմուծումները այստեղ բաց են թողնված։ [Ինտեգրման ամբողջական ստուգակետը](/examples/mug-shop-connect.tar.gz) պարունակում է համակարգման, վերբեռնման և ժամաչափի վարժության գործարկվող ֆայլեր։ Երբ ցանկանում եք ստուգել ամբողջական կապակցումը, կիրառեք այն Ձեր առկա նախագծի վրա։

Սկսեք [Cart-ի և Stock-ի համակարգումից](/hy/connect/workflows/), որի համար արտաքին ծառայություն պետք չէ։ Հետագա գլուխները մատակարարների ֆակտորիներ են տեղադրում Ձեր նախագծում և նշում նոր հրամաններն ու callback-ները, որոնք պետք է սահմանեք դրանք միացնելուց առաջ։

## Հետևեք իրադարձությանը ինտեգրման միջով

Ուսումնական նախագծի համար դիտարկեք պատվերի հաստատումը։ Աշխատանքային հոսքը ծրագրի նախագծում է, որը կառուցված է այս ինտեգրման պարզունակ տարրերից․

1. Հրամանն ընդունում է պատվերը և գրանցում պատվերի տեղադրման իրադարձություն։
2. Ելքային մշակիչը ճանաչում է այդ իրադարձությունը և նկարագրում էլեկտրոնային նամակի հարցում։
3. Ինտեգրումը հարցումը կատարում է պատվերի որոշման ֆունկցիայից դուրս։
4. Դրա callback-ը ստեղծում է հրաման, որը գրանցում է մատակարարի ընդունումը կամ ձախողումը։
5. Հարցումը ստացված կարգավիճակը տեսանելի է դարձնում։

Չորրորդ քայլը միտումնավոր **հրաման** է. նոր տեղեկությունը դեռ մտնում է ծրագրի կանոնների միջով։ Մատակարար կանչելը ուղղակիորեն չի խմբագրում էություն կամ հարցում։

**Ելքային** ինտեգրումն արձագանքում է ծրագրի իրադարձություններին։ **Մուտքային** ինտեգրումը սկսվում է իրադարձությունների հոսքից դուրս գտնվող բանից, օրինակ՝ ժամաչափից, և ուղարկում է հրաման։

## Կարդացեք փոքր բառապաշարը

Մշակիչի ներսում աշխատանքը կազմակերպող երկու փոքր գործողություն կա․

```haskell
batch :: Array Action -> Outbound
none :: Outbound
```

`Integration.outbound`-ը աջակցվող հարցման գրառումը դարձնում է մեկ գործողություն։ `Integration.batch`-ը հավաքում է իրադարձության համար կատարվող գործողությունները։ `Integration.none`-ը ասում է, որ այս մշակիչը տվյալ իրադարձության համար աշխատանք չունի։ Փաթեթը հավաքածու է, ոչ թե արտաքին համակարգերի վրա տարածվող գործարք։

Կոնկրետ հարցման տիպը որոշում է հասանելի դաշտերը։ Մատակարարների ինտեգրումների մեծ մասն առաջարկում է `onSuccess` և `onError`։ Երկու callback-ներն էլ պետք է ստեղծեն **նույն հրամանի տիպը**։ Հաջողության/ձախողման այլընտրանքներով հրամանը մեկ տարբերակ է, իսկ միմյանց հետ չկապված երկու հրամանի տիպերը մեկ `Request command` չեն բավարարի։

## Գրանցեք երկու ծայրերը

Մշակիչ սահմանելը այն չի գրանցում։ Ծրագիրը պետք է գրանցի ելքային մշակիչը և յուրաքանչյուր հրաման արտածելու ունակ հրաման պարունակող ծառայությունը։

Արտածվող հրամանները պետք է հայտարարեն `InternalTransport`. ինտեգրման դիսպետչերը դրանք հավաքում է հանրային HTTP endpoint-ներից առանձին։ Մեկ հրամանը չի կարող խառնել ներքին և հանրային տրանսպորտները։ Երբ մարդիկ ու ինտեգրումները նույն կանոնի կարիքն ունեն, օգտագործեք առանձին մուտքային կետեր, որոնք կիսում են որոշման տրամաբանությունը, ինչպես ցույց է տալիս [ժամաչափի օրինակը](/hy/connect/timers/)։ Ամբողջական Cart-ից Stock մշակիչը ավելացրեք Ձեր նախագծին [աշխատանքային հոսքերում](/hy/connect/workflows/)։

Բացակայող callback մշակիչը դիսպետչերը գրանցում է մատյանում։ Դա ապացույց չէ, որ սկզբնական արտաքին գործողությունը ձախողվել է. մատակարարը գուցե արդեն ընդունել է այն։

## Որտեղից է գալիս վստահությունը

Երեք սահման ստուգեք առանձին․

- **Ընտրություն․** նախատեսված իրադարձությունը գործողությո՞ւն է ստեղծում, իսկ կապ չունեցող իրադարձությունը՝ ոչինչ։
- **Թարգմանություն․** մատակարարի արդյունքը ճիշտ հրամա՞ն է ստեղծում՝ ներառյալ սխալ ձևավորված արդյունքներն ու մերժումները։
- **Ավարտ․** այդ հրամանը հասնո՞ւմ է գրանցված ծառայությանը և ստեղծո՞ւմ սպասվող հարցման վիճակը։

Ինտեգրման գործարկման միջավայրն օգտագործում է յուրաքանչյուր էության աշխատողներ և սահմանափակված հերթեր։ Այն ներառում է սխալների մշակում և կազմաձևվող ժամանակի սահմաններ։ Այս մեխանիզմները չեն հաստատում կայուն առաքում կամ գործընթացի վթարից և արտաքին մատակարարից հետո ճիշտ մեկ անգամ կատարում։ Կարևոր չավարտված աշխատանքի համար անհրաժեշտ է ծրագրի մակարդակի վերականգնման նախագիծ։

Տիպավորված մշակիչները մշակելիս էությունը վերակառուցում են իր հոսքից. նրանք չեն ստանում գործարկող իրադարձության պահին վերցված երաշխավորված snapshot։ Այն տեղեկությունը, որը պետք է նկարագրի հենց այդ դեպքը, պահեք իրադարձության մեջ։
