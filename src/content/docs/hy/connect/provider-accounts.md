Մարդը ցանկանում է, որ Ձեր ծրագիրն օգտագործի այլուր պահվող իր հաշիվը՝ օրինակ օրացույցի, փաստաթղթերի ծառայության կամ հաշվապահական գործիքի հաշիվը։ Նա պետք է կարողանա թույլատրել այդ կապը՝ առանց ծրագրին մատակարարի գաղտնաբառը տալու։ OAuth2-ը տրամադրում է համաձայնության հոսք և հետագա մուտքի հավատարմագրեր։

Սա տարբերվում է Ձեր ծրագրում մուտք գործելուց։ JWT նույնականացումը նույնացնում է օգտատիրոջը, իսկ մատակարարի OAuth2 token-ները թույլատրում են մուտք արտաքին հաշիվ։ Ուսումնական նախագծի համար մտածեք փորձնական հաշվապահական հաշիվ միացնելու մասին։ Համաձայնությունը այդ հնարավորության մեկ մասն է. հաշիվ ստեղծելու կամ պատվեր արտահանելու համար առանձին ադապտեր է պետք։

Սկսեք [ծրագրի մուտքի կառավարումից](/hy/build/access-control/) և [ինտեգրման արդյունքներից](/hy/connect/)։ Ընտրեք իրական հնարավորության համար անհրաժեշտ մատակարարի թույլտվությունների նվազագույնը։

## Կապին տեղ տվեք mug-shop-ում

Շարունակեք `neo new`-ով ստեղծած նախագծում։ Մատակարարի կազմաձևումն ու callback-ի կոդավորման օգնականները տեղադրեք `src/Shop/Integrations/Accounts.hs`-ում և դրանք միացրեք `src/App.hs`-ից։ OAuth2-ի և գաղտնիքների պահոցի մոդուլները գալիս են հիմնական փաթեթից. միայն համաձայնության երթուղիները միացնելու համար մատակարարի ինտեգրման փաթեթ պետք չէ։

Նախ `InternalTransport`-ով ավելացրեք միացված, ձախողված և անջատված արդյունքների հրամանները՝ Ձեր գրանցած որևէ ծառայության մեջ։ Հարցումը պետք է ցույց տա կապի վիճակը՝ token-ները չբացահայտելով։ Սրանք հաշվի կապի նոր հնարավորություններ են. Cart-ը և Stock-ը շարունակում են մնալ ծրագրի սկզբնական շերտերը։

## Հաստատեք մատակարարի համատեղելիությունը

Հիմնական փաթեթը տրամադրում է PKCE-ով կարգավորվող authorization-code հոսք, ոչ թե հաշվապահական մատակարարի նախադրված։ `Provider`-ը պարունակում է `name`, `authorizeEndpoint` և `tokenEndpoint`։ Հաստատեք, որ ընտրված մատակարարն աջակցում է հաճախորդի իրական փոխանակման ձևաչափին. form պարամետրերը ներառում են `client_id`, `client_secret` և PKCE verifier։ Մատակարարին հատուկ scopes-ը, authorization-ի լրացուցիչ պարամետրերն ու API գործողությունները պահանջում են իրենց համատեղելիության աշխատանքը։

Գործարկման պահին ստուգվում են մատակարարի endpoint-ների HTTPS-ն ու ցանցային հասցեների սահմանափակումները, իսկ կրկնվող անունները մերժվում են։ Callback URI-ն կառուցեք `OAuth2.mkRedirectUri`-ով, մշակեք դրա `Result`-ը և նույն URI-ն գրանցեք մատակարարում։ HTTPS-ը պարտադիր է, բացառությամբ աջակցվող localhost զարգացման հասցեների։

## Միացրեք հաշվի կապը

Սա **ծրագրի մասնակի ֆակտորին** է։ Շրջապատող ծրագիրը պետք է արդեն գրանցած լինի տրանսպորտն ու ծառայությունները։ `identityServerUrl`, `accountProviderConfig` և `existingSecretStore`-ը Ձեր տրամադրած արժեքներն են․

```haskell
    |> Application.withAuth @() (\_ -> identityServerUrl)
    |> Application.withSecretStore @() (\_ -> existingSecretStore)
    |> Application.withOAuth2StateKey "SHOP_OAUTH_STATE_KEY"
    |> Application.withOAuth2Provider @() (\_ -> accountProviderConfig)
```

Պետության բանալու կարգավորումը անվանում է միջավայրի փոփոխական, որը պարունակում է առնվազն 32 բայթ գաղտնիք։ Այն սահմանեք գործարկումից առաջ։ `withOAuth2StateKey`-ը պետք է նախորդի մատակարարի գրանցմանը։ Կազմաձևումից կախված արժեքների դեպքում `@()` ֆակտորինները փոխարինեք `Application.withConfig`-ով գրանցված կազմաձևման տիպից եկող ֆունկցիաներով։

Ե՛վ `withSecretStore`-ը, և՛ `withOAuth2Provider`-ը ընդունում են **ֆակտորին ֆունկցիաներ**, ոչ թե անմիջականորեն պահոց կամ մատակարարի գրառում։ Գործարկման աշխատանք պահանջող պահոցը պետք է ստեղծվի Ձեր գործարկման նախագծմամբ՝ նախքան ֆակտորինից դրա բռնակը վերադարձնելը. այս API-ն ֆակտորինի արդյունք չի ընդունում որպես `Task`։

Մատակարարի կազմաձևումն ունի այս **գրառման կառուցման հատվածը**․

```haskell
OAuth2ProviderConfig
  { provider = selectedProvider
  , clientId = registeredClientId
  , clientSecret = registeredClientSecret
  , redirectUri = validatedCallbackUri
  , scopes = requestedScopes
  , onSuccess = encodeConnected
  , onFailure = encodeConnectionFailure
  , onDisconnect = encodeDisconnected
  , successRedirectUrl = connectedPage
  , failureRedirectUrl = failedPage
  }
```

`OAuth2ProviderConfig`-ը սահմանված է `Auth.OAuth2.Provider`-ում։ Client ID-ները, գաղտնիքները, redirect URI-ները և scopes-ը օգտագործում են `Auth.OAuth2.Types`-ի տիպերը. գաղտնիքների և վավերացված redirect URI-ների համար օգտագործեք դրա smart constructor-ները։ Հավատարմագրերը պահեք [գաղտնի կազմաձևում](/hy/build/configuration/)։

## Հետևեք երեք երթուղիներին

| Նախատեսված հարցում | Ինչ է տեղի ունենում |
| --- | --- |
| `GET /connect/{provider}` | Նույնականացնում է օգտատիրոջը և ուղղորդում մատակարարի համաձայնությանը |
| `GET /callback/{provider}?code=…&state=…` | Ստուգում է ստորագրված state-ը, սպառում պահված գործարքը և փոխանակում code-ը |
| `POST /disconnect/{provider}` | Նույնականացնում է օգտատիրոջը և փորձում է ջնջել տեղային token-ը |

Connect երթուղին ընդունում է bearer header և զննարկչային redirect-ների համար ունի query-token fallback։ Հնարավորության դեպքում նախընտրեք header-ը. token կրող URL-ները թույլ մի տվեք մտնել ծրագրի կամ proxy-ի մատյաններ։ Callback-ը օգտագործում է ստորագրված state-ն ու պահված գործարքը՝ մատակարարի redirect-ից JWT չպահանջելով։

State-ը ժամկետանց է դառնում հինգ րոպեից հետո։ Դրա գործարքը սերվերի կողմում պահում է օգտատիրոջ ինքնությունն ու PKCE verifier-ը և օգտագործվում է մեկ անգամ։ Այդ պատճառով ձախողված փոխանակումը պահանջում է նոր կապ սկսել, ոչ թե նույն callback-ը վերարտադրել։

## Համաձայնությունը վերածեք ծրագրի արդյունքի

Հաջող փոխանակումից հետո token-ները պահվում են, նախքան `onSuccess`-ը ստանա նույնականացված օգտատիրոջ ID-ն և `TokenKey`-ը։ Յուրաքանչյուր callback վերադարձնում է JSON տեքստ՝ `Integration.CommandPayload` ձևաչափով. այն կառուցեք `Integration.encodeCommand`-ով՝ գրանցված ծրագրային հրամանի շուրջ։

`encodeConnected`-ը մշակում է `Text -> TokenKey -> Text`, `encodeConnectionFailure`-ը՝ `Text -> OAuth2Error -> Text`, իսկ `encodeDisconnected`-ը՝ `Text -> Text`։ Ստացված հրամանները կարող են տարբեր տիպեր լինել, քանի որ callback-ի սահմանը կոդավորված տեքստ է։ Հում token-ները հանեք հրամանների բեռներից և իրադարձություններից։ Կապի հրամանը թող գրանցի ծրագրի կապն ու հարմար հղումը, ապա արդյունքը բացահայտեք հարցումով։

Հաջողության URL հասնելը մի դիտարկեք որպես միացված հնարավորության աշխատանքի ապացույց։ Callback-ի հրամանի dispatch-ը և իրական մատակարարի API գործողությունը թեստավորեք առանձին։ Փոխանակումից առաջ եղած սխալները և `code` չունեցող համաձայնության մերժման redirect-ները պարտադիր չէ, որ կանչեն `onFailure`. ընթացիկ վեբ callback-ը սպասում է և՛ `code`, և՛ `state`։

## Պլանավորեք հավատարմագրերի կյանքի տևողությունը

Լռելյայն գաղտնիքների պահոցը հիշողության մեջ է։ Նախքան կապերը վերագործարկումից հետո պահպանելու խոստում տալը իրականացրեք և տրամադրեք կայուն գաղտնիքների պահոց։ Ընթացիկ ծրագիրը նաև հիշողության մեջ գործարքների պահոց է ստեղծում. համաձայնության ընթացքում վերագործարկումը կորցնում է գործարքը, իսկ մի քանի օրինակները պահանջում են callback-ի ուղղորդման մտածված քաղաքականություն կամ գործարքների պահոցի այլ ինտեգրում։

`TokenRefresh.withValidToken`-ը բացահայտ օգնական է ադապտերների հեղինակների համար։ Այն կարդում է պահված token-ները, կատարում տրամադրված գործողությունը և թարմացնում է այն, երբ կանչողի չարտոնվածության predicate-ով նույնացված սխալ է ստանում։ Թարմացված token-ները պահում է և գործողությունը մեկ անգամ կրկնում։ Այն `expiresInSeconds`-ից առաջընթացային թարմացում չի պլանավորում. յուրաքանչյուր բանալիի թարմացման lock-երը տեղային են գործընթացին։

Բացակայող token-ներին, refresh token-ներին կամ ձախողված թարմացմանը պետք է միացման նոր արդյունք։ Հաշվի անջատումը ներկայումս փորձում է տեղային ջնջում, բայց անտեսում է ջնջման սխալները և մատակարարի revoke endpoint չի կանչում։ Երբ արտադրանքին պետք է, ստուգեք ջնջումն ու իրականացրեք մատակարարի revocation-ը. «անջատված է» հեռավոր revocation-ի ապացույց չէ։

## Տեղային գործարկեք կապի հոսքը

Արդյունքների հրամաններն ու հաշվի կազմաձևումը գրանցելուց հետո `mug-shop`-ից գործարկեք `neo build` և `neo test`։ `neo run`-ը սկսեք զարգացման client credential-ներով և state key-ով՝ մատակարարում գրանցված localhost callback օգտագործելով։ Անցեք համաձայնության միջով և ուսումնասիրեք կապի հարցումը։ Մատակարարի API կանչը թեստավորեք առանձին. redirect էջ հասնելը API-ի մուտք չի հաստատում։

## Վարժություն․ ընդհատված համաձայնություն

Խնդրեք գործակալին ցուցադրել կապը, կեղծված կամ կրկնված state-ը, համաձայնության մերժումը, համաձայնության ընթացքում վերագործարկումը, թարմացման ձախողումը և ձախողվող գաղտնիքների պահոցով անջատումը։ Ապա բացատրեք, թե իր հաշիվը կապող մարդը ինչ է տեսնում յուրաքանչյուր դեպքում։

Վերահսկվող երթուղու ու թարմացման ստուգումները պահեք Ձեր նախագծի թեստերի հավաքածուում։ Դրանք կոնկրետ հաշվապահական մատակարար չեն հավաստում։ Այդ մատակարարի sandbox-ի ստուգումը գրանցեք առանձին, ապա կառուցեք իրական [մատակարարի ադապտերը](/hy/connect/custom-integrations/)։
