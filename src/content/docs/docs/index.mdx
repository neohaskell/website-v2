## Understand the approach

A first version is only the beginning. People ask for new behaviour, rules change, and an application becomes responsible for work that has already happened. You need to explain that work as well as add the next feature.

AI makes it easier to produce an implementation. It also makes it important to be precise about the meaning of a change. “Update this address” could mean a preference for the next order or a change to an order already in progress. Both can be easy to code. Choosing the right meaning requires understanding the process.

NeoHaskell connects that understanding to a shared model. The model describes what people can request, which rules apply, which facts the application records, and what people need to see. Those concepts have corresponding places in the implementation, so you and your agent can discuss the same behaviour at different levels of detail.

![A learning cycle connects your intent, a shared model, implementation with your agent, and evidence you inspect before accepting a change.](/diagrams/meaning-to-software.svg)

*Start with a rule you can explain. Follow it into the model and implementation, then compare the observable result with what you intended.*

## Why the past matters to the next change

When an application shows a value, it is often showing the result of earlier actions. A balance comes from money movements. A reservation status comes from requests, confirmations, and cancellations. Keeping only the current result can leave you unable to explain how it came about.

NeoHaskell’s application framework records accepted changes as events. It uses that history to reconstruct state and prepare views. A correction can become an explicit new fact, and a new report can use information already retained. You choose which facts and context the application needs; the framework cannot recover a reason that was never recorded.

## Follow a working project

The worked examples gradually build a small ecommerce application, starting with one product and a cart. This gives you a familiar setting in which to try each concept. You can follow the practice project or apply the same method to your own application.

The main route is:

1. [Describe application behaviour](/start/event-modeling/) and [agree how to work](/start/trusting-your-agent/).
2. [Set up a project](/getting-started/) and [explore it visually](/getting-started/visual-ide/).
3. [Build applications](/build/) through commands, state, queries, and tests.
4. [Connect systems](/connect/) and add carefully bounded AI features.
5. [Operate and evolve](/operate/) with persistence, deployment checks, and recovery.

Each chapter names what you will understand, what you will build, and what evidence to check. A worked example gives code and checks to run. A partial snippet teaches one mechanism and identifies the surrounding wiring. A design exercise asks you to choose and implement behaviour; suggested reasoning helps you assess the choice.
